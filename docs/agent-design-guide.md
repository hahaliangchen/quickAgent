# Agent 设计

更新：2026-11-11。**本文是当前设计的唯一依据。** 代码、面向 AI 的提示词、Skill、测试和其他文档与本文冲突时，一律按本文修改。标注「待实现」的部分，代码还没有做到；其他文档里的「当前」「已实现」只代表写作当时的状态。

## 1. 出发点

不考虑上下文容量时，最稳、最有效率的 Agent 就是一个朴素循环：消息按顺序堆叠 → 调用 AI → 执行它的工具调用 → 重复，AI 不再调用工具时结束。

问题只在于上下文容量有限。动态压缩、删减上下文会让实现变复杂、问题频出；遇到一种意外就加一种状态，最终成为死板的状态机。本设计不压缩上下文，而是借用编程语言的**函数作用域**来分流和裁剪：

- 函数内部的数据在函数返回后销毁；
- 调用方只知道调用过它、拿到了返回值，不必知道细节。

所以 AI 做事时用 JavaScript 写流程：难以用代码确定的部分声明为**虚函数**，由宿主在运行时交给 AI 完成，虚函数就是上面的朴素循环；一段完整的子流程可以声明为**模块**，由 AI 按契约写成代码（第 3 节）。每次 AI 工作都在自己的函数上下文里进行，上下文随函数返回而释放。这也利用了 AI 极其擅长编程这一点。

主 AI 根据任务选择最轻的方式：普通对话直接回答，小任务可以在权限范围内直接用工具；需要多阶段、重复或并发编排时，用代码表达自己打算怎么做（第 4 节）。程序里的普通函数要有实际实现；需要 AI 决定的地方写清职责、参数和结果，声明为虚函数或模块，不把整个任务预先展开成工程实现代码。可以先写熟悉问题的程序，根据结果再写实施程序，不必一开始就猜完整过程。

**只禁大问题。** 提示词给的书写方向只是建议，宿主只拦真正会出错的做法，不用规则束缚 AI。

## 2. 流程代码就是 JavaScript

- AI 写的流程是普通 JavaScript：顺序、分支、循环、函数、闭包、`async`/`await`、`Promise`、`try`/`catch` 都按 JS 语义理解，不另造流程语言，也不要求 AI 记一套额外规则。
- 当前执行器是 SWC 解析、Rust 自建的 JS 子集虚拟机（见 [执行语言手册](agent-program.md)）。子集的缺口应向真实 JS 补齐，而不是在提示词里教 AI 绕开。
- 给 AI 的编程指南（`read_program_guide`，内容在 `prompts/flow_capabilities.md`）应当越来越薄：虚拟机每向真实 JS 靠近一步，指南里“和真实 JS 的差别”就少一条，理想状态下只剩宿主相关的部分（工具库、虚函数、模块、错误处理）。
- 宿主机制尽量用 JS 已有的形式表达，不在虚拟机里加违背 JS 语义的特殊规则。例如提问是一个带名字的普通错误，恢复暂停的程序是一个返回 Promise 的库方法，模块像 `require` 一样在第一次调用时加载（第 3.3 节）。

## 3. 虚函数和模块

第一层是 module（`/** @module */`），第二层是虚函数（`/** @virtual */`），各用空声明表达契约。主程序先写紧凑的可执行编排计划，说明步骤、数据依赖、输入输出和验收，不一次写完每个阶段的实现。

| 所在位置 | 宿主处理 | 完成方式 |
| --- | --- | --- |
| 主编排中的第一层 @module | 按签名和契约查找已保存实现；缺少时让 AI 写成代码 | 执行代码并返回结果 |
| 实现中的第二层 @virtual | 用准备好的材料执行聚焦的 AI 工具循环 | 返回契约要求的 JSON |
| 普通 JS helper | 直接执行代码，不增加 AI 层级 | 普通 return |

实现文件在哪里由宿主掌握，编排者声明契约即可，不必 import 实现路径。module 按同签名同契约复用同一实现。实现代码采集证据、运行命令、处理数据和测试；随新证据变化的判断交给第二层虚函数，不把当前报告硬编码为通用分析算法。

宿主调度管理器按持久化调用链识别 AI 边界，统一检查同步、并发和恢复调用。普通 JS helper 不增加层数，加载缓存、修复或恢复不重置层数。调用描述和模型输入包含 ai_layer。第二层是终端，不能写程序或派生第三层 AI；越层报 VIRTUAL_LAYER_LIMIT，实现中嵌套 @module 报 SECOND_LAYER_VIRTUAL_REQUIRED。第一层通过显式参数拿输入，第二层才支持 @uses 词法捕获。

```js
const pages = await Promise.all(list.map(page => designPage(shared, page)));
/** @module Design one page from shared material; return {content:string}. */
async function designPage(shared, page) {}
```

宿主链接 designPage 的实现；该实现需要生成正文时，再声明第二层 @virtual writeBody(material)。两层声明都只有契约注释，真正交付的实现入口具有完整函数体，可以保留自身的 @module 注释。普通函数必须有实际代码，不会自动交给 AI 补全。

### 3.1 虚函数：纯 AI 钩子

- 虚函数只做一件事时最稳。提示词建议它功能单一，不承载太多能力；多步的流程，比如“跑测试、看失败、再修改”，写成代码（简单的直接写在主脚本里，复杂的放进模块），不交给一个虚函数。
- 它能用的工具，是声明它的模块代码 import 和 require 的库的方法，另外固定有 `find_library_methods` 和 `ask_user`（第 5 节）。
- 它要看的材料，最好由代码读好，作为参数传进去，不让它自己调工具去读：这样它看到的一定是实际内容，也省去来回的请求。内容太大时，代码按条拆开，分别调用。只有事先不知道要看什么时，才让它自己用工具去找。
- **可以只改工作区，不返回内容。** 改代码这类工作，虚函数直接用工具改好文件就完成了，契约不必有返回值。下一步要用改后的内容就去读文件：验收的虚函数自己读，或者由代码读好传进去。这就像类的方法，写方法改了字段，下一个读方法读这个字段。没有返回值的虚函数回复 `null`，调用方拿到 `null`。
- **一个文件，一步里只有一个写入者。** 要么虚函数直接改、不返回内容，要么它只返回内容、自己不写，由代码写入。两种都可以：改代码适合前者，生成页面、文档适合后者（第 3 节开头例子里的“返回 {content:string}；不写文件”）。不要混用：虚函数已经改好了文件，契约又要它返回文件内容，它只能拿修改说明凑数，代码再把说明写回去，源码就被覆盖了（2026-10-31 [Luna/Terra 对照](luna-terra-feature-probe.md) 里的 `luna-program2`）。
- **验收看工作区，不看转述。** 判断改得对不对，要读实际的文件、跑实际的测试；上一个函数说自己做了什么，不算事实。
- **并发的写入者不碰同一个文件**，就像两个方法不能同时改同一个字段：同一组文件的修改按顺序来，或者按文件分开（第 9 节）。
- 它说做不到（回复 `{"$task_error":…}`）是正常的信号，作为错误抛给调用它的代码（第 8 节）。

### 3.2 作用域和上下文

- 每次调用 AI 都有自己的上下文。主脚本是主任务的对话；虚函数只有自己的函数签名、契约注释、**实际传入的参数值**、`@uses` 点名的变量，以及 `@uses` 点名的库的说明（第 5.1 节）；写模块和修复模块的 AI 只有第 3.3 节和第 8 节列出的那些。调用方的对话、变量和读过的技能都不会带进来。
- 虚函数返回后，它的 AI 工作上下文释放，返回值交给调用方；模块执行及其返回值先使用 JS heap，不会自动进入 AI 上下文。
- 虚函数需要的数据有两条路，都按 JS 的语义：
  - **参数**：调用方显式传入，和普通函数一样。
  - **闭包**：约定注释里用 JSDoc 标签 `@uses <变量名> <说明>` 点名外层变量，像 JS 闭包捕获函数体里引用到的自由变量一样，只捕获点名的那几个，不是整个作用域。按**声明处**的词法作用域解析（调用处同名的局部变量遮不住它），名字不在作用域里或和参数重名时编译报错；值在**调用的那一刻**读取，异步调用之后外层再改也不同步过去。被捕获的变量出现在虚函数的上下文里（`closure`）。点名的是 require 得到的库时，虚函数带上的是这个库的说明（第 5.1 节）。
  - 不让 AI 去任意读取调用方的变量（没有 `read_scope` 之类的接口）；要什么，就在参数或 `@uses` 里写明。
- 模块只有参数一条路（第 3.3 节）。模块里声明的虚函数，可以用 `@uses` 点名模块自己的变量。
- `async` 函数在调用时拿到实参；调用方之后的变化不会同步过去。
- 数据跨作用域只走参数和返回值；工作区里的文件是所有函数共享的状态，改了就在那里，不经返回值转手（第 3.1、9 节）。调用方若发现缺信息，应修改函数的契约（参数、返回结构），而不是让宿主保留内部过程。
- 调用方代码负责检查返回值是否满足约定；不满足就不能当作成功。只改工作区、不返回内容的函数，要检查的是工作区本身。

### 3.3 模块：AI 写成的代码

模块是一段完整的流程，本身就知道自己做什么。主脚本负责编排，比如“读原有代码并分析 → 修改 → 审查并修正”就是三个模块，前一个的返回值作为参数交给后一个：

```js
const request = "……用户的原话……";
const analysis = await analyzeCode(request);
const changes = await modifyCode(request, analysis);
const review = await reviewAndFix(request, changes);

/** @module */
async function analyzeCode(request) {
  // 读取与 request 相关的代码，分析现有实现。
  // 返回 {files:[{path, role}], design:string, risks:[string]}。
}
// modifyCode、reviewAndFix 同样只写契约。
```

- **按契约写一次，之后复用。** 第一次调用时，宿主让 AI 按契约写出模块的代码，编译通过后存成文件再运行；之后对同一契约的调用直接加载这份文件运行，像 `require` 一样，不再请求 AI。同一契约的几个调用同时第一次运行时，只由其中一个请 AI 写，其余的等它写完再运行。同一契约指名字、签名和注释原文完全一样，改一个字就是另一个模块。
- **像维护项目一样演进。** 主 AI 写下一段编排前先看 `chat_modules`，需要时从流程目录按路径读源码。原契约适用就原样声明。只改实现时，用 `write_program({source, revise_modules:{模块名:{version, reason}}})` 指定已读过的当前版本和改动目标。执行到调用时，模块作者收到旧源码、实参和改动理由，交出完整实现。宿主编译通过后存为下一版本，同一轮的并发调用复用它。旧版本仍可从流程目录读取。如果要改输入、返回形状或承诺的行为，声明一个独立契约。
- **写成通用代码。** 模块会被多次调用，不能针对某一次调用把结果写死。写模块的 AI 看到的是契约、第一次调用的实参（只作为例子）、库方法的简要索引和本聊天已有的模块；要用哪个技能，它自己用 `read_skill` 读，调用方读过的技能不带进来（第 5.1 节）。
- **先探路，再实现。** 不知道文件结构或工具的实际返回时，模块作者可以用 `write_program({probe:true, source})` 提交一段保留原签名的只读程序。宿主用本次调用的实参执行，将小份返回值、打印或错误交回同一作者（`module_probe_result`）。探路用普通 JS 和只读文件工具，每段有自己的局部变量，结果完整交回；实际交付不下时明确报错，保留完整结果和读取引用，由作者缩小范围或调整下一段。下一段根据已观察到的路径、行号或结果结构继续。探路源码与回执记入日志，不成为共享实现。作者可以直接交出可复用的完整代码（`write_program({source})`），第一层作者须交付代码实现；需要一次性判断时，代码调用第二层虚函数获得 JSON 结果。
- **只靠参数拿输入。** 和真正的 JS 模块一样，模块不捕获调用方的变量，在模块上写 `@uses` 是编译错误。它自己决定引入哪些库（import 静态库，require 动态库，第 5 节），可以声明虚函数，也可以调用别的模块。
- **自己检查结果。** 运行时“不对劲”只有被看见，才会有人回来改：模块的代码应当检查自己的结果，比如断言、跑测试、对照规格，不对就抛出错误，或者把中间结果打印出来（第 4、8 节）。
- **存放在宿主的聊天文件夹里。** 宿主为每个项目建一个以项目命名的文件夹 `.codex-workspace-mcp/projects/<项目名>-<路径哈希前 8 位>/`（在宿主根目录下，不在项目里；哈希区分同名项目），项目里每个聊天一个子文件夹 `chats/<聊天 id>/`：主程序是这里的 `turn-<轮>.js`，模块文件在 `modules/` 下；项目跨聊天保存的流程在 `flows/`。同一个聊天里后续的调用和后面几轮都能复用，换一个聊天就重新写；要在别的聊天里复用，就把这一轮存成技能，以动态库的形式 require（第 4.1 节，待实现）。宿主在写代码的请求里列出本聊天已有模块的名字和契约；AI 写出同样的声明，就复用现成的。
- 主脚本是主 AI 编写的编排入口，不等同于可调用的 `@module` 实现；需要 shell 的工作必须声明模块，让模块的确定性代码执行。模块按调用方要拿到的结果定义，例如核实过的事实、统计或附文件行号的结论；复用时检查返回结果是否适合当前任务，不能只看它能否执行命令。已知步骤继续写成普通 JavaScript；模块内收集、处理材料，需要 AI 判断时才调用职责窄的虚函数，不强制增加 AI 层。代码分析交给 AI 的证据应包含相关完整单元、外层条件和提前返回。搜索命中只能证明命中的一行。一个适量的完整单元用一次打印，并保留文件和行范围；不要按任意字符位置截掉尾部。宿主实际交付不下时明确报错并保存原结果，AI 根据读取引用分段查看或调整编排，保留已完成操作；未读内容不能作为结论依据。行为结论要核对完整控制路径或实际执行顺序，区分读过测试与运行过测试。

## 4. 一轮对话：结局与记录

日志不再按单条 100,000 字符、200 条记录或最后 20 条静默裁剪。完整记录先保存在运行时；累计日志捕获超过堆预算时以 `OUTPUT_OVER_CAPACITY` 停止，拒收的完整记录也归档。主程序结局和模块探路结果在进入 AI 前按实际剩余上下文检查，放不下就明确失败，不交付成功前缀，原始输出、返回值和错误保存为 asset 并提供读取引用。资源错误由调用方调整编排，不作为普通实现错误自动修复重跑；已完成命令或写入不能盲目重放。只有 AI 下一次请求本身放不下时才是 `ContextOverflow`。显式按范围分页读取仍可使用，不把未请求的其余内容冒充已交付。

用户的消息进入会话；没有程序运行时通常开始新的一轮，运行中插话的处理见第 7.2 节。主 AI 可以直接回答、使用允许的工具，或者用 `write_program` 交出流程代码；不是每轮都必须写程序。交出程序时，宿主把它写进聊天文件夹，从文件读出、编译并执行。程序和调用结果是会话记录，主 AI 根据结果继续工作或向用户答复。

**先了解，再选择是否编排。** 没看过项目就写流程，容易猜错路径和文件，或只把整件事交给一个虚函数（2026-10-31 的 [Luna/Terra 对照](luna-terra-feature-probe.md)）。主 AI 可以先在模型—工具—结果循环里了解任务，也可以把熟悉过程本身写成一段程序；根据实际结果决定后续流程。宿主不规定必须分几段，也不要求先把所有实施细节想完：

- **代码会话可以直接读和修改文件，shell 由模块执行。** 主 AI 可以直接使用允许的结构化文件读取、写入、编辑、替换、目录与搜索、看图、读取附件及查询流程等方法。需要 shell 时，主程序声明 `@module`，由模块的确定性实现代码运行命令；主 AI、主程序和虚函数叶子不能直接 shell，查找工具也不扩大该范围。小型文件改动仍可直接完成；shell 步骤必须写成实际模块代码，不能换成一个宽泛 AI 钩子。插件会话和各类调用仍受原权限约束。
- **缺的方法自己找。** 宿主不默认发送所有工具定义（第 5 节）。代码会话中，主 AI 可用 `find_library_methods` 查找其他在权限范围内的方法；找到的方法只加入当前循环，越过相应上下文边界后不自动保留。发现方法和实际调用都不能扩大权限。插件专属会话使用其声明的能力。
- **看多少、运行什么，由任务决定。** shell 运行与结果处理写在模块代码里；主 AI 根据小份证据和诊断安排后续工作。
- **交出一段程序。** 主 AI 调用 `write_program({source})` 交出主脚本，这次回复里只调用它；宿主写入文件并编译，编译通过就在这次回复结束后运行，编译不过的诊断是这次调用的结果，AI 改好再交。写模块的 AI 也用它交出模块代码。回复正文里的代码一律是回答，宿主不解析、不运行：用户要一段 JS 示例时，回复里的代码只是给用户看的。以前从回复里认 ```js 代码块，既不稳定（代码写在推理里、和工具调用混在一条回复里都会落空），也分不清示例和要运行的程序。
- **代码会话中，程序开始执行时结束当前熟悉阶段。** 主程序编译通过、开始执行时，这段熟悉过程中的工具往来、中间文字和没编译通过的版本离开主 AI 的工作上下文；用户消息、已加载的技能、必要的已保存材料和这份程序保留，原始记录可用 `read_session_history` 读回。本轮已经正常完成的程序，结局也保留：那是做出来的事实，不是熟悉过程（2026-11-06 的运行里，第三段程序一开始执行，第二段的四份分析就从主 AI 的上下文里消失，答复只能凭印象写）。出错的版本只留一行：哪段程序、在哪一行、什么错误。编译不过时什么都没运行，熟悉阶段保留。程序 require 的库按第 5.1 节提供说明。插件专属会话不走这一步清理，保留其会话过程和已加载的插件说明。
- **把程序需要的事实交给程序。** 对会结束熟悉阶段的代码会话，路径、测试文件、参数等执行依据要写成代码或数据，或用 `@uses` 交给虚函数；不能假设此前所有工具输出还在上下文中。需要时从真实文件或已保存材料重新读取。
- **一轮可以有多段程序。** 一段主程序正常完成后，宿主把结果和输出交回主 AI；这只代表这一段结束，不自动代表用户的任务完成。主 AI 可基于实际结果继续读、继续写下一段程序或回答用户。比如先熟悉材料，再按实际情况写实施程序；执行顺序、分批和检查方式由 AI 根据任务决定。出错时按第 8 节处理，已经成功的工作不应重复。
- **没运行的程序要说出来。** `write_program` 和别的工具一起调用，或者在没法交程序的时候调用（例如程序已经在运行），别的调用照常执行，这次 `write_program` 的结果是 `PROGRAM_NOT_RUN`，什么都没写、没运行。

**程序结果与一轮结局要分开。** 每段程序完成或停止时，宿主记录结果及必要的停止位置，主 AI 据此继续或回答；正常完成一段不强制结束整轮。提问、暂停等边界会留下可供用户和后续工作理解的结局。具体记录按实际已完成的副作用说明，不以模型转述替代事实：

| 程序怎么结束 | 结局 |
| --- | --- |
| 正常完成 | 结果和输出交回主 AI；它决定继续工作还是结束这一轮 |
| 虚函数向用户提问 | “程序停在 第 2 行 summarize([…]) → 第 2 行 judge([…])，等你回答：……”（第 7.1 节） |
| 需要用户处理而暂停 | “程序停在 第 5 行 read_file，需要你处理：……需要你做的：……”，这一轮到此结束；程序保留到下一轮，用户处理好后可以恢复（第 7.3 节） |
| 用户插嘴而暂停 | “程序被你的新消息暂停，停在 第 2 行 summarize([…]) → 第 3 行 judge([…])（AI 处理中），这一步还没完成。程序的状态都保留着。”（第 7.2 节） |
| 自愈后仍然出错 | “程序在第 N 行出错停止：……”（第 8 节） |

- **用户看到的是话，不是代码。** 主 AI 用 `write_program` 交程序时，用户看到的只有这次回复的话，界面也不把这次调用显示成带源码的工具卡片；程序作为它自己的记录保存（见下一条）。回复正文里写给用户的代码照原样显示。
- **程序打印的内容交给写它的 AI。** `console.log`／`info`／`warn`／`error`／`debug` 按 Node 的方式输出一行（字符串原样，其他值按 JSON）；运行时保留完整记录，实际捕获预算耗尽时明确失败并归档，不按字符或条数裁尾。主程序结束时，完整日志随程序结果交回主 AI，供它继续工作；出错时输出随错误交回主 AI，模块出错时交给修复者（第 8 节）。结局写明是哪段程序（它的文件名）；若完整内容不适合剩余 AI 上下文，以资源错误给出完整结果的读取引用，由 AI 调整编排。运行时保留的全部输出和返回值随程序记录保存。用户界面的呈现与内部记录分开，不能用程序打印代替对用户的答复。
- **恢复的方法只给 AI。** 两种暂停的结局，用户看到的只说停在哪里、状态保留（需要用户处理时还说要做什么）；怎样用 `previous.resume()` 恢复，只写进交给主 AI 的那份结局。
- **停止路径**从主脚本一直写到停下的那一层：每一层停在哪一行、在调用谁（带参数，用来区分并发的同名调用），最内层若是还在工作的 AI，标「AI 处理中」「AI 正在编写模块」或「AI 正在修复模块」。提问和暂停用同一种写法，新一轮读到的是同一种格式。
- **代码由宿主执行，也作为会话记录保存。** 写程序的 AI 在当前工作上下文里可以看到自己交出的源码与程序结果；执行由宿主负责，虚函数和模块仍只接收各自作用域允许的信息。每轮执行的各段主程序保存在会话的 `program/start` 事件中，含源码和路径。模块的每个版本（写成时和每次修复后）保存在 `agent_modules` 中；主程序和模块同时是聊天文件夹里的文件（第 3.3 节）。会话记录本身在宿主的数据库里。两者都和聊天记录一起随会话回退、删除：回退到某一轮时，那之后写成或改过的模块一起退回。后续对话有会话记忆和历史引用。**回看像剥洋葱，一层一层按需读，不一下全读进来**：先看聊天和会话索引（每轮的请求和答复）；要知道某轮跑过哪些流程，先用 `read_session_history({programs:true, directory:".", turn})` 浏览聊天的流程文件夹。根目录列出该轮的主程序（文件、结局、代码长度、输出行数）和 `modules` 子目录。子目录按契约列出截至该轮可用的模块版本。目录页只给清单，可用 `next_directory_offset` 翻页。要细看时，用 `program` 打开清单里的相对路径，用 `start_line`、`end_line` 读指定行；模块文件可以用 `version` 选历史版本。打开主程序文件时加 `output:true` 可分页读保存的输出。目录视图从会话记录取历史源码，不受聊天文件夹里当前模块版本的影响。先读代码还是先读输出，看要回答什么：想知道当时得到了什么，先看输出；想知道怎么做的、为什么出错，先看代码。用的仍是读聊天记录的同一个方法，不另设工具。
- 新一轮从不重跑上一轮出错或停下的程序；要继续，由主 AI 写新程序。例外是暂停的程序：同一轮里被插嘴暂停的程序（第 7.2 节），以及因需要用户处理而暂停、保留到下一轮的程序（第 7.3 节），都可以由新程序显式恢复。

### 4.1 把成功的程序存成技能（待实现）

一轮程序跑成功了，这一轮本身就是一份验证过的流程：确定的部分已经是代码，虚函数标出了非 AI 不可的地方，用到的模块也是能直接运行的代码。用户可以把这一轮存成项目技能：一份说明，加上一个动态库（第 5 节），库里是由主程序改写成的入口方法和这一轮的模块，别的聊天用 `require` 现加载。之后同类的请求，主 AI 调用入口就行，不必再从头规划、写整份流程，流程里已经确定的编排也不再请 AI。这取代旧的“提炼技能”：旧做法从任务流里选几个步骤，把每步用的工具、输入输出交给模型，重新写成一份文字说明；信息有损，下次还要 AI 读着文字重新规划。

- **从一轮程序生成，用户改过再存。** 用户在程序正常完成的那一轮上选择存成技能。工作被确认点分在几轮里时（第 7 节），从这件工作的第一轮一直选到完成的那一轮，下面的“这一轮”就指这几轮。宿主取出：
  - 这一轮为完成任务而运行的相关主程序；同一段程序自愈时重写过的，取实际跑通的版本。一轮有多段时，各段都要取，不能只取最后一段而丢掉前面已完成的流程，怎么合起来见下一条；
  - 相关程序调用过的模块，包括模块里调用的模块，取这一轮跑完时的版本；
  - 这一轮的记录：用户的原话、结局、主程序自愈时收到的诊断、修复者对模块的修改。

  一个 AI 读这些材料，把主程序改写成入口方法（下一条），写出说明的草稿；用户看过、改过再保存。模块的代码原样保存，不改写：它们按契约写成，本来就是通用代码（第 3.3 节）。
- **主程序改写成入口方法。** 主脚本不会自动变成可复用的模块（第 3.3 节）。存技能时，取出的各段主程序合起来改写成库的方法，写法和模块一样：签名和注释是契约，函数体是改写后的代码。改写的方向：
  - **这一次的值变成参数。** 原话里的题目、页数、模板、素材这类只属于这一次的值，变成入口的参数；只针对这一次材料写死的处理，改成通用的。
  - **编排写成代码，内容留给虚函数。** 这一轮里靠 AI 临场决定、现在已经知道答案的事，比如下一步做什么、走哪条分支、出错后怎么改、分几段几批来做，写成代码；重复的结构用模板和循环生成，检查和导出也由代码做（第 3.1、3.3 节）。写内容的虚函数照旧只做一件事，不为了少几次调用把几份内容并进一个调用。
  - **确认点照旧。** 业务技能规定要用户确认的地方，改写后照样停下等用户（第 7 节），不因为“一键”省掉；入口只在确认点分开。比如 PPT 技能要求用户在大纲卡片上确认后才写页面，存下的就是两个入口：做到大纲卡片，确认后做到导出。
- **存成什么。** 技能保存在项目的 `.agents/skills/<名字>/`，随项目走，和其他项目技能一样列在每次请求里。目录里有：
  - `SKILL.md`：写短，给写程序的 AI 看：用途（什么时候用）、注意事项（来自这一轮的出错和修复），和几行调用入口的用法示例。方法的契约不用重复，用 `read_tool_contracts` 能查到。
  - `modules/`：入口方法和这一轮的模块文件，文件名按聊天文件夹里的规则，是函数名加契约编号。每个文件是库的一个方法：方法名就是函数名，契约就是签名和注释，同步还是异步由声明决定。
- **下次怎么用。** 写代码的 AI 在程序里写 `const notes = require("<名字>")`，再调用 `notes.summarizeFile(path, requirements)`。宿主运行库里存的代码，不再请 AI 写这些模块；库里的模块调用库里的其他模块时，照常按契约找到它；模块里的虚函数照常由 AI 完成。同类的请求，主 AI 熟悉之后写几行主脚本调用入口就够了。参数要从用户的原话里取，这本来就是 AI 的事，所以宿主不另设绕过主 AI、直接运行技能的办法。
- **先换个输入跑一遍。** 改写可能漏掉只属于第一轮的东西。存下后，用户换一个输入调用入口跑一遍：程序正常完成、结果也对，这个技能才算能用；不对就按下一条，从跑通的那一轮重新存。
- **库是只读的。** 方法出错，和其他库方法一样抛给调用方，库里的代码不交给修复者：调用方是主程序，由主程序自愈处理；是聊天里的模块，交给那个模块的修复者。要更新技能，就从新的一轮再存一次，覆盖原来的。
- **需求不同时**，AI 照常写自己的程序和模块，可以只用库里的一部分方法。
- **插件页面的会话**存成的技能放在哪里，尚未决定（第 12 节）。

### 4.2 记忆（待实现）

记忆让 Agent 在一个项目里越用越贴合，经验不随一次对话结束而丢失。它不能只靠用户纠正：那样会纠正的用户越用越强，不会纠正或纠正错了的用户学不到，甚至学偏。所以记忆按来源分三类，各有各的规则：

- **偏好，听用户的。** 语言、协作方式、写法习惯这类事由用户决定，不分用户强弱。用户纠正或说明时当场记下；以后补充了，就更新这一条，不新建。
- **技术教训，看事实。** 宿主本来就记着由事实证明的“错了 → 改对了”：编译诊断之后改对、主程序自愈后跑通、修复者改出的新版本跑通、测试先失败后通过、虚函数说做不到之后上层拆细做成。宿主把这些经过（错误原文、改了什么、改完的结果）交给模型，由模型提炼成教训，附上证据。用户提出的技术判断，先对照事实，比如测试、规格、实际运行：事实支持才记，并附上证据；不支持就告诉用户哪里对不上，不记。
- **能迁移的经验，进技能。** 换个项目、换个用户也用得上的做法，沉淀成技能（第 4.1、5 节），可以共享和审阅。不会纠正的用户引用技能，就能用上别人验证过的经验。

怎么存、怎么用：

- **一条记一件事。** 写清事实、原因、怎么用（适用范围），以及来源：用户的原话，或者哪次修复、哪次测试证明的。先只做项目级：按项目存在宿主的文件夹里，不进项目仓库；团队共用的规则仍然写进项目笔记（AGENTS.md）。
- **索引加按需读。** 和技能一样，每次请求只列每条记忆的名字和一句话描述，要用时再读全文，不全文注入。
- **模型自己记。** 主 AI 用 `remember` 新建或更新一条，用 `forget` 删掉一条；记之前先看索引，已有的就更新。代码、文档、git 记录里已经有的，以及只对这一次有用的，不记。
- **宿主不替模型判断。** 宿主不按关键词判断“用户在纠正”，也不判断“这回做对了”；它只交出事实，判断由模型做。
- **自动保存，但看得见。** 每次保存记一条事件，对话里显示“已记住：……”，用户可以在记忆面板里修改、删除。
- **记忆不是不可违背的规则。** 照着某条记忆做却和事实冲突时，模型把冲突说出来，修改或删掉这一条。
- **补漏。** 当场判断难免漏记。在会话归档这类自然的时间点，宿主可以发一次回顾请求，把这次会话里的纠正和出错修复交给模型，问还有没有值得记的。这次请求按时间点触发，不按内容触发。

## 5. 工具是库

工具方法以库的形式提供，调用返回工具的原始 JSON。库分两种，就像 JS 的内置模块和第三方包。项目技能里的库随第 4.1 节待实现。

- **静态库：宿主自带的工具。** 比如文件工具 `io`，一直都在。宿主自带的工具按能力分成几个库，见第 5.2 节。源码里用 `import * as io from "host:io"` 引入，编译时链接；写了不存在的库或方法，编译就报错。像 Node 一样，`host:<库>/promises` 引入同一组方法的异步版本，每个方法返回 Promise。
  - 也可以像 Node 里 `require("fs")` 那样写 `const io = require("io")`：执行到这一行时拿到同一组方法，`require("io/promises")` 拿到异步版本，同一次运行里再 require 拿到同一个对象。这样写的方法在调用处才检查，不在编译时检查。名字是 `host:` 后面那部分；项目技能和宿主自带的库同名时，先找宿主的库。没有 import 的程序里，宿主自带的库按名字就能用；程序自己声明了同名的变量时，比如 `const io = require("io")`，这个名字归程序自己。
- **动态库：第三方带来的工具。** 插件的工具方法（比如 ppt-master 的 `ppt`）和项目技能里的库（第 4.1 节）属于第三方，像 `require()` 一样现加载：
  - 程序执行到 `const ppt = require("ppt")` 这一行，宿主才按库名找到它，链接它的方法，返回模块对象。插件的库名是清单里的 `library`，要已启用；项目技能的库名就是技能名。用法和静态库相同，`require("ppt/promises")` 拿到异步版本。
  - 同一次运行里再 require 同一个库，拿到的是同一个对象；没有执行到的 require 不加载。
  - 一般的库找不到时，在 require 这一行抛错，由代码或写程序的 AI 处理。已激活插件声明的必需库或方法不可用时属于插件不可用，宿主报错中断，不能让 AI 猜测替代能力（第 8 节）。
  - 已启用的动态库不需要在每次 require 前另做激活。进入插件专属会话时，宿主负责激活插件及其声明的工具和说明；其他技能通过 `read_skill` 读取说明。写代码的 AI 用 `read_tool_contracts` 查方法契约，像先看 `.d.ts` 再写 require。
  - 程序挂起后恢复时，宿主重新链接已经加载的库；库已经不在，或者用到的方法已经没有了，就在调用处明确报错，不拿旧的契约去调用。
  - 方法可以由插件的原生代码、远程服务或命令实现，也可以是项目技能里的 JS 模块，在宿主的虚拟机里运行。
- 宿主**不在每次请求里发送完整工具列表**，以减少工具定义带来的上下文开销：写代码的请求只附简要索引，业务工具的完整定义不随请求发送。简要索引列出静态库的方法，以及可以 require 的库的名字和用途。
- 写代码的 AI（主 AI，以及写模块、修复模块的 AI）拿到简要索引和本聊天已有模块的列表，需要时用 `read_tool_contracts` 查方法契约、用 `read_program_guide` 查语言细节。主 AI 在熟悉阶段另外能直接调用几个读取、编辑和看图的方法；需要 shell 时声明模块，让模块代码执行，缺的用 `find_library_methods` 查（第 4 节）。写模块的 AI 只能调用这两个工具，以及读技能说明的 `read_skill`（第 5.1 节），其余都要写进代码；修复模块的 AI 另外能用 `edit_file`，只能改它负责的那个模块文件（第 8 节）。
- **虚函数的工具范围 = 声明它的模块代码 import 和 require 的库方法，排除 shell。** 写代码时引入什么，本身就是对这些虚函数需要哪些能力的预期，所以库要按能力拆开（第 5.2 节）。
- 虚函数的循环里固定保留 `find_library_methods` 和 `ask_user`。`find_library_methods` 按关键词查找方法，查找范围包括可以 require 的库，命中的词越多越靠前；找到的方法只加到**这一次循环**的范围里（由这次循环自己的消息推出），随函数返回消失，不写入持久状态；只能搜索，不提供「列出全部」。`ask_user` 见第 7.1 节。
- 查找、import 和 require 都不扩大权限，权限检查发生在实际调用时。

### 5.1 技能说明跟着引用走

技能的说明（SKILL.md）是库的文档。和普通语言里的函数一样，一个函数只带它自己用到的东西：哪段代码引用了这个库，说明就作用在那段代码上，不按调用关系往下传。比如控制整个做 PPT 流程的插件，在主程序里 require，它的说明给主 AI；只有某个函数要按 markdown 规则写东西，就在那个函数那里引用 markdown。

- **先有说明，再引用。** 写代码的 AI（主 AI、写模块的 AI）使用有说明的库前读取相应说明。插件专属会话的插件说明由宿主预先加载，不需要 AI 再调用 `read_skill`；其他技能用 `read_skill` 读。读到的说明只作用于相应 AI 的上下文。
- **说明跟着引用它的代码。** 一段代码 require 了某个库，宿主就把这个库的说明给负责这段代码的 AI：主程序的是主 AI，包括自愈时；模块的是写它和修复它的 AI。
- **虚函数只带它点名的。** 虚函数没有代码，它要按某个技能做事，就在契约里用 `@uses` 点名那个库的变量，像闭包只捕获用到的变量：

  ```js
  const md = require("markdown");

  /**
   * @virtual
   * 把 notes 写成一节 markdown，返回 {text:string}。
   * @uses md 按它的规则写
   */
  function writeSection(notes) {}
  ```

  点名了 `md`，它才带上 markdown 的说明；没点名的虚函数不带任何技能说明。它的工具范围不变（见上文）：工具在列表里只占一个名字，用不用由它自己决定；说明是一整份读进上下文、会被照着做的，所以只按用到带。
- **不按调用关系继承。** 父函数读过、引用过的技能，不自动带进它调用的函数；被调用的模块要用，自己 require。插件页面的会话属于这个插件，相当于主程序引用了它：插件的说明给主 AI，函数要用，同样自己引用。
- **只有说明的技能也用 require 引用。** 比如 commonmark、spec-driven-testing 这类没有方法的技能，`require("commonmark")` 拿到一个没有方法的对象，作用是把说明挂到这段代码上，就像 webpack 里 `import "./style.css"` 这种只为副作用的导入。这样所有技能都只有一种引用方式。

### 5.2 宿主自带的库按能力拆开

一个库只管一类能力，就像 Node 把内置模块分成 `fs`、`child_process`、`http`。import 什么，就是要什么能力：这样虚函数的工具范围（第 5 节）才有意义，每次请求带上的工具定义也只有用到的那几个库。

| 库 | 方法 |
| --- | --- |
| `io` | 文件：`read`、`read_lines`、`list`、`search`、`write`、`edit`、`replace`，以及工作区信息 `workspace_info` |
| `process` | 平台 shell 命令与会话：`exec_command`、`write_stdin`、`kill_session`；保留运行程序和项目脚本、安装依赖、查看和停止项目进程：`run_program`、`run_project_script`、`install_dependencies`、`get_project_process`、`stop_project_process` |
| `http` | `probe` |
| `browser` | `open`、`read`、`wait`、`diagnostics`、`click`、`press_key`、`upload`、`screenshot`、`close` |
| `memory` | 工作记忆、架构记忆、符号的业务上下文，各有 `record_*`、`list_*`、`search_*` |
| `vision` | `view_image`、`analyze_images`、`image_analysis_results` |
| `attachments` | `read_attachment` |
| `session` | 主对话自己的材料和记录：`read_session_history`、`read_asset`、`list_context_assets`、`refresh_asset`、`propose_project_note`。只有主脚本能用，虚函数和模块拿不到（第 3.2 节） |

- **不设兜底的库。** 每个宿主工具都属于一个有名字的库，新增工具时同时定下它归哪个库。测试按工具目录逐个检查，有一个没有归属就失败。
- **方法名**去掉和库名重复的前缀，比如 `browser_open` 成为 `browser.open`，`http_probe` 成为 `http.probe`；其余沿用原工具名，`io` 保留现在的短名。
- **按实际请求验收。** 虚函数只拿声明它的模块所引用且当前允许的非 shell 方法，以及固定的 `find_library_methods` 和 `ask_user`；即使模块 import 了 `process`，shell 三方法也不暴露给虚函数。shell 只供模块的确定性实现调用，主程序和主 AI 同样不能直接调用。

Shell stage 1 的三个方法属于 `process`，旧方法保留；只有模块的确定性代码能 shell，主 AI、主程序和虚函数均不直接运行。需要 shell 的主流程用 `@module` 声明职责，模块实现读取、运行、解析和检查；AI 钩子保持小而专一。Windows 用 PowerShell 7、Linux 用 Bash，路径和能力由 system 动态注入；每条 cmd 启动新进程，变量和 cd 不持久化，长进程保留 session，无 PTY。同 task、同 turn 的 shell 共用 `change_interval`，重叠改动合并跟踪到最后退出；别的 task/turn 与宿主编辑、写入、undo 等待全部停止。程序收到真实 stdout/stderr 和退出码，默认合计 8 MiB 输出堆预算；超限以 `SHELL_OUTPUT_OVER_CAPACITY` 明确失败，不交付成功前缀，保留完整 asset 和会话读取引用，后续模块可用 stream 分页处理。模块返回值先进入 JS heap，不能统称 AI 上下文；AI 只看打印、诊断、显式虚函数输入和成果摘要。详见[手册](agent-program.md#shell-stage-1process-库)与[shell 模块示例](../skills/task-program/examples/shell-in-module.js)。定位源代码优先 scoped `rg --files`／`rg -n`，默认遵守 `.gitignore`；不要递归 Get-ChildItem 扫遍 target 等产物。

### 5.3 插件提供能力与业务流程

插件可以只提供库和工具，也可以同时提供 Skill；没有 Skill 的插件无需伪造说明。插件声明了 Skill 或所需资源时，宿主必须加载有效内容，缺失或不可用就报错中断；插件声明了工具时，宿主必须保证其库和方法可用，不把连接失效当成让 AI 自己猜的普通业务失败。

内置插件（随宿主发布，如 `code-flow`、`git`）是 Agent 的外围核心：宿主启动即激活，不能停用，设置里的启用开关对它们无效；可以重载。只有外部插件可以启用或停用（`skill_packages::set_enabled`）。

Agent 的核心提示词始终保留；插件 Skill 是本插件业务如何做事的说明，在插件启用期间随会话生效，不取代 Agent 的核心职责。插件提供的方法仍按现有权限、工具契约和插件自身的确认规则执行。离开或停用插件时才卸载它的能力和说明；内容发生变化时重新加载插件，使宿主和服务端版本一致。

## 6. Promise 取代子 Agent

- 并发用 `async` 函数（虚函数或模块）加 `Promise.all`／`Promise.race` 等表达，可以并发，也可以不等待、先做下一件事。
- 不存在单独的「子 Agent」「任务分支」概念；一次虚函数调用就是一次 AI 工作，一次模块调用是运行一段代码（第一次调用时先由 AI 写出这段代码），结果都是返回值。
- 模型调用的并发数由宿主的队列限制。
- 并发的调用和串行的一样会被插嘴暂停（第 7.2 节）：各自在自己的下一步停下，恢复时各自从最内层接着跑。

## 7. 和用户的交互

程序运行中，用户和程序之间有程序主动提问、用户插话、宿主发现只有用户能解决的障碍，以及业务插件要求用户确认的边界。它们的停法不同：

- **提问是程序自己发起的**，所以是一个带名字的错误，沿调用链往上抛，代码有权处理它，比如认出它以后改用默认值、不去问用户。
- **插嘴来自用户**，是程序外部的决定，所以由宿主从外面暂停程序，程序里的 `catch` 拦不住。
- **需要用户处理的障碍是宿主判定的**，也在程序外部：和插嘴一样从外面暂停，`catch` 拦不住（第 7.3 节）。

### 7.1 向用户提问

- 虚函数需要用户确认或补充信息时调用 `ask_user`，它就在这里结束：问题以名为 `WaitingForUser` 的错误（`code: WAITING_FOR_USER`）向上传。
- 模块不会把它当成代码错误交给修复者；主程序也不会为它自愈。代码若捕获错误，按 `error.name === "WaitingForUser"` 认出它；没有特别处理时应当重新抛出。这是普通 JS 的做法，虚拟机不另设不可捕获的规则。
- 问题经过每一层调用时补上那一层的停止位置，到达主程序后成为这一轮的结局，程序到此结束。提问不会暂停程序，也没有恢复。
- 用户的下一条消息，无论是同意、否决还是别的话，都开始新的一轮，主 AI 据此写新程序。

插件的明确确认边界与普通 `ask_user` 不同：插件可以在执行页面操作前返回 `WAITING_FOR_USER`，宿主不派发该操作，将问题交给用户并结束当前主程序；程序中的 `catch` 不能吞掉这个边界。插件决定何时、为何确认，宿主只执行通用的授权与等待协议，不把某个业务步骤硬编码进 Agent。用户确认后再按当前会话继续，不把“方案已保存”当成“用户已确认”。

### 7.2 程序运行中用户插嘴

- 程序是按用户当时的需求写的，新消息可能让后面的步骤作废，也可能只是追加内容，所以插嘴会**暂停**整个程序：既不塞进正在运行的虚函数，或正在写、修模块的窗口（那会破坏函数只看自己参数的隔离），也不直接结束程序。
- 宿主在每个帧的下一步之前从外面停下它：正在执行的工具调用先做完，每一步都有记录，各帧的状态原样保留。暂停的程序移进自己的帧，和主 AI 并行存在，不算当前任务。
- 主 AI 在同一轮里收到暂停的结局和这条消息，自己决定接下来怎么做：
  - 继续旧程序：新程序 `import * as previous from "host:previous/promises"`，`previous.resume()` 返回一个 Promise，让旧程序从停下的那一步接着跑，得到它的返回值；可以和新工作并行，也可以 `await` 后再做。这个库只在有程序暂停时出现。
  - 不继续：新程序不调用它，或者只用文字回答。旧程序在这一轮结束时丢弃，已写入的文件保留。
- 恢复中的程序再被插嘴，会和新程序一起再次暂停；下一个程序恢复新程序时，两层一起接着跑。旧程序里的提问经过 `previous.resume()` 原样传上来，仍然是提问。
- 没有程序在运行时，插嘴照旧直接交给主 AI。

### 7.3 需要用户处理时暂停

有些失败再怎么换做法也解决不了：没配置的能力或设置（如联网搜索的凭据）、用户或审查拒绝的操作、权限模式不允许的操作，以及同一个调用以同样的错误连续失败多次。宿主把这类结果标为 `NEEDS_USER`。它不是程序自己要问的问题（第 7.1 节），而是宿主在程序外部发现的障碍，所以按插嘴的方式处理：

- **整个程序在安全点暂停。** 被拦的那一步不交付给程序，代码里的 `catch` 拦不住它；其余各帧在自己的下一步之前停下，状态原样保留，和第 7.2 节相同。虚函数的工具调用被拦时，它所在的函数也一起暂停。
- **这一轮到此结束。** 结局写明停在哪一步、错误是什么、用户需要做什么，不再请 AI 绕过它。主 AI 直接调用工具（不在程序里）遇到障碍时，只能回复一次告诉用户，不能再调用工具。
- **程序保留到下一轮。** 用户处理好以后发消息，新一轮的主 AI 写新程序，`previous.resume()` 让旧程序从被拦的那一步重试：程序代码里的那一步重新执行；虚函数里的那次调用，它的 AI 收到“用户已处理，请再调用一次”。已经完成的步骤不重做。下一轮结束时仍没有恢复的，和插嘴暂停的程序一样丢弃。
- 宿主不为此另设状态：判定只看工具结果，暂停与恢复沿用第 7.2 节的帧机制。

### 7.4 用户停止后接着跑

用户点停止，多半是方向不对，也可能只是想先停一下。所以停止不丢掉程序，也不自动恢复，而是和第 7.3 节一样保留到下一轮，由主 AI 看了下一条消息再决定。

- **停止是立刻中断，不是安全点。** 正在执行的那一步可能做了一半。宿主把主程序连同各层调用的帧原样留下，结局写明停在哪一步、哪些操作没做完；用户看到的那份只说停在哪、能接着跑，怎么恢复只写在主 AI 那份里。
- **下一轮由主 AI 复盘。** 用户要接着做，主 AI 写 `await previous.resume()`：已完成的步骤不重做，程序代码里没做完的操作从头再做一遍；虚函数自己发出、没拿到结果的调用，它的 AI 收到"被中断、结果不确定"，自己决定要不要再做。用户改了需求，或者没做完的操作不能做两遍（例如改了一半的 shell 命令），就不恢复，写新程序；保留的程序在这一轮结束时丢弃。
- **只保留一轮。** 被停止的那一轮不消耗这一轮；正在恢复别的程序时被停止，两层一起保留。
- **换了宿主读不回来就丢弃。** 调教阶段常常停下、改代码、重启后端再继续。保存的状态是旧版本宿主写的，读不回来时在下一轮开始前丢弃，并告诉主 AI"上一段程序无法恢复，写新程序"，不报错。
- 恢复的程序在自己的任务里运行（和并发调用一样），不在调用方的栈上嵌套：恢复中再恢复时，每层都嵌一整个循环，debug 构建下会栈溢出。

## 8. 错误：统一走异常

- **编译错误**：源码在任何操作前整份编译；失败时什么都不执行，带行列和原因的诊断交回同一个 AI，由它改正后重新提交。正常的诊断和宿主进程崩溃是两回事；进程崩溃时不能声称已返回编译错误。
- **运行时错误**：按 JS 语义沿调用栈 `throw`，由流程代码的 `try`/`catch` 决定重试、换做法或继续上抛。
- **AI 写的代码出错，交回 AI 改。** AI 写的代码不可能次次正确：
  - **模块**：模块调用中没有捕获的错误，交给一个新开的修复者。它只拿到模块文件和这次的问题：错误和停止位置、这次调用的实参、程序打印的输出、已经完成的写入，以及模块 require 的库的说明（第 5.1 节）。模块的代码本身就带着足够的上下文，不需要当初写它的 AI。修复者像通常的编程 Agent 一样只改出问题的地方：用 `edit_file` 按原文精确替换，只能改这个模块文件，改动大时一次替换一整段也可以；每改一次宿主就编译一次，编译不过时，诊断作为这次 `edit_file` 的结果返回，它接着改。它回复改好了，宿主把文件存为新版本，从头重跑这次调用（不重做已列出的写入），之后的调用都用新版本；它也可以回复 `{"$task_error":…}` 放弃，这时错误才抛给调用方。修复进行时，已经在跑的同一模块的调用照旧用旧版本；在同一版本上出错的调用等这一次修复，不重复修。
  - **主程序**：没有捕获的错误，连同这一轮已写入的文件，交回主 AI。它在同一轮里用 `write_program` 交出修正后的完整程序（从头运行，不重做已写入的部分），或用文字告诉用户为什么做不成。这时熟悉阶段的上下文已经去掉，需要时它可以再看、再跑（第 4 节）。每轮最多重写 3 次；仍然出错时，错误作为结局结束这一轮，下一条消息从新的一轮开始，不会重跑出错的程序。
  - **出错的程序收回它发出的调用。** 一段程序（主程序，或模块的一次调用）因错误结束时，它还在跑的并发调用在各自下一步之前停下：正在执行的工具调用先做完，之后不再请求模型，帧记为中断，结果不交付。主程序的诊断里列出被停下的调用。重写或重跑的程序从头开始，不接着用它们。这和 Node 里没被处理的错误让进程退出一样：没人再等的工作随之结束（2026-11-06 的运行里，出错后另外 8 个调用又跑了约 50 次请求，和重写的程序抢并发名额，结果没人用）。
  - 普通函数的错误照常直接抛出；提问不是错误，不自愈。
- **虚函数说做不到是正常的。** 它回复 `{"$task_error":…}` 时，错误抛给调用它的代码，和其他错误一样处理：代码可以捕获它、换一种做法；模块里没有捕获的，交给修复者。修复者通常该做的是把活拆细或换一种做法，而不是把“这一块做不到”当成整个任务做不到。
- **单个结果太大不算超限。** 一个工具结果放不进虚函数剩下的上下文时，结果不交付，虚函数收到它有多大、为什么没交付，换一个更窄的调用（更小的路径、行范围或数量）；必须全部才能做时，回 `{"$task_error":…}`。虚函数没有读资产的工具，所以不让它分页去读。
- **上下文超限：不压缩，直接抛错。** 虚函数自己的上下文放不下下一次请求时，它以名为 `ContextOverflow` 的错误结束，异常回到调用它的代码：代码可以把工作拆得更细后重新调用，或者继续上抛；模块里没有处理的，同样交给修复者。错误中带上虚函数已经完成的副作用（例如已写入的文件），避免上层重复写入或覆盖。
- **主窗口放不下时，交给 AI 自己处理，不暴露给用户。** 放不进剩余空间的结果不交付，原件存为资产，AI 收到 `MATERIAL_OVER_CAPACITY`（大小、剩余空间、资产编号），自行决定按页读取、释放已加载的材料或换一种做法。
- **输出截断或工具调用参数不完整**：模型以 `length` 结束，或任何工具调用的参数不是完整 JSON 时，该回复中的调用全部不执行；宿主记录原始调用，把不完整参数替换为安全的历史内容，并向 AI 返回截断及未执行的提示，让它在同一轮缩短后重试。纯文字被截断也要提示未完成。参数写完了却不是合法 JSON（例如字符串里有非法转义）不是截断：调用同样全部不执行，宿主说明解析错误和出错处附近的原文，不让 AI 去缩短。输出 `write_program` 等工具参数时，流式事件记录工具名和参数长度，界面可显示进度；它不代表程序已经开始执行。
- **模型服务连不上，不算谁做不到。** 模型请求在拿到完整回复之前没有任何副作用，连接失败、回复完整之前超时、5xx、429 时宿主退避重试几次（429 按 Retry-After）。仍然不行，就以名为 `ModelUnavailable` 的错误结束，只写原因、不带服务地址；它和提问一样升到主程序，不交给修复者，也不触发主程序自愈。
- 模型的上下文窗口按该模型条目声明的值取（`contextWindow`，如 deepseek 1,048,576、qwen 262,144、subapi 的 GPT 1,050,000）；没声明的模型才用保守默认 256k，另有一个只防明显错值的上限（2,000,000）。
- **思考不关。** 思考等级最低是 low，配置成 none 或 minimal 也按 low 发。
- **两种接口。** 提供方默认走 Chat Completions；配置成 `api: openai-responses` 时走 Responses，像 Codex 一样：角色提示词是 `instructions`，其余系统消息在原位置成为 developer 消息，消息的名字写在正文开头；`store: false`，要求返回加密推理，每一步把模型之前的推理项放回请求、排在它引出的调用前面，模型接着自己的思路走。Chat Completions 没有地方放加密推理，经 sub2api 这类把 Chat 转成 Responses 的中转时，前面几步的推理就传不回来。两种接口的回复都整理成同一种消息，宿主其余部分不区分。
- **结果未知的外部写操作不自动重放。** 进程中断时被切断的调用不会在重启后接着跑，因为它最后一步可能已经执行却没有记录；这些调用按失败处理。只有插嘴暂停在安全点停下的调用才会接着跑；用户停止时进程还在，宿主知道哪些操作被切断，由主 AI 决定是否接着跑（第 7.4 节）。

## 9. 副作用边界

作用域隔离的是上下文，不是外部世界。并发的虚函数和模块可能写同一个文件，所以宿主为 Agent 的写入保留按文件的基线；遇到外部修改或并发冲突时停止并保留双方内容（`managed_files`）。基线按任务记，看的是谁改的，不是用什么改的：任务自己运行的命令改了它管理的文件，和受管写入一样算它自己的改动，命令结束后基线跟上；命令开始前文件就已经和基线不同，基线不动，下一次写入照样停下；仍在后台运行的进程之后还会写，它的改动不算。命令运行时宿主里的其他写入都要等它，分不清的只有这段时间里宿主之外（用户的编辑器、其他进程）改了同一个文件，这种情况算作任务自己的改动。外部修改只在一轮之内算：每轮开始时，和基线不同的文件把基线改成现在的内容，因为两轮之间是用户在掌控，那时的改动就是新一轮要面对的现状（2026-11-11，任务第 1 轮读过的文件下午被另一个会话改了，第 7 轮重新读过后再改，仍按六小时前的基线判成冲突，整轮失败）。代价是：上一轮停下保留的程序，若在下一轮恢复后整份写一个两轮之间被改过的文件，不再被拦。

同一个任务里的函数共用这份基线，所以函数之间另有一条规则。每次写入，不管是受管写入还是命令的改动，都记一个写入版本和写入者：并行的 async 函数记它自己，主程序和它的同步调用记 `@main`。async 函数开始时记下当时的版本号，被插嘴暂停的程序记暂停那一刻的版本号。async 函数用 `io.write` 整份写一个文件时，如果它开始之后有别的写入者写过这个文件，它手里的内容可能是旧的，宿主就停下，保留当前文件和待写内容。它开始之前的写入不算，所以按顺序调用的函数、后面几轮的函数都不受影响。宿主不记函数读到的是哪个版本，同时运行的函数即使重新读过文件，也照样会被拦；提示词里"一个文件一步只有一个写入者"，就是引导模型避开这种写法。局部修改（`io.edit`、`io.replace`）是在文件当前内容上替换，抹不掉别人的改动，不检查；主程序自己的整份写入也不检查。

这属于副作用边界，与上下文管理无关。

## 10. 已废弃，不得恢复

以下机制与本设计冲突，已经删除，不得再加回来：

- **上下文折叠**：按容量把旧对话折叠成摘要（原 `step_context`）。资产存储及 `read_asset`、`release_assets` 等工具不在此列：它们是 AI 自己处理大材料的手段，保留。
- **任务/步骤/saga 流程**：任务树的步骤节点和结束节点、结束节点持有迭代器、模型可调用的 `create_task`／`branch_task`，任务板（`read_task_board`）与任务定义、计划确认（`main_task_anchor`）。保留下来的是精简后的函数帧。
- **从回复正文解析程序**：把回复里的 ```js 代码块当成要运行的程序。程序只经 `write_program` 交出（第 4 节）。
- **要 AI 额外记住的特殊 API**：`invoke_library`、`define_task_body`、`host.read_scope`／`scope_variables`，以及要求 AI 手动调用的 `execute_program`、`check_program`。（`read_program_guide` 保留，是按需查阅的编程指南，不是流程的一部分。）
- **完整工具列表**：每次请求都附上所有工具定义。
- **兜底的 `host` 库**：没归到其他库的宿主工具全部并进一个库，import 它就拿到全部能力。宿主自带的库按能力拆开（第 5.2 节）。
- **适配层**：把虚拟机执行伪装成旧式工具往来，以便沿用上述机制。
- **用状态驱动流程**：状态标记、完成确认、计划工具、证据/阻塞校验、催促提示。

- 第 2 节的两处缺口，都出现在 2026-10-31 的对照里。一是 `require("host:io")` 被拒：Node 里 `require("node:fs")` 和 `require("fs")` 都能用，require 也应当接受 `host:` 前缀（Terra 第一次写的程序）。二是调用没有声明的函数时，诊断说的是 “call/ai wrappers are unsupported”，应当和 JS 一样说 `implementAndTest is not defined`（`luna-program` 第一次写的程序）。

### 近期验证与风险（2026-11-02）

- 一轮内的多段主程序、插件 Skill 与库加载、插件确认边界、长 console 行和工具调用生成进度已有宿主实现；当前工作区相关代码尚有未提交改动。Qwen 和 DeepSeek 的 PPT 会话验证了插件确认后分批编写、执行和保存页面的实际路径，不代表虚函数、模块复用及修复等全部能力均经过真实验收。
- DeepSeek Flash 的一次 10 页任务中，模型提交的流程源码已保存，但宿主在记录程序开始前发生线程栈溢出，进程退出；具体触发位置和原因尚未定位。重试时模型分批提交程序，10 页成功导出，没有再次发生栈溢出；这不能证明原问题已经修复。外部写入结果未知时不自动重放。
- 同一次成功重试中，结束页因漏掉模板属性被插件拒绝，模型读取原页面后修复并继续；该例验证的是业务插件的恢复路径，不是把 PPT 规则写进通用宿主。

31. 模块按交付结果定义，完整输出遇容量壁障显式失败（2026-11-07）：提示与示例强调返回核实的事实、统计或附证据的结论，复用按契约结果判断，保留普通 JS 与可选窄职责虚函数。取消 VM 单条字符裁剪、日志记录淘汰、主程序最近 20 条和短返回值、模块探路预览。捕获内存、shell 堆交付或 AI 输出交付预算耗尽时保留原结果、返回资源错误和读取引用，不交付成功前缀，不自动修复重放已完成命令。回归：`output_capacity_complete_console_records_survive_snapshot`、`output_capacity_capture_exhaustion_is_fatal_and_retains_rejected_record`、`output_capacity_host_failure_cannot_be_caught_as_partial_success`、`output_capacity_complete_console_reaches_actual_model_request`、`output_capacity_main_failure_preserves_original_and_allows_rewrite`、`output_capacity_probe_delivers_complete_value_or_explicit_failure`、`output_capacity_module_failure_propagates_without_fixer_or_replay`、`program_delivery_preserves_parseable_json_and_bounds_only_bytes`。真实模型结果另存本轮运行报告，不能从测试通过推定模型一定按提示分工。
