# Agent 设计

更新：2026-11-19。**本文与 [Context-as-Code v2 架构规范](context-as-code-design.md) 共同作为当前设计的唯一依据。** 代码、面向 AI 的提示词、Skill、测试和其他文档与二者冲突时，一律按规范修改。

> **2026-11-19 架构升级说明（Context-as-Code v2，已落地实施）**：
> 主驱动已全面升级为 **Context-as-Code v2**（完整规范见 [docs/context-as-code-design.md](context-as-code-design.md)），以下核心契约优先于下文历史章节中的旧描述：
> - **零 JSON Schema `tools`、零 `write_program` / `handoff_step` 双轨壳**：模型直接续写 `async function executeTask() {` 中的裸 JavaScript（工具声明在静态 `.d.ts` 中由 Rust 代理执行），以 `return <<<` 零转义 Markdown 终结符或纯内存 JS `return` 结束本轮；仅当本步 `external_tool_calls == 0` 才终止循环（含外部调用时的抢跑 `return <<<` 触发 First-Trap Truncation 丢弃）。
> - **每轮全新空 VM + 不可变追加式 `// =>` + 单步 `EPHEMERAL_PEEK`**：短值（`<= 2KB`）进永久 `// =>`（同一步重复别名折叠），中值（`2KB..=24KB`）单步带行号展开并跨别名去重，大值（`> 24KB`）给高熵索引并自动归档 `asset_id` 供跨轮 `session.read_asset` 取回；轮末剥离 `EPHEMERAL_PEEK` 并销毁 VM。
> - **惰性资源句柄（`ResourceHandle`）**：文件读取与大命令输出自带 `Ref#N` 与 `.slice()`（支持多区间）、`.grep()`、`.outline()`、`.head()`、`.tail()`；传给 `@virtual` 时外层零展开、子帧自动解引用。
> - **内外同构隔离 `@virtual` 帧**：子帧使用同一套纯 JS + `.d.ts` + `// =>` + `EPHEMERAL_PEEK` 引擎，剥离 `process`/`session`/`ask_user`、禁止嵌套 `@virtual`，支持 `Promise.all` 真并发与 `delegate_agent_settings` 异构模型路由，返回即 GC 并在父轨迹留 `[virtual ...]` 事实回执。
> - **跨会话复用与优雅交互**：支持 `require("<lib>")` / `require("<lib>/promises")` 加载内置预设与 `.agents/skills/<name>/modules/*.js`，支持 `host.ask_user` 优雅挂起（`NEEDS_USER`）、`host_folder` `turn-NN.js` 归档与 `rewind` 回滚。
> - **现状：跨平台 Capability Security 与原生库。** 文件元数据/受控复制走 `io.stat` / `io.copy`，环境探针走只读 `sys.*`；磁盘、PATH 与进程信息使用原生平台 API，macOS TCP listener enumeration 明确返回 `supported: false`。Linux `bwrap` 进程沙箱与 `run_readonly_command` 已退场；Linux、Windows、macOS 的命令统一采用入口规则与三档审批（执行前询问、自动审批、完全权限），不做 OS 级进程隔离。旧事件仍可回放。历史章节如有冲突，以此处与第 9 节为准。

## 1. 出发点

不考虑上下文容量时，最稳、最有效率的 Agent 就是一个朴素循环：消息按顺序堆叠 → 调用 AI → 执行它的工具调用 → 重复，AI 不再调用工具时结束。

问题只在于上下文容量有限。动态压缩、删减上下文，或者在对话循环里人为模拟阶段状态机和事件切片，都会让实现越来越复杂、问题频出。本设计不靠在 ReAct 对话里叠状态机来“假装”作用域，而是借用编程语言的**函数作用域**本身来划清边界、分割逻辑与释放内存：

- 确定性的多步工作、文件扫描、命令执行和结果过滤用 JavaScript 函数编写，中间数据留在 JS heap，函数返回即销毁；
- 需要 AI 判断、理解或并发处理的局部能力声明为 **`@virtual` 虚函数**：就像 C++ 的 `virtual` 一样只声明能力契约（参数、职责、工具范围与返回值），不同之处在于**宿主在函数作用域内通过朴素 ReAct 循环替它完成实现**，拿到返回值后，这段 AI 上下文随函数结束自然释放。

所以能根据已有知识或当前上下文直接回答的问题，主 AI 直接回答；零散查询和简单编辑直接调用工具；一旦明确有批处理、多步分析、跨文件/多命令验证或需要隔离上下文的工作，主 AI 短暂探明前提后就用 `write_program` 提交一次性 JavaScript 编排程序：把确定性步骤写成 JS 函数，把需要 AI 的边界声明成单层 `@virtual` 虚函数。程序和结果留下意图与事实，函数内的中间噪音天然不进入主窗口。

**只禁大问题，大道至简。** 提示词给的书写方向只是建议，宿主只守真正会破坏隔离或导致上下文失控的底线，不叠多余仪式。

## 2. 流程代码就是 JavaScript

- AI 写的流程是普通 JavaScript：顺序、分支、循环、函数、闭包、`async`/`await`、`Promise`、`try`/`catch` 都按 JS 语义理解，不另造流程语言，也不要求 AI 记一套额外规则。默认宿主库和普通 `@virtual` 能力提供同步外观：调用点拿到返回值后继续下一条语句；宿主内部可以保存当前 VM 帧、等待外部回执，再从原语句恢复。只有显式使用异步库或需要并发时才引入 `async`/`await`。
- 当前执行器是 SWC 解析、Rust 自建的 JS 子集虚拟机（见 [执行语言手册](agent-program.md)）。子集的缺口应向真实 JS 补齐，而不是在提示词里教 AI 绕开。
- 给 AI 的编程指南（`read_program_guide`，内容在 `prompts/flow_capabilities.md`）应当越来越薄：虚拟机每向真实 JS 靠近一步，指南里“和真实 JS 的差别”就少一条，理想状态下只剩宿主相关的部分（工具库、虚函数、模块、错误处理）。
- 宿主机制尽量用 JS 已有的形式表达，不在虚拟机里加违背 JS 语义的特殊规则。例如提问是一个带名字的普通错误，恢复暂停的程序是一个返回 Promise 的库方法，模块像 `require` 一样在第一次调用时加载（第 3.3 节）。

## 3. 虚函数和函数作用域

主程序就是普通 JavaScript，普通 JS 函数在宿主的虚拟机里确定性执行；**虚函数只有一层**：用 `/** @virtual ... */` 声明能力契约后，宿主直接为它开启一个独立隔离的朴素 ReAct 循环（terminal AI leaf）完成该契约，不再要求“第一层先请模块作者生成 JS 文件、再由模块调第二层虚函数”的双层绕路。历史会话里的显式 `@module` 保留兼容，但新流程统一以顶层 JS 编排 + 单层 `@virtual` 为准。

| 所在位置 | 宿主处理 | 完成方式 |
| --- | --- | --- |
| 主编排顶层代码与普通 JS helper | 直接在 JS heap 上确定性执行（可按会话权限调用 `io`/`git`/`process` 等库） | 普通 `return` |
| 编排中的 `@virtual` 虚函数 | 按显式参数 / `@uses` 和非 shell 工具范围开启隔离的朴素 AI 循环 | 返回契约要求的 JSON，随后释放上下文 |

```js
const pages = await Promise.all(list.map(page => designPage(shared, page)));
/** @virtual Design one page from shared material; return {content:string}. */
async function designPage(shared, page) {}
```

`@virtual` 可以是空函数体，也可以先写几行 JS 快速检查 / 提前 `return`、末尾以意图注释收尾：JS 能直接 `return` 的就不请求 AI，走到末尾注释才挂起交给朴素 AI 循环并带上局部绑定。普通函数必须有实际代码，不会自动交给 AI 补全；带契约注释、函数体为空却漏写 `@virtual` 的函数在编译时直接报错。宿主调度器检查 AI 层级：虚函数内不能再 `write_program` 或派生活动虚函数（越层报 `VIRTUAL_LAYER_LIMIT`）。

### 3.1 `@virtual` 虚函数：隔离的朴素 AI 循环

- `@virtual` 只承担清晰、聚焦的 AI 理解、判断、生成或局部编辑职责；数据读取、命令执行、循环与汇总写在调用它的 JS 函数里。
- 它能用的工具默认来自声明代码 `import` 和 `require` 的库方法（**严禁调用任何 `process.*` 工具**），加上固定的 `find_library_methods` 和 `ask_user`（第 5 节）；若编排显式传入 `host.context()` 的收窄工具列表，宿主仍强制剥除 `write_program`、`handoff_step` 与所有 shell 工具。
- 它要看的材料最好由 JS 代码读好后作为参数传进去，不让它自己绕圈去搜；内容太大时由 JS 拆批并发调用。
- **可以只改工作区，不返回内容。** 改代码类虚函数直接改好文件回复 `null` 即可；要返回文本再写入的则不要自己写文件。**一个文件在一步里只有一个写入者**，验收看实际文件与测试，不看转述。
- 说做不到时回复 `{"$task_error":…}`，作为异常抛给 JS 调用方。

### 3.2 作用域和上下文

- 每次 AI 调用都有干净的独立上下文：主窗口是主任务对话；虚函数只有自己的函数签名、契约注释、**显式传入的参数值**、`@uses` 点名的词法变量和库的说明（第 5.1 节）。调用方的工具输出和无关对话默认不带入。
- 虚函数返回后，它的 AI 上下文立即释放；JS 普通函数与变量在 JS heap 上运行并在返回后销毁，不进入主 AI 窗口。
- 主程序可以通过 `host.context()` 显式读取当前消息前缀并收窄构造 `subContext` 传给需要共享前文的 `@virtual` 叶子（仍受非 shell 与禁 `write_program` 边界约束）。
- 需要额外信息时修改函数参数/返回值契约，不在 ReAct 对话里靠外部切片工具逆向翻找历史作用域。

### 3.3 程序产物在聊天文件夹的保存与复盘

- 宿主为每个项目建 `.codex-workspace-mcp/projects/<项目名>-<路径哈希前 8 位>/`，每个聊天一个 `chats/<聊天 id>/`：主程序是 `<名字>.js`，直接调用记录是 `<名字>.calls.js`（旧 `@module` 兼容文件在 `modules/`，项目流程在 `flows/`）。
- 需要执行多条命令、读取多份大文件/日志或对比多个结果时，直接写在主程序 JS 函数里：输出进 JS heap，程序自检或传给 `@virtual` 叶子判断后 `return` 结构化结果；实际交付不下时明确报错并保留读取引用。

## 4. 一轮对话：结局与记录

日志的完整记录保存在运行时，不按字符或条数裁剪；累计日志捕获超过堆预算时以 `OUTPUT_OVER_CAPACITY` 停止，拒收的完整记录也归档。主程序结局和模块探路结果在进入 AI 前按实际剩余上下文检查，放不下就明确失败，不交付成功前缀，原始输出、返回值和错误保存为 asset 并提供读取引用。资源错误由调用方调整编排，不作为普通实现错误自动修复重跑；已完成命令或写入不能盲目重放。只有 AI 下一次请求本身放不下时才是 `ContextOverflow`。显式按范围分页读取仍可使用，不把未请求的其余内容冒充已交付。

用户的消息进入会话；没有程序运行时通常开始新的一轮，运行中插话的处理见第 7.2 节。主 AI 可以直接回答、使用允许的工具，或者用 `write_program` 交出流程代码；不是每轮都必须写程序。交出程序时，宿主把它写进聊天文件夹，从文件读出、编译并执行。程序和调用结果是会话记录，主 AI 根据结果继续工作或向用户答复。

**串联顶层虚函数 + 可选 JS/`@virtual` 函数分割，宽容量、自然消融、不强加仪式。** 最外层会话本身等价于在共享不可变前缀 `mainContext` 之上串联调用的顶层虚函数（`(function(){ /* 朴素循环或 write_program */; mainContext += selfContext.slice(...); })() → continueInspection() → 下一轮 analysisIssue()`）：每个顶层虚函数在自己的局部 `selfContext` 里自由运行朴素 ReAct 循环——既可以直接调用工具完成任务（不设“只能探 1–4 步、必须写程序”的硬门槛），也可以在遇到批处理、多命令构建测试、长日志过滤或并发分片判断时通过 `write_program` 用普通 JS 函数和单层 `@virtual` 提前隔离并释放中间大输出（不在未知路径/目标时盲写大程序）。即便主 AI 全程跑朴素循环或连续运行多段程序，只有在窗口真正逼近物理上限时，宿主才会通过顶层 `handoff_step` 自动收尾当前顶层虚函数、提取精华切片并释放旧 `selfContext`，切入下一个串联顶层虚函数：

- **读取和检索走结构化工具，项目构建、测试、诊断走 `process.exec_command`。** 主程序按会话权限运行命令，输出进入 JS heap；`@virtual` 叶子和插件会话不暴露 `process.*`。
- **写具体调用的一层查接口。** 主 AI 可用 `find_library_methods` 查找在权限范围内的库方法供程序调用，主窗口工具列表本身固定不变（第 11 节第 32 条）；虚函数找到的方法只作用于这一次调用。
- **宽松容量边界，高水位兜底，绝不低门槛打断。** 直接工具投喂保持充裕上限（单次 `clamp(32k, 128k)` tokens、单轮 `clamp(64k, 256k)` tokens），`program_result` / `module_probe_result` 的交付软上限按当前会话上下文预算的 `1/4` 计算（`soft_tokens = (input_budget / 4).max(1)`，`soft_chars = soft_tokens * 3`，同时保留 `required + 4096 <= input_budget` 剩余窗口硬边界；不设 `host.digest` 与宿主自动摘要折叠），超出即归档完整输出为 `program_output_asset` 并返回显式 `MATERIAL_OVER_CAPACITY` / `OUTPUT_OVER_CAPACITY`（附 `result_field_chars` 顶层字段字符分布）引导按需 `read_asset` 或收窄字段。无论直接 ReAct 还是 `write_program` 交付 `program_result`（首行带 `[event_seq: N]`）回到主循环，均仅在真正逼近容量上限时（常规 `current_tokens >= input_budget * 4 / 5` 且 `step_rounds_in_scope >= 3` 且可回收增量 `>= input_budget / 12`，或紧急 `current_tokens >= input_budget * 7 / 8` 且存在可回收增量）才发出一次 `step_wrap_requested`（`virtual_step_wrap_required`），要求选择：(1) 调用 `handoff_step`——遵循 `mainContext += selfContext.slice(...)`，给出 `next_goal` 与坐标 **`slices`**（`[{seq, lines?, grep?, context_lines?, head?, tail?, keys?, label?}]`），由宿主按 `event_seq` 原文截取并追加不可变的 `virtual_step_handoff` 消息（总预算 192 KiB FIFO 淘汰），清空已完成顶层作用域的探索工具输出并将旧 `program_result` 压为一行带 `event_seq` 的轻量 `program_record`；或 (2) 直接纯文本答复。未近 80% 水位前绝不打断；不设每轮 `set_next_step` 或 `workspace_ledger`。
- **交出一段程序。** 主 AI 调用 `write_program({source})` 交出主脚本，这次回复里只调用它；宿主写入文件并编译，编译通过就在这次回复结束后运行，编译不过的诊断是这次调用的结果，AI 改好再交。回复正文里的代码一律是回答，宿主不解析、不运行。
- **代码会话中，`write_program` 在连续主窗口上下文中直接追加执行。** 主程序编译通过并开始执行时，不擦除此前直接 ReAct 阶段的文件读取、推理与工具往来，完整保留 KV 前缀缓存与既得事实（避免多段程序之间失忆或反复重读）；程序内部通过 `io`/`process` 等库产生的中间大输出保留在 JS heap 上，不进入主 AI 窗口。只有高水位 `handoff_step` 触发时，才按锚点规则重整窗口。
- **主窗口与内层 `@virtual` 叶子统一工具交付与 `mainContext += selfContext.slice(...)` 零重写切片语义。** 主窗口及内层 `@virtual` 叶子（`Role::Leaf`）下发的工具结果统一暴露 `event_seq`，材料信封在主窗口统一解包为原值并保留 `event_seq`；`read_asset` 同时接受 `asset_id` 或整数 `seq`；`@virtual` 叶子可以在返回的 JSON 对象中附带 `"$slices": [{seq, ...}]`，宿主在返回值离开叶子前调用同一套 `build_handoff_slices` 按 `event_seq` 解析为 `"slices"`（无效切片触发 `FUNCTION_RESULT_INVALID` 由叶子修正），使叶子的中间工具输出随作用域释放，只把精准证据切片与结论并入父 JS 作用域。

**程序结果与一轮结局要分开。** 每段程序完成或停止时，宿主记录结果及必要的停止位置，主 AI 据此继续或回答；正常完成一段不强制结束整轮。提问、暂停等边界会留下可供用户和后续工作理解的结局。具体记录按实际已完成的副作用说明，不以模型转述替代事实：

| 程序怎么结束 | 结局 |
| --- | --- |
| 正常完成 | 结果和输出交回主 AI；它决定继续工作还是结束这一轮 |
| 虚函数向用户提问 | “程序停在 第 2 行 summarize([…]) → 第 2 行 judge([…])，等你回答：……”（第 7.1 节） |
| 需要用户处理而暂停 | “程序停在 第 5 行 read_file，需要你处理：……需要你做的：……”，这一轮到此结束；程序保留到下一轮，用户处理好后可以恢复（第 7.3 节） |
| 用户插嘴而暂停 | “程序被你的新消息暂停，停在 第 2 行 summarize([…]) → 第 3 行 judge([…])（AI 处理中），这一步还没完成。程序的状态都保留着。”（第 7.2 节） |
| 自愈后仍然出错 | “程序在第 N 行出错停止：……”（第 8 节） |

- **用户看到的是话，不是代码。** 主 AI 用 `write_program` 交程序时，用户看到的只有这次回复的话，界面也不把这次调用显示成带源码的工具卡片；程序作为它自己的记录保存（见下一条）。回复正文里写给用户的代码照原样显示。
- **程序打印的内容交给写它的 AI。** `console.log`／`info`／`warn`／`error`／`debug` 按 Node 的方式输出一行（字符串原样，其他值按 JSON）；运行时保留完整记录，实际捕获预算耗尽时明确失败并归档，不按字符或条数裁尾。主程序结束时，完整日志随程序结果交回主 AI，供它继续工作；出错时输出随错误交回主 AI，模块出错时交给修复者（第 8 节）。结局写明是哪段程序（它的文件名）；若完整内容不适合剩余 AI 上下文，以资源错误给出完整结果的读取引用，由 AI 调整编排。运行时保留的全部输出和返回值随程序记录保存。用户界面的呈现与内部记录分开，不能用程序打印代替对用户的答复。
- **恢复的方法只给 AI。** 两种暂停的结局，用户看到的只说停在哪里、状态保留（需要用户处理时还说要做什么）；怎样用 `previous.resume()` 恢复，只写进交给主 AI 的那份结局。
- **停止路径**从主脚本一直写到停下的那一层：每一层停在哪一行、在调用谁（带参数，用来区分并发的同名调用），最内层若是还在工作的 AI，标「AI 处理中」「AI 正在编写模块」或「AI 正在修复模块」。提问和暂停用同一种写法，新一轮读到的是同一种格式。
- **代码由宿主执行，也作为会话记录保存。** 写程序的 AI 在当前工作上下文里可以看到自己交出的源码与程序结果；执行由宿主负责，虚函数和模块仍只接收各自作用域允许的信息。每轮执行的各段主程序保存在会话的 `program/start` 事件中，含源码和路径。模块的每个版本（写成时和每次修复后）保存在 `agent_modules` 中；主程序和模块同时是聊天文件夹里的文件（第 3.3 节）。会话记录本身在宿主的数据库里。两者都和聊天记录一起随会话回退、删除：回退到某一轮时，那之后写成或改过的模块一起退回。后续对话有会话记忆和历史引用。**回看像剥洋葱，一层一层按需读，不一下全读进来**：先看窗口里的聊天和聊天文件夹的文件清单（下一条）；要知道某轮跑过哪些流程，先用 `read_session_history({programs:true, directory:".", turn})` 浏览聊天的流程文件夹。根目录按轮列出主程序（文件、结局、代码长度、输出行数）、直接调用记录（调用次数）和 `modules` 子目录。子目录按契约列出截至该轮可用的模块版本。目录页只给清单，可用 `next_directory_offset` 翻页。要细看时，用 `program` 打开清单里的相对路径，用 `start_line`、`end_line` 读指定行；模块文件可以用 `version` 选历史版本。打开主程序文件时加 `output:true` 可分页读保存的输出。目录视图从会话记录取历史源码，不受聊天文件夹里当前模块版本的影响。先读代码还是先读输出，看要回答什么：想知道当时得到了什么，先看输出；想知道怎么做的、为什么出错，先看代码。用的仍是读聊天记录的同一个方法，不另设工具。
- **新一轮：聊天原样接上，做过的事看代码（2026-11-13，第 11 节第 43 条）。** 这个 Agent 由编排代码驱动，一轮做了什么，代码已经写清楚了；常规 Agent 那种按事件记录、摘要回答的历史不适合它。整个聊天就是一个代码项目，主 AI 回看前面的轮次，和看项目代码一样。主 AI 每轮仍开新窗口，窗口里放两样东西，取代原来的会话记忆索引（`conversation_memory` 里的 `answer`、`worked_on`、`programs`）：
  - **聊天本身。** 此前每轮用户的原话和主 AI 给用户的答复，原样作为对话消息放进来，不截断、不摘要。用户说“按你说的 2 和 4 做”，主 AI 要知道 2 和 4 是什么，只能靠原话。本轮内的工具往来、中间文字和程序输出不重复带入下一轮（它们在下面的清单与文件中）。对话从第一轮起累加，加上某一轮会超过上限（`CHAT_CHARS`，暂定 4 万字）时，从这一轮重新开始，之前的整轮离开窗口，不折叠成摘要（第 10 节）；它们的文件仍在下面的清单里，可以打开读。不是每轮挤掉最早的一轮：那样对话的开头每轮都变，这一段每轮都不命中缓存；重新开始后，到下一次重新开始之前开头不变。从超限的这一轮开始而不是清零，因为下一句最可能指的就是它。每轮从头算，回退后结果一样。
  - **聊天文件夹，像一个代码项目。** 宿主列出聊天文件夹的文件清单（`chat_files`）：按轮分组，每个文件标出是程序还是直接调用记录、结局如何；模块的契约照旧在 `chat_modules` 里。最近一轮的文件附全文（合计暂定 2.4 万字；单个程序超过 1.2 万字保留首尾，调用记录超过时先留写入、编辑、运行程序和出错的行，再留主 AI 的话，再从后往前留其他调用，省掉的地方各写一行）。这条消息以“【宿主提供的材料，不是用户的话】”开头、“【宿主材料结束】”结尾：Messages 接口不带消息的 name，相邻的用户消息会合并，不写明就和用户的新请求混在一起。更早的由主 AI 按需打开：`read_session_history({programs:true, program:"<文件名>"})`，和读项目文件一样可用 `start_line`、`end_line`。
- **文件名说明它做什么。** 程序文件像项目里的代码文件一样命名，只用英文小写字母、数字和连字符，不用中文：主 AI 交程序时用 `write_program` 的 `name` 起名，比如 `save-permission-per-chat`，宿主加 `.js`，同名时加 `-2`、`-3`；没起名时取用户请求里的英文词，没有就叫 `program`。文件名不带轮次，轮次在清单里。
- **没写程序的工作也记成代码。** 主 AI 直接调用的方法本来就是库方法（第 5 节）。宿主按调用顺序把一轮里的直接调用写成 `<名字>.calls.js`，名字和这一轮第一段程序相同；这一轮没写程序，就按它改过的文件命名（`permissionMode.ts`、`agent_service.rs` 得到 `permission-mode-agent-service`），没改文件按读过的文件，再没有取请求里的英文词，最后是 `chat`：每个调用一行，写成程序里调用它的样子，比如 `io.read_file({path: "src/a.rs", start_line: 100, end_line: 175})`；参数里的大段内容（写入和编辑的正文）换成长度注释；行尾注释写结果的一句话，比如读了多少行、搜到几处、改了几处、命令的退出码，出错时写错误的第一行。主 AI 在调用之间说的话写成注释。这一轮中间交出并运行的程序，在它出现的位置写一行注释，指向那个程序文件和它的结局；程序调用模块时宿主记下的 `create_task` 不算直接调用。这样一轮做了什么，按顺序读这一个文件就知道。这份文件是记录，不是程序：宿主不运行它。它从会话记录生成，每轮开始前和回退后，宿主让聊天文件夹和会话记录一致：补写记录文件，删掉记录里已经没有的文件（回退掉的轮次的程序和记录、没编译通过的程序）。2026-11-13 本仓库的会话库里，150 轮中有 62 轮只有直接调用、没有程序；第 34、38 条之后这样的轮次会更多。不记成代码，按程序回看就有一半是空的。
- 新一轮从不重跑上一轮出错或停下的程序；要继续，由主 AI 写新程序。例外是暂停的程序：同一轮里被插嘴暂停的程序（第 7.2 节），以及因需要用户处理而暂停、保留到下一轮的程序（第 7.3 节），都可以由新程序显式恢复。

### 4.1 把成功的程序存成技能（待实现）

一轮程序跑成功了，这一轮本身就是一份验证过的流程：确定的部分已经是代码，虚函数标出了非 AI 不可的地方，用到的模块也是能直接运行的代码。用户可以把这一轮存成项目技能：一份说明，加上一个动态库（第 5 节），库里是由主程序改写成的入口方法和这一轮的模块，别的聊天用 `require` 现加载。之后同类的请求，主 AI 调用入口就行，不必再从头规划、写整份流程，流程里已经确定的编排也不再请 AI。这取代旧的“提炼技能”：旧做法从任务流里选几个步骤，把每步用的工具、输入输出交给模型，重新写成一份文字说明；信息有损，下次还要 AI 读着文字重新规划。

- **从一轮程序生成，用户改过再存。** 用户在程序正常完成的那一轮上选择存成技能。工作被确认点分在几轮里时（第 7 节），从这件工作的第一轮一直选到完成的那一轮，下面的“这一轮”就指这几轮。宿主取出：
  - 这一轮为完成任务而运行的相关主程序；同一段程序自愈时重写过的，取实际跑通的版本。一轮有多段时，各段都要取，不能只取最后一段而丢掉前面已完成的流程，怎么合起来见下一条；
  - 相关程序调用过的模块，包括模块里调用的模块，取这一轮跑完时的版本；
  - 这一轮的记录：用户的原话、结局、主程序自愈时收到的诊断、修复者对模块的修改。

  一个 AI 读这些材料，把主程序改写成入口方法（下一条），写出说明的草稿；用户看过、改过再保存。模块的代码原样保存，不改写：它们按契约写成，本来就是通用代码（第 3.3 节）。
- **主程序改写成入口方法。** 主脚本不会自动变成可复用的模块（第 3.3 节）。存技能时，取出的各段主程序合起来改写成库的方法，写法和模块一样：签名和注释是契约，函数体是改写后的代码。改写的方向：
  - **这一次的值变成参数。** 原话里的题目、页数、模板、素材这类只属于这一次的值，变成入口的参数；只针对这一次材料写死的处理，改成通用的。
  - **编排写成代码，内容留给虚函数。** 这一轮里靠 AI 临场决定、现在已经知道答案的事，比如下一步做什么、走哪条分支、出错后怎么改、分几段几批来做，写成代码；重复的结构用模板和循环生成，检查和导出也由代码做（第 3.1、3.3 节）。写内容的虚函数照旧只做一件事，不为了少几次调用把几份内容并进一个调用。
  - **确认点照旧。** 业务技能规定要用户确认的地方，改写后照样停下等用户（第 7 节），不因为“一键”省掉；入口只在确认点分开。比如 PPT 技能要求用户在大纲卡片上确认后才写页面，存下的就是两个入口：做到大纲卡片，确认后做到导出。
- **存成什么。** 技能保存在项目的 `.agents/skills/<名字>/`，随项目走，和其他项目技能一样列在每次请求里。目录里有：
  - `SKILL.md`：写短，给写程序的 AI 看：用途（什么时候用）、注意事项（来自这一轮的出错和修复），和几行调用入口的用法示例。方法的契约不用重复，用 `read_tool_contracts` 能查到。
  - `modules/`：入口方法和这一轮的模块文件，文件名按聊天文件夹里的规则，是函数名加契约编号。每个文件是库的一个方法：方法名就是函数名，契约就是签名和注释，同步还是异步由声明决定。
- **下次怎么用。** 写代码的 AI 在程序里写 `const notes = require("<名字>")`，再调用 `notes.summarizeFile(path, requirements)`。宿主运行库里存的代码，不再请 AI 写这些模块；库里的模块调用库里的其他模块时，照常按契约找到它；模块里的虚函数照常由 AI 完成。同类的请求，主 AI 熟悉之后写几行主脚本调用入口就够了。参数要从用户的原话里取，这本来就是 AI 的事，所以宿主不另设绕过主 AI、直接运行技能的办法。
- **先换个输入跑一遍。** 改写可能漏掉只属于第一轮的东西。存下后，用户换一个输入调用入口跑一遍：程序正常完成、结果也对，这个技能才算能用；不对就按下一条，从跑通的那一轮重新存。
- **库是只读的。** 方法出错，和其他库方法一样抛给调用方，库里的代码不交给修复者：调用方是主程序，由主程序自愈处理；是聊天里的模块，交给那个模块的修复者。要更新技能，就从新的一轮再存一次，覆盖原来的。
- **需求不同时**，AI 照常写自己的程序和模块，可以只用库里的一部分方法。
- **插件页面的会话**存成的技能放在哪里，尚未决定（第 12 节）。

### 4.2 记忆（待实现）

记忆让 Agent 在一个项目里越用越贴合，经验不随一次对话结束而丢失。它不能只靠用户纠正：那样会纠正的用户越用越强，不会纠正或纠正错了的用户学不到，甚至学偏。所以记忆按来源分三类，各有各的规则：

- **偏好，听用户的。** 语言、协作方式、写法习惯这类事由用户决定，不分用户强弱。用户纠正或说明时当场记下；以后补充了，就更新这一条，不新建。
- **技术教训，看事实。** 宿主本来就记着由事实证明的“错了 → 改对了”：编译诊断之后改对、主程序自愈后跑通、修复者改出的新版本跑通、测试先失败后通过、虚函数说做不到之后上层拆细做成。宿主把这些经过（错误原文、改了什么、改完的结果）交给模型，由模型提炼成教训，附上证据。用户提出的技术判断，先对照事实，比如测试、规格、实际运行：事实支持才记，并附上证据；不支持就告诉用户哪里对不上，不记。
- **能迁移的经验，进技能。** 换个项目、换个用户也用得上的做法，沉淀成技能（第 4.1、5 节），可以共享和审阅。不会纠正的用户引用技能，就能用上别人验证过的经验。

怎么存、怎么用：

- **一条记一件事。** 写清事实、原因、怎么用（适用范围），以及来源：用户的原话，或者哪次修复、哪次测试证明的。先只做项目级：按项目存在宿主的文件夹里，不进项目仓库；团队共用的规则仍然写进项目笔记（AGENTS.md）。
- **索引加按需读。** 和技能一样，每次请求只列每条记忆的名字和一句话描述，要用时再读全文，不全文注入。
- **模型自己记。** 主 AI 用 `remember` 新建或更新一条，用 `forget` 删掉一条；记之前先看索引，已有的就更新。代码、文档、git 记录里已经有的，以及只对这一次有用的，不记。
- **宿主不替模型判断。** 宿主不按关键词判断“用户在纠正”，也不判断“这回做对了”；它只交出事实，判断由模型做。
- **自动保存，但看得见。** 每次保存记一条事件，对话里显示“已记住：……”，用户可以在记忆面板里修改、删除。
- **记忆不是不可违背的规则。** 照着某条记忆做却和事实冲突时，模型把冲突说出来，修改或删掉这一条。
- **补漏。** 当场判断难免漏记。在会话归档这类自然的时间点，宿主可以发一次回顾请求，把这次会话里的纠正和出错修复交给模型，问还有没有值得记的。这次请求按时间点触发，不按内容触发。

## 5. 工具是库

工具方法以库的形式提供，调用返回工具的原始 JSON。库分两种，就像 JS 的内置模块和第三方包。项目技能里的库随第 4.1 节待实现。

- **静态库：宿主自带的工具。** 比如文件工具 `io`，一直都在。宿主自带的工具按能力分成几个库，见第 5.2 节。源码里用 `import * as io from "io"` 引入，编译时链接；写了不存在的库或方法，编译就报错。像 Node 一样，`<库>/promises` 引入同一组方法的异步版本，每个方法返回 Promise。像 Node 的 `node:` 前缀，`host:io` 这类写法是兼容别名，import 和 require 都接受，加载同一个库。
  - 也可以像 Node 里 `require("fs")` 那样写 `const io = require("io")`：执行到这一行时拿到同一组方法，`require("io/promises")` 拿到异步版本，同一次运行里再 require 拿到同一个对象。这样写的方法在调用处才检查，不在编译时检查。项目技能和宿主自带的库同名时，先找宿主的库。没有 import 的程序里，宿主自带的库按名字就能用；程序自己声明了同名的变量时，比如 `const io = require("io")`，这个名字归程序自己。
- **动态库：第三方带来的工具。** 插件的工具方法（比如 ppt-master 的 `ppt`）和项目技能里的库（第 4.1 节）属于第三方，像 `require()` 一样现加载：
  - 程序执行到 `const ppt = require("ppt")` 这一行，宿主才按库名找到它，链接它的方法，返回模块对象。插件的库名是清单里的 `library`，要已启用；项目技能的库名就是技能名。用法和静态库相同，`require("ppt/promises")` 拿到异步版本。
  - 同一次运行里再 require 同一个库，拿到的是同一个对象；没有执行到的 require 不加载。
  - 一般的库找不到时，在 require 这一行抛错，由代码或写程序的 AI 处理。已激活插件声明的必需库或方法不可用时属于插件不可用，宿主报错中断，不能让 AI 猜测替代能力（第 8 节）。
  - 已启用的动态库不需要在每次 require 前另做激活。进入插件专属会话时，宿主负责激活插件及其声明的工具和说明；其他技能通过 `read_skill` 读取说明。写代码的 AI 用 `read_tool_contracts` 查方法契约，像先看 `.d.ts` 再写 require。
  - 程序挂起后恢复时，宿主重新链接已经加载的库；库已经不在，或者用到的方法已经没有了，就在调用处明确报错，不拿旧的契约去调用。
  - 方法可以由插件的原生代码、远程服务或命令实现，也可以是项目技能里的 JS 模块，在宿主的虚拟机里运行。
- 宿主**不在每次请求里发送完整工具列表**，以减少工具定义带来的上下文开销：写代码的请求只附简要索引，业务工具的完整定义不随请求发送。简要索引列出静态库的方法，以及可以 require 的库的名字和用途。
- 写代码的 AI（主 AI，以及写模块、修复模块的 AI）拿到简要索引和本聊天已有模块的列表，需要时用 `read_tool_contracts` 查方法契约、用 `read_program_guide` 查语言细节。主 AI 另外能直接调用几个读取、编辑和看图的方法；需要补充的程序方法用 `find_library_methods` 查（第 4 节）。写模块的 AI 只能调用这两个工具，以及读技能说明的 `read_skill`（第 5.1 节），其余都要写进代码；修复模块的 AI 另外能用 `edit_file`，只能改它负责的那个模块文件（第 8 节）。
- **虚函数的工具范围 = 声明它的模块代码 import 和 require 的库方法，排除 shell。** 写代码时引入什么，本身就是对这些虚函数需要哪些能力的预期，所以库要按能力拆开（第 5.2 节）。
- 虚函数的循环里固定保留 `find_library_methods` 和 `ask_user`。`find_library_methods` 按关键词查找方法，查找范围包括可以 require 的库，命中的词越多越靠前；找到的方法只加到**这一次循环**的范围里（由这次循环自己的消息推出），随函数返回消失，不写入持久状态；只能搜索，不提供「列出全部」。`ask_user` 见第 7.1 节。
- 查找、import 和 require 都不扩大权限，权限检查发生在实际调用时。

### 5.1 技能说明跟着引用走

技能的说明（SKILL.md）是库的文档。和普通语言里的函数一样，一个函数只带它自己用到的东西：哪段代码引用了这个库，说明就作用在那段代码上，不按调用关系往下传。比如控制整个做 PPT 流程的插件，在主程序里 require，它的说明给主 AI；只有某个函数要按 markdown 规则写东西，就在那个函数那里引用 markdown。

- **先有说明，再引用。** 写代码的 AI（主 AI、写模块的 AI）使用有说明的库前读取相应说明。插件专属会话的插件说明由宿主预先加载，不需要 AI 再调用 `read_skill`；其他技能用 `read_skill` 读。读到的说明只作用于相应 AI 的上下文。
- **说明跟着引用它的代码。** 一段代码 require 了某个库，宿主就把这个库的说明给负责这段代码的 AI：主程序的是主 AI，包括自愈时；模块的是写它和修复它的 AI。
- **虚函数只带它点名的。** 虚函数没有代码，它要按某个技能做事，就在契约里用 `@uses` 点名那个库的变量，像闭包只捕获用到的变量：

  ```js
  const md = require("markdown");

  /**
   * @virtual
   * 把 notes 写成一节 markdown，返回 {text:string}。
   * @uses md 按它的规则写
   */
  function writeSection(notes) {}
  ```

  点名了 `md`，它才带上 markdown 的说明；没点名的虚函数不带任何技能说明。它的工具范围不变（见上文）：工具在列表里只占一个名字，用不用由它自己决定；说明是一整份读进上下文、会被照着做的，所以只按用到带。
- **不按调用关系继承。** 父函数读过、引用过的技能，不自动带进它调用的函数；被调用的模块要用，自己 require。插件页面的会话属于这个插件，相当于主程序引用了它：插件的说明给主 AI，函数要用，同样自己引用。
- **只有说明的技能也用 require 引用。** 比如 commonmark、spec-driven-testing 这类没有方法的技能，`require("commonmark")` 拿到一个没有方法的对象，作用是把说明挂到这段代码上，就像 webpack 里 `import "./style.css"` 这种只为副作用的导入。这样所有技能都只有一种引用方式。

### 5.2 宿主自带的库按能力拆开

一个库只管一类能力，就像 Node 把内置模块分成 `fs`、`child_process`、`http`。import 什么，就是要什么能力：这样虚函数的工具范围（第 5 节）才有意义，每次请求带上的工具定义也只有用到的那几个库。

| 库 | 方法 |
| --- | --- |
| `io` | 文件：`read`、`read_lines`、`list`、`search`、`stat`、`copy`、`write`、`edit`、`replace`，以及工作区信息 `workspace_info` |
| `sys` | 只读跨平台探针：`disk_space`、`which`、`listening_ports`、`processes`；进程结果不包含命令行，部分平台的端口枚举会返回 `supported: false` |
| `process` | 按会话权限运行项目命令和管理进程：`exec_command`、`write_stdin`、`kill_session`、`run_program`、`run_project_script`、`install_dependencies`、`get_project_process`、`stop_project_process` |
| `http` | `probe`、`request`；请求有响应体限长与控制面 URL 检查，外部请求或写方法需审批 |
| `git` | `status`、`diff`、`log`、`blame`、`commit`、`restore` 支持 `repo`；`diff` 支持 `check` |
| `browser` | `open`、`read`、`wait`、`diagnostics`、`click`、`press_key`、`upload`、`screenshot`、`close` |
| `memory` | 工作记忆、架构记忆、符号的业务上下文，各有 `record_*`、`list_*`、`search_*` |
| `vision` | `view_image`、`analyze_images`、`image_analysis_results` |
| `attachments` | `read_attachment` |
| `session` | 主对话自己的材料和记录：`read_session_history`、`read_asset`、`list_context_assets`、`refresh_asset`、`propose_project_note`。只有主脚本能用，虚函数拿不到（第 3.2 节） |

- **不设兜底的库。** 每个宿主工具都属于一个有名字的库，新增工具时同时定下它归哪个库。测试按工具目录逐个检查，有一个没有归属就失败。
- **方法名**去掉和库名重复的前缀，比如 `browser_open` 成为 `browser.open`，`http_probe` 成为 `http.probe`；其余沿用原工具名，`io` 保留现在的短名。
- **按实际请求验收。** `@virtual` 叶子只拿当前允许的非 `process` 方法，声明代码即使导入 `process` 也不会向子帧暴露。主程序与模块代码按会话权限调用 `process.*`，输出进入 JS heap、不自动进入 AI 上下文。

需要项目构建、测试或诊断时，主程序与模块按会话权限调用 `process.exec_command`、`write_stdin`、`kill_session`；文件、检索、Git、数据库和远程操作分别走 `io.*`、`git.*`、`db.*`、`ssh.*`。Windows 用 PowerShell 7、Linux 用 Bash，路径和能力由 system 动态注入；每条 cmd 启动新进程，变量和 cd 不持久化，长进程保留 session，无 PTY。同 task、同 turn 的 shell 共用 `change_interval`，重叠改动合并跟踪到最后退出；别的 task/turn 与宿主编辑、写入、undo 等待全部停止。程序收到真实 stdout/stderr 和退出码，默认合计 8 MiB 输出堆预算；超限以 `SHELL_OUTPUT_OVER_CAPACITY` 明确失败，不交付成功前缀，保留完整 asset 和会话读取引用，后续模块可用 stream 分页处理。模块返回值先进入 JS heap，不能统称 AI 上下文；AI 只看打印、诊断、显式虚函数输入和成果摘要。详见[手册](agent-program.md#shell-stage-1process-库)与[shell 模块示例](../skills/task-program/examples/shell-in-module.js)。定位源代码优先 scoped `rg --files`／`rg -n`，默认遵守 `.gitignore`；不要递归 Get-ChildItem 扫遍 target 等产物。

### 5.3 插件提供能力与业务流程

插件可以只提供库和工具，也可以同时提供 Skill；没有 Skill 的插件无需伪造说明。插件声明了 Skill 或所需资源时，宿主必须加载有效内容，缺失或不可用就报错中断；插件声明了工具时，宿主必须保证其库和方法可用，不把连接失效当成让 AI 自己猜的普通业务失败。

内置插件（随宿主发布，如 `blueprint`、`git`）是 Agent 的外围核心：宿主启动即激活，不能停用，设置里的启用开关对它们无效；可以重载。只有外部插件可以启用或停用（`skill_packages::set_enabled`）。

Agent 的核心提示词始终保留；插件 Skill 是本插件业务如何做事的说明，在插件启用期间随会话生效，不取代 Agent 的核心职责。插件提供的方法仍按现有权限、工具契约和插件自身的确认规则执行。离开或停用插件时才卸载它的能力和说明；内容发生变化时重新加载插件，使宿主和服务端版本一致。

## 6. Promise 取代子 Agent

- 并发用 `async` 函数（虚函数或模块）加 `Promise.all`／`Promise.race` 等表达，可以并发，也可以不等待、先做下一件事。
- 不存在单独的「子 Agent」「任务分支」概念；一次虚函数调用就是一次 AI 工作，一次模块调用是运行一段代码（第一次调用时先由 AI 写出这段代码），结果都是返回值。
- 模型调用的并发数由宿主的队列限制。
- 并发的调用和串行的一样会被插嘴暂停（第 7.2 节）：各自在自己的下一步停下，恢复时各自从最内层接着跑。

## 7. 和用户的交互

程序运行中，用户和程序之间有程序主动提问、用户插话、宿主发现只有用户能解决的障碍，以及业务插件要求用户确认的边界。它们的停法不同：

- **提问是程序自己发起的**，所以是一个带名字的错误，沿调用链往上抛，代码有权处理它，比如认出它以后改用默认值、不去问用户。
- **插嘴来自用户**，是程序外部的决定，所以由宿主从外面暂停程序，程序里的 `catch` 拦不住。
- **需要用户处理的障碍是宿主判定的**，也在程序外部：和插嘴一样从外面暂停，`catch` 拦不住（第 7.3 节）。

### 7.1 向用户提问

- 虚函数需要用户确认或补充信息时调用 `ask_user`，它就在这里结束：问题以名为 `WaitingForUser` 的错误（`code: WAITING_FOR_USER`）向上传。
- 模块不会把它当成代码错误交给修复者；主程序也不会为它自愈。代码若捕获错误，按 `error.name === "WaitingForUser"` 认出它；没有特别处理时应当重新抛出。这是普通 JS 的做法，虚拟机不另设不可捕获的规则。
- 问题经过每一层调用时补上那一层的停止位置，到达主程序后成为这一轮的结局，程序到此结束。提问不会暂停程序，也没有恢复。
- 用户的下一条消息，无论是同意、否决还是别的话，都开始新的一轮，主 AI 据此写新程序。

插件的明确确认边界与普通 `ask_user` 不同：插件可以在执行页面操作前返回 `WAITING_FOR_USER`，宿主不派发该操作，将问题交给用户并结束当前主程序；程序中的 `catch` 不能吞掉这个边界。插件决定何时、为何确认，宿主只执行通用的授权与等待协议，不把某个业务步骤硬编码进 Agent。用户确认后再按当前会话继续，不把“方案已保存”当成“用户已确认”。

### 7.2 程序运行中用户插嘴

- 程序是按用户当时的需求写的，新消息可能让后面的步骤作废，也可能只是追加内容，所以插嘴会**暂停**整个程序：既不塞进正在运行的虚函数，或正在写、修模块的窗口（那会破坏函数只看自己参数的隔离），也不直接结束程序。
- 宿主在每个帧的下一步之前从外面停下它：正在执行的工具调用先做完，每一步都有记录，各帧的状态原样保留。暂停的程序移进自己的帧，和主 AI 并行存在，不算当前任务。
- 主 AI 在同一轮里收到暂停的结局和这条消息，自己决定接下来怎么做：
  - 继续旧程序：新程序 `import * as previous from "previous/promises"`，`previous.resume()` 返回一个 Promise，让旧程序从停下的那一步接着跑，得到它的返回值；可以和新工作并行，也可以 `await` 后再做。这个库只在有程序暂停时出现。
  - 不继续：新程序不调用它，或者只用文字回答。旧程序在这一轮结束时丢弃，已写入的文件保留。
- 恢复中的程序再被插嘴，会和新程序一起再次暂停；下一个程序恢复新程序时，两层一起接着跑。旧程序里的提问经过 `previous.resume()` 原样传上来，仍然是提问。
- 没有程序在运行时，插嘴照旧直接交给主 AI。

### 7.3 需要用户处理时暂停

有些失败再怎么换做法也解决不了：没配置的能力或设置（如联网搜索的凭据）、用户或审查拒绝的操作、权限模式不允许的操作，以及同一个调用以同样的错误连续失败多次。宿主把这类结果标为 `NEEDS_USER`。它不是程序自己要问的问题（第 7.1 节），而是宿主在程序外部发现的障碍，所以按插嘴的方式处理：

- **整个程序在安全点暂停。** 被拦的那一步不交付给程序，代码里的 `catch` 拦不住它；其余各帧在自己的下一步之前停下，状态原样保留，和第 7.2 节相同。虚函数的工具调用被拦时，它所在的函数也一起暂停。
- **这一轮到此结束。** 结局写明停在哪一步、错误是什么、用户需要做什么，不再请 AI 绕过它。主 AI 直接调用工具（不在程序里）遇到障碍时，只能回复一次告诉用户，不能再调用工具。
- **程序保留到下一轮。** 用户处理好以后发消息，新一轮的主 AI 写新程序，`previous.resume()` 让旧程序从被拦的那一步重试：程序代码里的那一步重新执行；虚函数里的那次调用，它的 AI 收到“用户已处理，请再调用一次”。已经完成的步骤不重做。下一轮结束时仍没有恢复的，和插嘴暂停的程序一样丢弃。
- 宿主不为此另设状态：判定只看工具结果，暂停与恢复沿用第 7.2 节的帧机制。

### 7.4 用户停止后接着跑

用户点停止，多半是方向不对，也可能只是想先停一下。所以停止不丢掉程序，也不自动恢复，而是和第 7.3 节一样保留到下一轮，由主 AI 看了下一条消息再决定。

- **停止是立刻中断，不是安全点。** 正在执行的那一步可能做了一半。宿主把主程序连同各层调用的帧原样留下，结局写明停在哪一步、哪些操作没做完；用户看到的那份只说停在哪、能接着跑，怎么恢复只写在主 AI 那份里。
- **下一轮由主 AI 复盘。** 用户要接着做，主 AI 写 `await previous.resume()`：已完成的步骤不重做，程序代码里没做完的操作从头再做一遍；虚函数自己发出、没拿到结果的调用，它的 AI 收到"被中断、结果不确定"，自己决定要不要再做。用户改了需求，或者没做完的操作不能做两遍（例如改了一半的 shell 命令），就不恢复，写新程序；保留的程序在这一轮结束时丢弃。
- **只保留一轮。** 被停止的那一轮不消耗这一轮；正在恢复别的程序时被停止，两层一起保留。
- **换了宿主读不回来就丢弃。** 调教阶段常常停下、改代码、重启后端再继续。保存的状态是旧版本宿主写的，读不回来时在下一轮开始前丢弃，并告诉主 AI"上一段程序无法恢复，写新程序"，不报错。
- 恢复的程序在自己的任务里运行（和并发调用一样），不在调用方的栈上嵌套：恢复中再恢复时，每层都嵌一整个循环，debug 构建下会栈溢出。

## 8. 错误：统一走异常

- **声明了却没人调用的函数是编译错误。** 宿主不替程序调用任何函数，模块实现只调用它的入口；一个函数从没被调用、也没被当作值传出去，就永远不会执行。宿主在 AI 交来的主程序、模块实现和探路程序上检查，指出是哪个函数、该在哪里调用（2026-11-11 连续 18 段程序定义了 `main()` 却没调用，每段都立刻空跑结束，AI 看不出原因，反复重写）。"程序入口是 main()"是语言定为 JS 之前的旧约定，已废弃：JavaScript 本身不会调用任何函数。虚拟机单元测试也不再猜入口：要测一个函数的返回值就按名字调用它（如同宿主调用模块入口），要测程序就运行顶层语句。
- **编译错误**：源码在任何操作前整份编译；失败时什么都不执行，带行列和原因的诊断交回同一个 AI，由它改正后重新提交。正常的诊断和宿主进程崩溃是两回事；进程崩溃时不能声称已返回编译错误。
- **运行时错误**：按 JS 语义沿调用栈 `throw`，由流程代码的 `try`/`catch` 决定重试、换做法或继续上抛。
- **AI 写的代码出错，交回 AI 改。** AI 写的代码不可能次次正确：
  - **模块**：模块调用中没有捕获的错误，交给一个新开的修复者。它只拿到模块文件和这次的问题：错误和停止位置、这次调用的实参、程序打印的输出、已经完成的写入，以及模块 require 的库的说明（第 5.1 节）。模块的代码本身就带着足够的上下文，不需要当初写它的 AI。修复者像通常的编程 Agent 一样只改出问题的地方：用 `edit_file` 按原文精确替换，只能改这个模块文件，改动大时一次替换一整段也可以；每改一次宿主就编译一次，编译不过时，诊断作为这次 `edit_file` 的结果返回，它接着改。它回复改好了，宿主把文件存为新版本，从头重跑这次调用（不重做已列出的写入），之后的调用都用新版本；它也可以回复 `{"$task_error":…}` 放弃，这时错误才抛给调用方。修复进行时，已经在跑的同一模块的调用照旧用旧版本；在同一版本上出错的调用等这一次修复，不重复修。
  - **主程序**：没有捕获的错误，连同这一轮已写入的文件，交回主 AI。它在同一轮里用 `write_program` 交出修正后的完整程序（从头运行，不重做已写入的部分），或用文字告诉用户为什么做不成。前序上下文与直接工具读取继续保留在窗口中，必要时也可以再看、再跑（第 4 节）。不设固定重写次数上限：只要还没做完、且错误不是需要暂停给用户的提问或模型不可用，诊断就继续交回主 AI 决定重写、改用直接工具还是用文字收尾。
  - **出错的程序收回它发出的调用。** 一段程序（主程序，或模块的一次调用）因错误结束时，它还在跑的并发调用在各自下一步之前停下：正在执行的工具调用先做完，之后不再请求模型，帧记为中断，结果不交付。主程序的诊断里列出被停下的调用。重写或重跑的程序从头开始，不接着用它们。这和 Node 里没被处理的错误让进程退出一样：没人再等的工作随之结束（2026-11-06 的运行里，出错后另外 8 个调用又跑了约 50 次请求，和重写的程序抢并发名额，结果没人用）。
  - 普通函数的错误照常直接抛出；提问不是错误，不自愈。
- **虚函数说做不到是正常的。** 它回复 `{"$task_error":…}` 时，错误抛给调用它的代码，和其他错误一样处理：代码可以捕获它、换一种做法；模块里没有捕获的，交给修复者。修复者通常该做的是把活拆细或换一种做法，而不是把“这一块做不到”当成整个任务做不到。
- **单个结果太大不算超限。** 一个工具结果放不进虚函数剩下的上下文时，结果不交付，虚函数收到它有多大、为什么没交付，换一个更窄的调用（更小的路径、行范围或数量）；必须全部才能做时，回 `{"$task_error":…}`。虚函数没有读资产的工具，所以不让它分页去读。
- **上下文超限：不压缩，直接抛错。** 虚函数自己的上下文放不下下一次请求时，它以名为 `ContextOverflow` 的错误结束，异常回到调用它的代码：代码可以把工作拆得更细后重新调用，或者继续上抛；模块里没有处理的，同样交给修复者。错误中带上虚函数已经完成的副作用（例如已写入的文件），避免上层重复写入或覆盖。
- **重复读取只给指针。** AI 自己再读一个文件时，如果同一版本的这几行已经由前面某次读取交付、而且还留在它的上下文里，宿主只回一条说明，指向那次读取，不再交付第二份：读进来的内容会随之后每次请求重发，重复一份就多一份开销。这只在对话末尾追加，不改前面的记录，缓存照常命中。文件变了、那次读取已释放，或带 `force_read`，照常交付全文；程序代码的读取进 JS heap，不受影响。起因：2026-11-11 一次审查约四分之一的读取是重复读。
- **主窗口放不下或单轮直接返回过大时，交给 AI 自己处理，不暴露给用户。** 放不进剩余空间、或直接工具单次/单轮并发交付超过软上限的结果不会整坨灌入对话，原件存为资产，AI 收到 `MATERIAL_OVER_CAPACITY`（大小、触发阈值、剩余空间、资产编号），自行决定按页读取、缩窄范围、转入程序内聚合或释放已加载的材料。
- **输出截断或工具调用参数不完整**：模型以 `length` 结束，或任何工具调用的参数不是完整 JSON 时，该回复中的调用全部不执行；宿主记录原始调用，把不完整参数替换为安全的历史内容，并向 AI 返回截断及未执行的提示，让它在同一轮缩短后重试。纯文字被截断也要提示未完成。参数写完了却不是合法 JSON（例如字符串里有非法转义）不是截断：调用同样全部不执行，宿主说明解析错误和出错处附近的原文，不让 AI 去缩短。输出 `write_program` 等工具参数时，流式事件记录工具名和参数长度，界面可显示进度；它不代表程序已经开始执行。
- **模型服务连不上，不算谁做不到。** 模型请求在拿到完整回复之前没有任何副作用，连接失败、回复完整之前超时、5xx、429 时宿主退避重试几次（429 按 Retry-After）。仍然不行，就以名为 `ModelUnavailable` 的错误结束，只写原因、不带服务地址；它和提问一样升到主程序，不交给修复者，也不触发主程序自愈。
- 模型的上下文窗口按该模型条目声明的值取（`contextWindow`，如 deepseek 1,048,576、qwen 262,144、subapi 的 GPT 1,050,000）；没声明的模型才用保守默认 256k，另有一个只防明显错值的上限（2,000,000）。
- **后端允许按配置发送 `none` 思考等级，Agent 页面保留不可选**：后端将 `minimal` 映射为 `low`，而显式配置的 `none` / `off` 原样放行关闭思考（Anthropic Messages 映射为 `thinking: {type:"disabled"}`）；Agent 会话界面的思考等级选择器继续不提供 `none`。
- **两种接口。** 提供方默认走 Chat Completions；配置成 `api: openai-responses` 时走 Responses，像 Codex 一样：角色提示词是 `instructions`，其余系统消息在原位置成为 developer 消息，消息的名字写在正文开头；`store: false`，要求返回加密推理，每一步把模型之前的推理项放回请求、排在它引出的调用前面，模型接着自己的思路走。Chat Completions 没有地方放加密推理，经 sub2api 这类把 Chat 转成 Responses 的中转时，前面几步的推理就传不回来。两种接口的回复都整理成同一种消息，宿主其余部分不区分。
- **结果未知的外部写操作不自动重放。** 进程中断时被切断的调用不会在重启后接着跑，因为它最后一步可能已经执行却没有记录；这些调用按失败处理。只有插嘴暂停在安全点停下的调用才会接着跑；用户停止时进程还在，宿主知道哪些操作被切断，由主 AI 决定是否接着跑（第 7.4 节）。

## 9. 副作用边界

作用域隔离的是上下文，不是外部世界。并发的虚函数和模块可能写同一个文件，所以宿主为 Agent 的写入保留按文件的基线；遇到外部修改或并发冲突时不覆盖，保留双方内容，把发生了什么交给 AI 决定，这一轮不因此结束（`managed_files`，第 11 节第 37 条）。基线按任务记，看的是谁改的，不是用什么改的：任务自己运行的命令改了它管理的文件，和受管写入一样算它自己的改动，命令结束后基线跟上；命令开始前文件就已经和基线不同，基线不动，下一次写入照样停下；仍在后台运行的进程之后还会写，它的改动不算。命令运行时宿主里的其他写入都要等它，分不清的只有这段时间里宿主之外（用户的编辑器、其他进程）改了同一个文件，这种情况算作任务自己的改动。外部修改只在一轮之内算：每轮开始时，和基线不同的文件把基线改成现在的内容，因为两轮之间是用户在掌控，那时的改动就是新一轮要面对的现状（2026-11-11，任务第 1 轮读过的文件下午被另一个会话改了，第 7 轮重新读过后再改，仍按六小时前的基线判成冲突，整轮失败）。代价是：上一轮停下保留的程序，若在下一轮恢复后整份写一个两轮之间被改过的文件，不再被拦。

**权限边界（现状）。** Linux、Windows、macOS 统一按工具入口规则和三档权限审批执行：执行前询问（`ask`）、自动审批（`auto_review`）、完全权限（`full_access`）。保留旧会话的 `read_only` / `workspace_write` 行为：只读会话不执行命令；`ask`、`auto_review` 和 `workspace_write` 下，工具显式指定的跨项目写入或执行目录仍按目标目录获得人工审批（单次、本会话或本项目）；`full_access` 不要求目录审批。跨项目写入仍有基线与哈希校验，不进当前项目本轮改动记录。

所有命令都以当前系统用户身份运行，不使用 `bwrap`，原 `run_readonly_command` 不再可调用。入口仍剥离父进程内部环境变量、拦截显式敏感凭据和宿主状态引用，网络能力保留控制面 URL 拦截和 HTTP 防护。这些规则不限制命令启动后实际读写的文件或网络访问，也不等同于 OS 沙箱。

同一个任务里的函数共用这份基线，所以函数之间另有一条规则。每次写入，不管是受管写入还是命令的改动，都记一个写入版本和写入者：并行的 async 函数记它自己，主程序和它的同步调用记 `@main`。async 函数开始时记下当时的版本号，被插嘴暂停的程序记暂停那一刻的版本号。async 函数用 `io.write` 整份写一个文件时，如果它开始之后有别的写入者写过这个文件，它手里的内容可能是旧的，宿主就停下，保留当前文件和待写内容。它开始之前的写入不算，所以按顺序调用的函数、后面几轮的函数都不受影响。宿主不记函数读到的是哪个版本，同时运行的函数即使重新读过文件，也照样会被拦；提示词里"一个文件一步只有一个写入者"，就是引导模型避开这种写法。局部修改（`io.edit`、`io.replace`）是在文件当前内容上替换，抹不掉别人的改动，不检查；主程序自己的整份写入也不检查。

这属于副作用边界，与上下文管理无关。

## 10. 已废弃，不得恢复

以下机制与本设计冲突，已经删除，不得再加回来：

- **上下文折叠**：按容量把旧对话折叠成摘要（原 `step_context`）。资产存储及 `read_asset`、`release_assets` 等工具不在此列：它们是 AI 自己处理大材料的手段，保留。
- **任务/步骤/saga 流程**：任务树的步骤节点和结束节点、结束节点持有迭代器、模型可调用的 `create_task`／`branch_task`，任务板（`read_task_board`）与任务定义、计划确认（`main_task_anchor`）。保留下来的是精简后的函数帧。
- **从回复正文解析程序**：把回复里的 ```js 代码块当成要运行的程序。程序只经 `write_program` 交出（第 4 节）。
- **要 AI 额外记住的特殊 API**：`invoke_library`、`define_task_body`、`host.read_scope`／`scope_variables`，以及要求 AI 手动调用的 `execute_program`、`check_program`。（`read_program_guide` 保留，是按需查阅的编程指南，不是流程的一部分。）
- **完整工具列表**：每次请求都附上所有工具定义。
- **兜底的 `host` 库**：没归到其他库的宿主工具全部并进一个库，import 它就拿到全部能力。宿主自带的库按能力拆开（第 5.2 节）。
- **适配层**：把虚拟机执行伪装成旧式工具往来，以便沿用上述机制。
- **用状态驱动流程与对话伪造作用域**：状态标记、完成确认、每步声明计划（`set_next_step`）、`workspace_ledger` 自动账本、以及为了跑 shell 强行绕双层 `@module` 作者/修复者路径的旧约束。

26. `edit_file` 的报错写明文件里实际有什么：旧文本找不到时，附上文件里最接近的几行（带行号）。找法是旧文本各行（忽略缩进，跳过太短的行）在文件里出现的位置推出起始行，取多数；单行旧文本差一点时，取和它共有单词最多的那一行；什么都不像就说"没有一行出现在文件里"。旧文本不唯一时，写明出现了几次、在哪几行。实现在 `file_edit::text_edits`（`closest_lines`、`occurrences`），Agent 和外部 MCP 的 `edit_file` 都走这里。测试：`a_missing_anchor_shows_the_closest_lines_of_the_file`、`an_ambiguous_anchor_says_where_it_occurs`，以及经过 `business_tool` 的 `a_failed_edit_tells_the_agent_what_the_file_has`。起因：2026-11-01 mini-webpack 第 1—18 轮，`edit_file` 147 次失败 50 次（34%）：38 次旧文本找不到（23 次刚读过文件但没抄准，14 次自己改过之后没重读），11 次不唯一；原来的报错只说"没找到"，模型往往要重读整个文件再试。失败从发生到同一文件下次写成功合计 10.6 分钟，约占总时长一成。没有去掉 `edit_file`：按行号的 `replace_range` 27 次里 21 次不带 `expected_old_text`，行号过时会悄悄替换错行；整份重写又贵。

35. `search_text` 按 grep 的习惯工作（2026-11-13）。当天 25 次有结果记录的搜索里 5 次为空，其中 3 次是写了 `a|b|c`、`model_round\(` 却没传 `regex:true`，被当成字面量匹配；模型另有 7 次传了不存在的 `limit`，被悄悄忽略；搜不到之后它就转去 shell 里用 grep。现在：（一）不传 `regex` 时由查询本身决定：含 `|`、反斜杠转义、`^`/`$` 锚点、`.*`、`.+` 或 `(?`，且能编译成正则、又不匹配空串，就按正则匹配，结果的 `hints` 写明这一点，传 `regex:false` 可强制按字面量；`a || b`（会匹配空串）、`arr[0]`（方括号不算标记）照旧按字面量。显式传 `regex` 时照旧。（二）`output_mode`：`content`（默认，匹配行）、`files`（只列匹配的文件，别名 `files_with_matches`）、`count`（每个文件的匹配行数和 `total`），适合先粗后细。（三）`glob`（字符串或数组，别名 `globs`），按 `rg -g` 的写法过滤文件：`*.rs` 匹配任意深度，`src/**/*.ts` 从工作区根算起，`!` 开头排除。（四）`context_lines`（别名 `context`，最多 20）在 content 模式下给每个匹配带上 `before`、`after` 行，长行同样截成片段。（五）`limit`、`head_limit` 是 `max_matches` 的别名；content 模式数匹配行，另两种模式数文件。符号索引只用于 content 模式、不带 glob 和上下文行的字面量搜索。程序代码里的 `io.search` 是同一个方法，契约同步更新。测试：`search_reads_like_grep`。实现在 `src/tools.rs`，模型看到的说明在 `src/mcp.rs`，返回契约在 `src/agent_service.rs`。

49. 回归函数作用域编排 + 单层 `@virtual` 朴素循环 + 零重写高水位兜底（2026-11-16）。(一) 主程序 `write_program` 在有执行权限的会话里可直接调用 `process.run_readonly` 及受权限约束的 `process.*`（输出进入 JS heap，不占主对话），不再要求通过双层 `@module` 绕路；同时封死 `@virtual` 叶子通过 `library_catalog` / `host.context().tools` / `execute_call` 获得 `run_readonly_command` 的沙箱泄漏。(二) 去掉 `set_next_step` 与 `workspace_ledger` 伪作用域仪式：主 AI 短探 1–4 步看清路径后直接交出 JS 编排，由函数作用域和单层 `@virtual` 朴素循环自然释放上下文；`handoff_step` 退回为高水位兜底（仅在 `step_rounds_in_scope >= 3 && current_tokens >= 180k` 或紧急上限 `240k` 时触发），并**保留轻量坐标切片 `slices`**（`{seq, lines?, grep?, context_lines?, head?, tail?, keys?, label?}`，由宿主按 `event_seq` 自动穿透 `read_asset` 信封从原文精准截取，匹配为空直接报 `HANDOFF_SLICE_INVALID` 而不清空窗口），同时把 `step_name`、`situation`、`next_step`、`main_context_patch` 全部降为可选，只要求简短 `next_goal`，避免 AI 花昂贵的输出 token 重写总结。(三) 收紧 Main ReAct 直接投喂软上限（不按 1M 窗口等比放大到上百万字符），避免单轮吞进海量原始输出。(四) 统一主窗口 `event_seq` 下发与材料解包（不再按 `library_catalog` 区分待遇）；统一 `end_familiarization` 与 `reset_messages_for_virtual_step` 的锚点保留，确保置顶 `saved_asset`、`virtual_step_handoff` 与 `context_slices` 在 `write_program` 启停后完整留存；保留 `compact_cut_off_context` 的 16,000 字首尾断点摘录防止长回复截断失忆。
50. 移除 `end_familiarization` 擦除并解耦 `write_program` 与高水位重置（2026-11-17）。`write_program` 启动时直接在连续的主窗口上下文上追加执行，不再擦除前置 ReAct 的文件读取、推理和工具往来：既保持 KV 前缀缓存命中，也避免同一轮运行多个 `write_program` 或失败重试时丢掉前面看过的事实（程序内部库调用的大输出仍隔离在 JS heap 上，不污染 `w.messages`）。相应地，`write_program` 不再承担高水位清窗职责也不再重置 `step_rounds_in_scope` / `step_handoff_required`；当主窗口达到高水位（`>= 180k`）触发 `virtual_step_wrap_required` 后，`write_program` 同样受 `step_handoff_required` 拦截，须先通过 `handoff_step` 携带坐标 `slices` 重置窗口（或直接用纯文本回答）。同时放弃额外的 `host.state()` / `host.patch_state()` JS 状态袋，保持 `require("host")` 只暴露只读快照与工具目录（`context()` / `tools()`）。
51. 统一外层 `handoff_step` 与内层 `@virtual` 叶子为纯 JS 作用域 + 零重写 `slices` 模型（2026-11-17）。(一) 彻底退休 `Window::main_context` KV 状态袋、`step_trail` 与 `main_context_patch`，改为 `Window::handoff_entries: Vec<Value>`（总预算按 FIFO 淘汰最早条目，单条超限报 `HANDOFF_OVER_LIMIT`）与可选 `summary`；每次 `handoff_step` 只在窗口尾部追加一条不可变的 `virtual_step_handoff` 消息，既贴合 `mainContext += selfContext.slice(...)` 的纯词法作用域心智，也让历史步骤消息跨步、跨轮保持字节级不变以命中 KV 前缀缓存。(二) 内层 `@virtual` 叶子（`Role::Leaf`）工具结果同样暴露 `event_seq`，叶子返回 JSON 对象里的 `"$slices"` 在离开叶子前由宿主统一用 `build_handoff_slices` 解析成 `"slices"`（切片无效走 `FUNCTION_RESULT_INVALID` 诊断修正），实现内外统一的零重写证据切片传递。
52. 放宽上下文与交付软上限，对齐串联顶层虚函数模型并修复 `program_result` 水位与清窗闭环（2026-11-17）。(一) 放宽直接工具与 `handoff_step` 预算（单次工具 `32k..128k` tokens、单轮 `64k..256k` tokens，`handoff_entries` 总预算放宽至 192 KiB、切片放宽至 128 KiB / 48 条），`program_result` 软上限设为 `input_budget / 4`（按 `.chars().count()` 计 Unicode 字符数，超限归档 `program_output_asset` 并附 `result_field_chars`），不设 `host.digest` 等暗箱摘要。(二) 去掉写死的 `180k / 240k` 封顶，`maybe_require_step_wrap` 统一放宽至整窗 `80%`（`input_budget * 4 / 5`，`>= 3` 轮且可回收增量 `>= input_budget / 12`）与紧急 `87.5%`（`input_budget * 7 / 8`），`program_result`（附 `[event_seq: N]`）回主循环同样纳入检查并在 `handoff_step` 时压为一行带 `event_seq` 的 `program_record`（支持按 `event_seq` 切片）。(三) 主提示词去掉“1–4 步强制转编排”的紧箍咒，外层朴素循环与 `write_program` 函数分割按需自然选用。
53. 流程图改由对话事件画（2026-11-22）：上下文即代码改造后函数帧表不再写新帧，`agent.flow` 插槽原来只拿会话 id、自己读 `/agent/tasks/{id}/frames` 与 `/frames/{帧 id}`，新的会话于是画不出流程图。现在由 `AgentPage` 把会话的 `events` 和 `task` 一起交给 `FlowView`，图和对话用同一份 `chatItems`：`frontend/src/flowGraph.ts` 把一轮拆成请求、每个 AI 步骤、步骤下面它调用的工具（同一个 AI 连续调用、没有人领属的工具并成一个「工具调用 ×N」节点）、程序调用（它自己的步骤缩进挂在调用下面）、子代理、插话、回复和结局，一列排下来，分支右缩进 34px、最多缩 4 层；`components/FlowNode.tsx` 按 `FLOW_HEIGHT` 画固定高度，`layoutFlow` 用同一组数字排队，所以连线从一张卡片的下边落到下一张的上边。同一路径按步骤顺序连成一条线，不从父节点重新分叉，缩进的第二张卡片不会被穿过。读帧的 `frameLayout.ts`、`FrameNode.tsx` 和 `frame-view-ui.test.mjs` 删掉。测试 `frontend/tests/flow-graph.test.mjs` 六个用例：一轮的结构（工具挂在调用它的步骤下、收尾的步骤改成回复、结局接在最后一个节点后面）、未领属的连续工具并成一个计数节点、程序调用内部缩进、深层链收窄、轮次列表、以及未完成的一轮里运行中的步骤和等待结果的工具。

## 11. 上下文即代码、动态函数栈与每轮清空重建 VM（2026-11-18）

详细规范见 [`docs/context-as-code-design.md`](context-as-code-design.md)。核心运行契约如下：

1. **按用户轮次配对（`ContextDocument`）与每轮强制重建空白 VM**：
   - 每个用户请求构成一对标准 `(user #t, assistant #t)` 消息：活动轮次的 `user #t` 承载用户原话、只追加不回改的已执行代码段列表 `CodeSegment`（`c1..cm`）以及尾部的临时运行态视图 `ExecutionOverlay`；轮次完成发出最终原生 Markdown `assistant #t` 时，宿主剥离尾部 `ExecutionOverlay`、将本轮代码落盘至会话文件夹，并**无条件销毁本轮 `Runtime` 虚拟机**。
   - 下一轮用户请求到来时，宿主通过 `Runtime::new_repl` 创建全新的空白 VM（零跨轮变量/函数作用域污染）。前序轮次的 `[system, user #1, assistant #1, ...]` 保持字节级不可变，100% 命中跨轮 Prefix KV Cache；跨轮回溯只需从上文前轮代码中摘抄最小只读片段重新求值，严禁重放已完成的文件写入或外部副作用命令（大输出与命令回执通过单行 `// [receipt ...]` 锚点配合 `session.read_asset` 按需读取）。
2. **轮内增量段编译、三档存活绑定透视与 TDZ 安全回滚**：
   - 同一用户轮次内，每次 `<run>...</run>` 通过 `Runtime::prepare_segment` 在同一词法模块环境上增量编译执行：完整数据继续保留在当前轮次的 JS `Heap` 中供后续代码段直接切片、过滤和计算（如 `raw.slice(...)`），无需重复读盘或调 `read_asset`；尾随裸表达式结果写入 `$_`。
   - `ExecutionOverlay` 将本步新增/变更绑定（`last_step_bindings`）按三档透视（`<= 16 KB` 完整内联、`16–96 KB` 首尾预览并标注存活于 JS 绑定、`> 96 KB` 元数据与 `sha256` + 2 KB 头部），未变更的前序绑定自动退化为单行紧凑签名（`older_locals`），内置静态命名空间不混入用户局部变量视图。
   - 语法/编译期拒绝（`SOURCE_REJECTED`、`executed: false`）绝不污染已执行代码段列表；运行期中途抛错（`FailedAfterEffect`）仅回滚当前段尚未完成初始化的 TDZ 绑定（若重声明覆盖前段同名变量则精确恢复前段原值），已落地的外部副作用记录在 `last_step_effects` 供下一步修复段衔接。
3. **普通 JS 函数零 Token 闭环与单层 `@virtual` 临时子栈**：
   - 普通 JS 函数与循环在 Rust VM 内一次跑完（0 额外模型调用），中间大文本随函数返回自然出栈。
   - 单层 `@virtual` 异步调用冻结父帧前缀，通过 `Runtime::new_repl_with_scope` 预绑定位置实参与 `@uses` 闭包变量，在消息底部压入临时 `ChildFrameStack`（严禁 `process.*` shell 能力与嵌套 `@virtual`，严禁裸 Markdown 回复 `VIRTUAL_RETURN_REQUIRED`）；子帧通过 `<run>\nreturn <json_value>;\n</run>`（或 `host.ask_user` / `$task_error`）返回时，整个子栈与子帧中间读取内容从上下文尾部彻底移除，主帧前缀缓存毫发无损。
4. **零 JSON Schema 纯文本协议与流式前瞻门控**：
   - `window_request` + `model_stream::code_only_request` 在所有线上模型请求中彻底移除 `tools`、`tool_choice` 与 `parallel_tool_calls`；`io`、`git`、`process`、`host`、`session` 等静态库声明通过 `program_tool_headers` 注入，运行期仍走宿主结构化 `Action` 权限、沙箱与审计管线。
   - 执行步只允许单个 `<run>...</run>` 块（混写正文报 `MIXED_RUN_AND_REPLY`、多块报 `MULTIPLE_RUN_BLOCKS`、长度截断报 `OUTPUT_TRUNCATED`，均为 `executed: false`）；`RunStreamGate` 按 UTF-8 字符边界做流式前瞻门控，`<run>` 代码流转为 `tool_progress` 而不向聊天界面泄漏原始代码，普通 Markdown 回复流正常实时增量推送。
   - 覆盖全部核心不变量的端到端 `run_task` 验收矩阵位于 `src/context_acceptance_tests.rs`。
