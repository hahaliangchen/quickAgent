# Agent 设计

更新：2026-10-31。**本文是当前设计的唯一依据。** 代码、面向 AI 的提示词、Skill、测试和其他文档与本文冲突时，一律按本文修改。标注「待实现」的部分，代码还没有做到；其他文档里的「当前」「已实现」只代表写作当时的状态。

## 1. 出发点

不考虑上下文容量时，最稳、最有效率的 Agent 就是一个朴素循环：消息按顺序堆叠 → 调用 AI → 执行它的工具调用 → 重复，AI 不再调用工具时结束。

问题只在于上下文容量有限。动态压缩、删减上下文会让实现变复杂、问题频出；遇到一种意外就加一种状态，最终成为死板的状态机。本设计不压缩上下文，而是借用编程语言的**函数作用域**来分流和裁剪：

- 函数内部的数据在函数返回后销毁；
- 调用方只知道调用过它、拿到了返回值，不必知道细节。

所以 AI 做事时用 JavaScript 写流程：难以用代码确定的部分声明为**虚函数**，由宿主在运行时交给 AI 完成，虚函数就是上面的朴素循环；一段完整的子流程可以声明为**模块**，由 AI 按契约写成代码（第 3 节）。每次 AI 工作都在自己的函数上下文里进行，上下文随函数返回而释放。这也利用了 AI 极其擅长编程这一点。

写流程之前，主 AI 先用朴素循环熟悉要做的事（第 4 节）。熟悉阶段本身也是一个作用域，返回值就是流程代码：流程开始执行时，熟悉阶段的上下文随之释放，留下的只有写进程序的东西。

**只禁大问题。** 提示词给的书写方向只是建议，宿主只拦真正会出错的做法，不用规则束缚 AI。

## 2. 流程代码就是 JavaScript

- AI 写的流程是普通 JavaScript：顺序、分支、循环、函数、闭包、`async`/`await`、`Promise`、`try`/`catch` 都按 JS 语义理解，不另造流程语言，也不要求 AI 记一套额外规则。
- 当前执行器是 SWC 解析、Rust 自建的 JS 子集虚拟机（见 [执行语言手册](agent-program.md)）。子集的缺口应向真实 JS 补齐，而不是在提示词里教 AI 绕开。
- 给 AI 的编程指南（`read_program_guide`，内容在 `prompts/flow_capabilities.md`）应当越来越薄：虚拟机每向真实 JS 靠近一步，指南里“和真实 JS 的差别”就少一条，理想状态下只剩宿主相关的部分（工具库、虚函数、模块、错误处理）。
- 宿主机制尽量用 JS 已有的形式表达，不在虚拟机里加违背 JS 语义的特殊规则。例如提问是一个带名字的普通错误，恢复暂停的程序是一个返回 Promise 的库方法，模块像 `require` 一样在第一次调用时加载（第 3.3 节）。

## 3. 虚函数和模块

程序里需要 AI 的地方有两种写法，看**声明**，不看写在哪一层代码里：

| 声明 | 是什么 | AI 怎么工作 |
| --- | --- | --- |
| `/** @virtual */` | 虚函数：纯 AI 钩子 | 每次调用由 AI 用工具循环完成，就是第 1 节的朴素循环；不写代码 |
| `/** @module */` | 模块：一段完整的流程 | AI 按契约写成代码文件，之后的调用都运行这份代码 |

宿主已按声明区分这两种写法；面向 AI 的提示词和示例还按旧的说法写，见第 11 节的“现状”。

**运行时只有虚函数调用 AI；其他函数都是完整的代码**：要么是程序里写好的普通函数，要么是 AI 按契约写成的模块。普通函数里不能只写注释等 AI 补全，也不能让宿主替它猜实现。

**用不用模块，由写代码的 AI 自己决定。** 这和写项目一样：简单的任务直接在主脚本里一页写完，复杂的拆成多个模块。宿主不规定程序的结构，提示词只给建议（第 1 节）。

两种声明的函数体都只有注释，即这个函数的契约：职责、参数含义、返回结构、不做什么。和现实编程语言里的虚函数一样，它定义能力的期望，实现留给后面。声明可以像普通 JS 一样嵌套在另一个函数体内；标记只管它自己，不会让外层函数也变成虚函数或模块。同步还是异步由 `async` 决定，和这两种标记无关。

```js
import * as io from "host:io";

const pages = await Promise.all(list.map(item => designPage(shared, item)));

/** @virtual */
async function designPage(shared, page) {
  // 依据 shared 中的实际材料设计本页。
  // 返回 {content:string}；不写文件。
}
```

### 3.1 虚函数：纯 AI 钩子

- 虚函数只做一件事时最稳。提示词建议它功能单一，不承载太多能力；多步的流程，比如“跑测试、看失败、再修改”，写成代码（简单的直接写在主脚本里，复杂的放进模块），不交给一个虚函数。
- 它能用的工具，是声明它的那段代码（主脚本或模块）import 和 require 的库的方法，另外固定有 `find_library_methods` 和 `ask_user`（第 5 节）。
- 它要看的材料，最好由代码读好，作为参数传进去，不让它自己调工具去读：这样它看到的一定是实际内容，也省去来回的请求。内容太大时，代码按条拆开，分别调用。只有事先不知道要看什么时，才让它自己用工具去找。
- **可以只改工作区，不返回内容。** 改代码这类工作，虚函数直接用工具改好文件就完成了，契约不必有返回值。下一步要用改后的内容就去读文件：验收的虚函数自己读，或者由代码读好传进去。这就像类的方法，写方法改了字段，下一个读方法读这个字段。没有返回值的虚函数回复 `null`，调用方拿到 `null`。
- **一个文件，一步里只有一个写入者。** 要么虚函数直接改、不返回内容，要么它只返回内容、自己不写，由代码写入。两种都可以：改代码适合前者，生成页面、文档适合后者（第 3 节开头例子里的“返回 {content:string}；不写文件”）。不要混用：虚函数已经改好了文件，契约又要它返回文件内容，它只能拿修改说明凑数，代码再把说明写回去，源码就被覆盖了（2026-10-31 [Luna/Terra 对照](luna-terra-feature-probe.md) 里的 `luna-program2`）。
- **验收看工作区，不看转述。** 判断改得对不对，要读实际的文件、跑实际的测试；上一个函数说自己做了什么，不算事实。
- **并发的写入者不碰同一个文件**，就像两个方法不能同时改同一个字段：同一组文件的修改按顺序来，或者按文件分开（第 9 节）。
- 它说做不到（回复 `{"$task_error":…}`）是正常的信号，作为错误抛给调用它的代码（第 8 节）。

### 3.2 作用域和上下文

- 每次调用 AI 都有自己的上下文。主脚本是主任务的对话；虚函数只有自己的函数签名、契约注释、**实际传入的参数值**、`@uses` 点名的变量，以及 `@uses` 点名的库的说明（第 5.1 节）；写模块和修复模块的 AI 只有第 3.3 节和第 8 节列出的那些。调用方的对话、变量和读过的技能都不会带进来。
- 函数返回后，它的上下文整体释放；调用方只拿到返回值。
- 虚函数需要的数据有两条路，都按 JS 的语义：
  - **参数**：调用方显式传入，和普通函数一样。
  - **闭包**：约定注释里用 JSDoc 标签 `@uses <变量名> <说明>` 点名外层变量，像 JS 闭包捕获函数体里引用到的自由变量一样，只捕获点名的那几个，不是整个作用域。按**声明处**的词法作用域解析（调用处同名的局部变量遮不住它），名字不在作用域里或和参数重名时编译报错；值在**调用的那一刻**读取，异步调用之后外层再改也不同步过去。被捕获的变量出现在虚函数的上下文里（`closure`）。点名的是 require 得到的库时，虚函数带上的是这个库的说明（第 5.1 节）。
  - 不让 AI 去任意读取调用方的变量（没有 `read_scope` 之类的接口）；要什么，就在参数或 `@uses` 里写明。
- 模块只有参数一条路（第 3.3 节）。模块里声明的虚函数，可以用 `@uses` 点名模块自己的变量。
- `async` 函数在调用时拿到实参；调用方之后的变化不会同步过去。
- 数据跨作用域只走参数和返回值；工作区里的文件是所有函数共享的状态，改了就在那里，不经返回值转手（第 3.1、9 节）。调用方若发现缺信息，应修改函数的契约（参数、返回结构），而不是让宿主保留内部过程。
- 调用方代码负责检查返回值是否满足约定；不满足就不能当作成功。只改工作区、不返回内容的函数，要检查的是工作区本身。

### 3.3 模块：AI 写成的代码

模块是一段完整的流程，本身就知道自己做什么。主脚本负责编排，比如“读原有代码并分析 → 修改 → 审查并修正”就是三个模块，前一个的返回值作为参数交给后一个：

```js
const request = "……用户的原话……";
const analysis = await analyzeCode(request);
const changes = await modifyCode(request, analysis);
const review = await reviewAndFix(request, changes);

/** @module */
async function analyzeCode(request) {
  // 读取与 request 相关的代码，分析现有实现。
  // 返回 {files:[{path, role}], design:string, risks:[string]}。
}
// modifyCode、reviewAndFix 同样只写契约。
```

- **按契约写一次，之后复用。** 第一次调用时，宿主让 AI 按契约写出模块的代码，编译通过后存成文件再运行；之后对同一契约的调用直接加载这份文件运行，像 `require` 一样，不再请求 AI。同一契约的几个调用同时第一次运行时，只由其中一个请 AI 写，其余的等它写完再运行。同一契约指名字、签名和注释原文完全一样，改一个字就是另一个模块。
- **写成通用代码。** 模块会被多次调用，不能针对某一次调用把结果写死。写模块的 AI 看到的是契约、第一次调用的实参（只作为例子）、库方法的简要索引和本聊天已有的模块；要用哪个技能，它自己用 `read_skill` 读，调用方读过的技能不带进来（第 5.1 节）。
- **只靠参数拿输入。** 和真正的 JS 模块一样，模块不捕获调用方的变量，在模块上写 `@uses` 是编译错误。它自己决定引入哪些库（import 静态库，require 动态库，第 5 节），可以声明虚函数，也可以调用别的模块。
- **自己检查结果。** 运行时“不对劲”只有被看见，才会有人回来改：模块的代码应当检查自己的结果，比如断言、跑测试、对照规格，不对就抛出错误，或者把中间结果打印出来（第 4、8 节）。
- **存放在宿主的聊天文件夹里。** 宿主为每个聊天建一个文件夹（例如工作区下的 `.codex-workspace-mcp/chats/<聊天 id>/modules/`），模块文件放在这里，不进用户的项目目录。同一个聊天里后续的调用和后面几轮都能复用，换一个聊天就重新写；要在别的聊天里复用，就把这一轮存成技能，以动态库的形式 require（第 4.1 节，待实现）。宿主在写代码的请求里列出本聊天已有模块的名字和契约；AI 写出同样的声明，就复用现成的。
- 主脚本可以看成最外层的模块，但它是主 AI 每轮写的，不存成可复用的模块。

## 4. 一轮对话：结局与记录

用户的每条消息开始一轮。主 AI 先熟悉要做的事，再回复一段 ```js 主脚本；宿主编译并执行它，这一轮留下的是**结局**，而不是代码。

**先熟悉，再写主脚本。** 没看过项目就写的主脚本，只能把整件事交给一个虚函数，或者猜错路径和文件（2026-10-31 的 [Luna/Terra 对照](luna-terra-feature-probe.md)）。所以一轮从朴素循环开始：

- **熟悉阶段能看、能跑，不能改。** 除了会话自己的工具（技能、契约、编程指南、聊天记录和存下的材料 `read_asset`），主 AI 还能直接调用宿主自带的几个方法：`io` 的 `read`、`read_lines`、`list`、`search`、`workspace_info`，`process` 的 `run_project_script`、`run_program`，以及看用户发来的图片和附件的 `vision.view_image`、`vision.analyze_images`、`vision.image_analysis_results`、`attachments.read_attachment`（库的划分见第 5.2 节）。改代码之前常常要先跑一下才知道现状，比如现有测试是否全部通过、命令现在输出什么；只能看、不能跑，流程就得去猜这些。运行方法照常受会话权限约束：权限不允许执行时，熟悉阶段也没有它们；`Ask` 模式下运行前先问用户。`io` 的 `write`、`edit`、`replace` 不在其中，改文件只在流程里；主 AI 直接调用没给它的方法，宿主回一条 `TOOL_UNAVAILABLE`，说明改动放进程序。插件页面的会话保持原样，只用它自己的工具。
- **缺的方法自己找。** 默认只给上面这几个，免得每次请求都带上用不到的工具定义（第 5 节）。别的方法用 `find_library_methods` 查，和虚函数一样：找到的方法只加入这一次循环，越过界限时随这段上下文一起去掉。查找结果不含写入类的方法，也就是 `io` 的三个写方法，以及标记为 `WorkspaceWrite` 的插件工具。
- **看多少、跑什么，由模型自己决定。** 宿主不设时限，也不负责切换。命令也可能改动文件，比如构建产物；提示词写明“这里运行是为了了解，不在这里改项目”，不另设限制（第 12 节）。
- **回复主脚本，就是熟悉阶段的返回值。** 和虚函数用不带工具调用的回复返回结果一样，不带工具调用、含一段 ```js 的回复就是主脚本，不另设工具。
- **主脚本开始执行时，熟悉阶段的上下文去掉。** 主脚本编译通过、开始执行的那一刻，这一轮里此前的工具往来、中间的文字和没编译通过的版本都离开主 AI 的上下文，只留下用户的消息（包括熟悉期间插进来的话）、对话记忆和开始执行的这份主脚本。原始记录照常保存，需要时用 `read_session_history` 读回。编译不过时什么都没运行，不算越过界限，上下文保留，AI 带着完整信息改。用 `read_skill` 读过的说明照旧留着，和跨轮带上的技能一样；主脚本 require 的库，说明照常附给主 AI（第 5.1 节）。主 AI 自己调用的方法在之后的请求里保留原名，结果按方法的原始返回显示。
- **熟悉得到的事实写进程序。** 越过界限后，事实只剩程序里的那份，比如路径、现成的测试文件、参数在哪里解析，要写成代码、数据，或者用 `@uses` 交给虚函数的变量。程序因此自带依据，按第 4.1 节存成技能时也更完整。
- **之后照常。** 正常完成就以结局结束这一轮；出错时，主 AI 拿到的是程序、错误和输出（第 8 节），需要时可以再看、再跑；下一份主脚本开始执行时，这一段同样去掉。
- **没运行的程序要说出来。** 回复里同时有 js 代码块和工具调用时，工具照常执行，宿主另外告诉主 AI 代码块没有运行、要单独回复程序；有 ```js 标记却认不出完整的代码块（比如紧贴在 `</thinking>` 后面）时，宿主同样说明没有运行，不当作普通回答结束这一轮。两者都是 `PROGRAM_NOT_RUN`。

**结局**是宿主写给这一轮的几行文字，也是这一轮的回答和新一轮对话记忆里的内容，AI 不看代码也能接着干。它总是列出这一轮写入的文件，并说明程序停在哪里：

| 程序怎么结束 | 结局 |
| --- | --- |
| 正常完成 | “程序已完成。”和返回值 |
| 虚函数向用户提问 | “程序停在 第 2 行 summarize([…]) → 第 2 行 judge([…])，等你回答：……”（第 7.1 节） |
| 用户插嘴而暂停 | “程序被你的新消息暂停，停在 第 2 行 summarize([…]) → 第 3 行 judge([…])（AI 处理中），这一步还没完成。”和恢复的方法（第 7.2 节） |
| 自愈后仍然出错 | “程序在第 N 行出错停止：……”（第 8 节） |

- **用户看到的是话，不是代码。** 主 AI 的回复里带程序时，用户看到的只有程序前后的话；程序作为它自己的记录保存（见下一条）。
- **程序打印的内容交给写它的 AI。** `console.log`／`info`／`warn`／`error`／`debug` 按 Node 的方式输出一行（字符串原样，其他值按 JSON），只保留最近的若干行。主程序结束时，最近 20 行写进结局的「输出」——这部分只给 AI：用户看到的结局不带它，AI 的上下文和下一轮记忆里保留；主程序出错时，输出随错误一起交回主 AI；模块出错时，交给修复它的 AI（第 8 节）。这样 AI 可以在代码里自己打印想看的中间结果。
- **停止路径**从主脚本一直写到停下的那一层：每一层停在哪一行、在调用谁（带参数，用来区分并发的同名调用），最内层若是还在工作的 AI，标「AI 处理中」「AI 正在编写模块」或「AI 正在修复模块」。提问和暂停用同一种写法，新一轮读到的是同一种格式。
- **代码是会话记录，不常驻上下文。** 执行时，代码只是宿主在跑的流程，不在任何 AI 的上下文里。每一轮的主程序，以及模块的每个版本（写成时和每次修复后），都作为这个会话的记录保存（`program/start` 事件，含源码和它实现的函数）；模块同时是聊天文件夹里的文件（第 3.3 节）。两者都和聊天记录一起随会话回退、删除：回退到某一轮时，那之后写成或改过的模块一起退回。新一轮默认只看上一轮的结局；需要回顾时，主 AI 用读聊天记录的同一个方法 `read_session_history({programs:true, turn})` 按需读出，不另设工具。
- 新一轮从不重跑上一轮出错或停下的程序；要继续，由主 AI 写新程序。唯一的例外是同一轮里被插嘴暂停的程序，它可以由新程序显式恢复（第 7.2 节）。

### 4.1 把成功的程序存成技能（待实现）

一轮程序跑成功了，它用到的模块就是一组已经验证过、能直接运行的代码。用户可以把这一轮存成项目技能：一份说明，加上由这些模块组成的动态库（第 5 节），别的聊天用 `require` 现加载。这取代旧的“提炼技能”：旧做法从任务流里选几个步骤，把每步用的工具、输入输出交给模型，重新写成一份文字说明；信息有损，下次还要 AI 读着文字重新规划。

- **从一轮程序生成，用户改过再存。** 入口放在程序正常完成的那一轮上。用户选中这一轮，宿主取出：
  - 这一轮最后跑完的那份主程序（主程序自愈时重写过的，取最后一份）；
  - 它调用过的模块，包括模块里调用的模块，取这一轮跑完时的版本；
  - 这一轮的记录：用户的原话、结局、主程序自愈时收到的诊断、修复者对模块的修改。

  一个 AI 读这些材料，写出说明的草稿，用户编辑后保存。AI 只写说明；模块的代码原样保存，不改写。
- **存成什么。** 技能保存在项目的 `.agents/skills/<名字>/`，随项目走，和其他项目技能一样列在每次请求里。目录里有：
  - `SKILL.md`：写短，给写程序的 AI 看：用途（什么时候用）、注意事项（来自这一轮的出错和修复），和一段简短的用法示例（由这一轮的主程序缩写而成）。方法的契约不用重复，用 `read_tool_contracts` 能查到。
  - `modules/`：这一轮的模块文件，文件名和聊天文件夹里的一样，是函数名加契约编号。每个模块是库的一个方法：方法名就是函数名，契约就是模块的签名和注释，同步还是异步由模块的声明决定。
- **下次怎么用。** 写代码的 AI 在程序里写 `const notes = require("<名字>")`，再调用 `notes.summarizeFile(path, requirements)`。宿主运行库里存的代码，不再请 AI 写这些模块；库里的模块调用库里的其他模块时，照常按契约找到它；模块里的虚函数照常由 AI 完成。
- **库是只读的。** 方法出错，和其他库方法一样抛给调用方，库里的代码不交给修复者：调用方是主程序，由主程序自愈处理；是聊天里的模块，交给那个模块的修复者。要更新技能，就从新的一轮再存一次，覆盖原来的。
- **需求不同时**，AI 照常写自己的程序和模块，可以只用库里的一部分方法。

### 4.2 记忆（待实现）

记忆让 Agent 在一个项目里越用越贴合，经验不随一次对话结束而丢失。它不能只靠用户纠正：那样会纠正的用户越用越强，不会纠正或纠正错了的用户学不到，甚至学偏。所以记忆按来源分三类，各有各的规则：

- **偏好，听用户的。** 语言、协作方式、写法习惯这类事由用户决定，不分用户强弱。用户纠正或说明时当场记下；以后补充了，就更新这一条，不新建。
- **技术教训，看事实。** 宿主本来就记着由事实证明的“错了 → 改对了”：编译诊断之后改对、主程序自愈后跑通、修复者改出的新版本跑通、测试先失败后通过、虚函数说做不到之后上层拆细做成。宿主把这些经过（错误原文、改了什么、改完的结果）交给模型，由模型提炼成教训，附上证据。用户提出的技术判断，先对照事实，比如测试、规格、实际运行：事实支持才记，并附上证据；不支持就告诉用户哪里对不上，不记。
- **能迁移的经验，进技能。** 换个项目、换个用户也用得上的做法，沉淀成技能（第 4.1、5 节），可以共享和审阅。不会纠正的用户引用技能，就能用上别人验证过的经验。

怎么存、怎么用：

- **一条记一件事。** 写清事实、原因、怎么用（适用范围），以及来源：用户的原话，或者哪次修复、哪次测试证明的。先只做项目级：按项目存在宿主的文件夹里，不进项目仓库；团队共用的规则仍然写进项目笔记（AGENTS.md）。
- **索引加按需读。** 和技能一样，每次请求只列每条记忆的名字和一句话描述，要用时再读全文，不全文注入。
- **模型自己记。** 主 AI 用 `remember` 新建或更新一条，用 `forget` 删掉一条；记之前先看索引，已有的就更新。代码、文档、git 记录里已经有的，以及只对这一次有用的，不记。
- **宿主不替模型判断。** 宿主不按关键词判断“用户在纠正”，也不判断“这回做对了”；它只交出事实，判断由模型做。
- **自动保存，但看得见。** 每次保存记一条事件，对话里显示“已记住：……”，用户可以在记忆面板里修改、删除。
- **记忆不是不可违背的规则。** 照着某条记忆做却和事实冲突时，模型把冲突说出来，修改或删掉这一条。
- **补漏。** 当场判断难免漏记。在会话归档这类自然的时间点，宿主可以发一次回顾请求，把这次会话里的纠正和出错修复交给模型，问还有没有值得记的。这次请求按时间点触发，不按内容触发。

## 5. 工具是库

工具方法以库的形式提供，调用返回工具的原始 JSON。库分两种，就像 JS 的内置模块和第三方包。项目技能里的库随第 4.1 节待实现。

- **静态库：宿主自带的工具。** 比如文件工具 `io`，一直都在。宿主自带的工具按能力分成几个库，见第 5.2 节。源码里用 `import * as io from "host:io"` 引入，编译时链接；写了不存在的库或方法，编译就报错。像 Node 一样，`host:<库>/promises` 引入同一组方法的异步版本，每个方法返回 Promise。
  - 也可以像 Node 里 `require("fs")` 那样写 `const io = require("io")`：执行到这一行时拿到同一组方法，`require("io/promises")` 拿到异步版本，同一次运行里再 require 拿到同一个对象。这样写的方法在调用处才检查，不在编译时检查。名字是 `host:` 后面那部分；项目技能和宿主自带的库同名时，先找宿主的库。没有 import 的程序里，宿主自带的库按名字就能用；程序自己声明了同名的变量时，比如 `const io = require("io")`，这个名字归程序自己。
- **动态库：第三方带来的工具。** 插件的工具方法（比如 ppt-master 的 `ppt`）和项目技能里的库（第 4.1 节）属于第三方，像 `require()` 一样现加载：
  - 程序执行到 `const ppt = require("ppt")` 这一行，宿主才按库名找到它，链接它的方法，返回模块对象。插件的库名是清单里的 `library`，要已启用；项目技能的库名就是技能名。用法和静态库相同，`require("ppt/promises")` 拿到异步版本。
  - 同一次运行里再 require 同一个库，拿到的是同一个对象；没有执行到的 require 不加载。
  - 找不到库，就在 require 这一行抛错，和其他错误一样可以 catch，没接住就交回写这段代码的 AI（第 8 节）。
  - 不需要事先激活。`read_skill` 只是读技能的说明，像读 README，说明作用在谁身上见第 5.1 节；写代码的 AI 用 `read_tool_contracts` 查库里方法的契约，像先看 `.d.ts` 再写 require。
  - 程序挂起后恢复时，宿主重新链接已经加载的库；库已经不在，或者用到的方法已经没有了，就在调用处明确报错，不拿旧的契约去调用。
  - 方法可以由插件的原生代码、远程服务或命令实现，也可以是项目技能里的 JS 模块，在宿主的虚拟机里运行。
- 宿主**不在每次请求里发送完整工具列表**，以减少工具定义带来的上下文开销：写代码的请求只附简要索引，业务工具的完整定义不随请求发送。简要索引列出静态库的方法，以及可以 require 的库的名字和用途。
- 写代码的 AI（主 AI，以及写模块、修复模块的 AI）拿到简要索引和本聊天已有模块的列表，需要时用 `read_tool_contracts` 查方法契约、用 `read_program_guide` 查语言细节。主 AI 在熟悉阶段另外能直接调用几个读、运行和看图的方法，缺的用 `find_library_methods` 查（第 4 节）。写模块的 AI 只能调用这两个工具，以及读技能说明的 `read_skill`（第 5.1 节），其余都要写进代码；修复模块的 AI 另外能用 `edit_file`，只能改它负责的那个模块文件（第 8 节）。
- **虚函数的工具范围 = 声明它的那段代码（主脚本或模块）import 和 require 的库的方法。** 写代码时引入什么，本身就是对这些虚函数需要哪些能力的预期，所以库要按能力拆开（第 5.2 节）。
- 虚函数的循环里固定保留 `find_library_methods` 和 `ask_user`。`find_library_methods` 按关键词查找方法，查找范围包括可以 require 的库，命中的词越多越靠前；找到的方法只加到**这一次循环**的范围里（由这次循环自己的消息推出），随函数返回消失，不写入持久状态；只能搜索，不提供「列出全部」。`ask_user` 见第 7.1 节。
- 查找、import 和 require 都不扩大权限，权限检查发生在实际调用时。

### 5.1 技能说明跟着引用走

技能的说明（SKILL.md）是库的文档。和普通语言里的函数一样，一个函数只带它自己用到的东西：哪段代码引用了这个库，说明就作用在那段代码上，不按调用关系往下传。比如控制整个做 PPT 流程的插件，在主程序里 require，它的说明给主 AI；只有某个函数要按 markdown 规则写东西，就在那个函数那里引用 markdown。

- **先读说明，再引用。** 写代码的 AI（主 AI、写模块的 AI）要用哪个库，先用 `read_skill` 读它的说明，像先看 README 再写 require。读到的说明只留在这个 AI 自己的上下文里。
- **说明跟着引用它的代码。** 一段代码 require 了某个库，宿主就把这个库的说明给负责这段代码的 AI：主程序的是主 AI，包括自愈时；模块的是写它和修复它的 AI。
- **虚函数只带它点名的。** 虚函数没有代码，它要按某个技能做事，就在契约里用 `@uses` 点名那个库的变量，像闭包只捕获用到的变量：

  ```js
  const md = require("markdown");

  /**
   * @virtual
   * 把 notes 写成一节 markdown，返回 {text:string}。
   * @uses md 按它的规则写
   */
  function writeSection(notes) {}
  ```

  点名了 `md`，它才带上 markdown 的说明；没点名的虚函数不带任何技能说明。它的工具范围不变（见上文）：工具在列表里只占一个名字，用不用由它自己决定；说明是一整份读进上下文、会被照着做的，所以只按用到带。
- **不按调用关系继承。** 父函数读过、引用过的技能，不自动带进它调用的函数；被调用的模块要用，自己 require。插件页面的会话属于这个插件，相当于主程序引用了它：插件的说明给主 AI，函数要用，同样自己引用。
- **只有说明的技能也用 require 引用。** 比如 commonmark、spec-driven-testing 这类没有方法的技能，`require("commonmark")` 拿到一个没有方法的对象，作用是把说明挂到这段代码上，就像 webpack 里 `import "./style.css"` 这种只为副作用的导入。这样所有技能都只有一种引用方式。

### 5.2 宿主自带的库按能力拆开

一个库只管一类能力，就像 Node 把内置模块分成 `fs`、`child_process`、`http`。import 什么，就是要什么能力：这样虚函数的工具范围（第 5 节）才有意义，每次请求带上的工具定义也只有用到的那几个库。

| 库 | 方法 |
| --- | --- |
| `io` | 文件：`read`、`read_lines`、`list`、`search`、`write`、`edit`、`replace`，以及工作区信息 `workspace_info` |
| `process` | 运行程序和项目脚本、安装依赖、查看和停止项目进程：`run_program`、`run_project_script`、`install_dependencies`、`get_project_process`、`stop_project_process` |
| `http` | `probe` |
| `browser` | `open`、`read`、`wait`、`diagnostics`、`click`、`press_key`、`upload`、`screenshot`、`close` |
| `code` | 代码地图：`search_code_map` |
| `code_go`、`code_rust`、`code_ts`、`code_python` | 各语言的符号，列出、搜索、读取：例如 `list_ts_symbols`、`search_ts_symbols`、`read_ts_symbol` |
| `memory` | 工作记忆、架构记忆、符号的业务上下文，各有 `record_*`、`list_*`、`search_*` |
| `vision` | `view_image`、`analyze_images`、`image_analysis_results` |
| `attachments` | `read_attachment` |
| `session` | 主对话自己的材料和记录：`read_session_history`、`read_asset`、`list_context_assets`、`refresh_asset`、`propose_project_note`。只有主脚本能用，虚函数和模块拿不到（第 3.2 节） |

- **不设兜底的库。** 每个宿主工具都属于一个有名字的库，新增工具时同时定下它归哪个库。测试按工具目录逐个检查，有一个没有归属就失败。
- **方法名**去掉和库名重复的前缀，比如 `browser_open` 成为 `browser.open`，`http_probe` 成为 `http.probe`；其余沿用原工具名，`io` 保留现在的短名。
- **按实际请求验收。** 只 import 了 `io` 和 `process` 的代码里声明的虚函数，请求里只能有这两个库的方法，再加固定的 `find_library_methods` 和 `ask_user`。

## 6. Promise 取代子 Agent

- 并发用 `async` 函数（虚函数或模块）加 `Promise.all`／`Promise.race` 等表达，可以并发，也可以不等待、先做下一件事。
- 不存在单独的「子 Agent」「任务分支」概念；一次虚函数调用就是一次 AI 工作，一次模块调用是运行一段代码（第一次调用时先由 AI 写出这段代码），结果都是返回值。
- 模型调用的并发数由宿主的队列限制。
- 并发的调用和串行的一样会被插嘴暂停（第 7.2 节）：各自在自己的下一步停下，恢复时各自从最内层接着跑。

## 7. 和用户的交互

程序运行中，用户和程序之间有两条路：程序问用户，和用户插话给程序。两者停法不同：

- **提问是程序自己发起的**，所以是一个带名字的错误，沿调用链往上抛，代码有权处理它，比如认出它以后改用默认值、不去问用户。
- **插嘴来自用户**，是程序外部的决定，所以由宿主从外面暂停程序，程序里的 `catch` 拦不住。

### 7.1 向用户提问

- 虚函数需要用户确认或补充信息时调用 `ask_user`，它就在这里结束：问题以名为 `WaitingForUser` 的错误（`code: WAITING_FOR_USER`）向上传。
- 模块不会把它当成代码错误交给修复者；主程序也不会为它自愈。代码若捕获错误，按 `error.name === "WaitingForUser"` 认出它；没有特别处理时应当重新抛出。这是普通 JS 的做法，虚拟机不另设不可捕获的规则。
- 问题经过每一层调用时补上那一层的停止位置，到达主程序后成为这一轮的结局，程序到此结束。提问不会暂停程序，也没有恢复。
- 用户的下一条消息，无论是同意、否决还是别的话，都开始新的一轮，主 AI 据此写新程序。

### 7.2 程序运行中用户插嘴

- 程序是按用户当时的需求写的，新消息可能让后面的步骤作废，也可能只是追加内容，所以插嘴会**暂停**整个程序：既不塞进正在运行的虚函数，或正在写、修模块的窗口（那会破坏函数只看自己参数的隔离），也不直接结束程序。
- 宿主在每个帧的下一步之前从外面停下它：正在执行的工具调用先做完，每一步都有记录，各帧的状态原样保留。暂停的程序移进自己的帧，和主 AI 并行存在，不算当前任务。
- 主 AI 在同一轮里收到暂停的结局和这条消息，自己决定接下来怎么做：
  - 继续旧程序：新程序 `import * as previous from "host:previous/promises"`，`previous.resume()` 返回一个 Promise，让旧程序从停下的那一步接着跑，得到它的返回值；可以和新工作并行，也可以 `await` 后再做。这个库只在有程序暂停时出现。
  - 不继续：新程序不调用它，或者只用文字回答。旧程序在这一轮结束时丢弃，已写入的文件保留。
- 恢复中的程序再被插嘴，会和新程序一起再次暂停；下一个程序恢复新程序时，两层一起接着跑。旧程序里的提问经过 `previous.resume()` 原样传上来，仍然是提问。
- 没有程序在运行时，插嘴照旧直接交给主 AI。

## 8. 错误：统一走异常

- **编译错误**：源码在任何操作前整份编译；失败时什么都不执行，带行列和原因的诊断交回同一个 AI，由它改正后重新提交。
- **运行时错误**：按 JS 语义沿调用栈 `throw`，由流程代码的 `try`/`catch` 决定重试、换做法或继续上抛。
- **AI 写的代码出错，交回 AI 改。** AI 写的代码不可能次次正确：
  - **模块**：模块调用中没有捕获的错误，交给一个新开的修复者。它只拿到模块文件和这次的问题：错误和停止位置、这次调用的实参、程序打印的输出、已经完成的写入，以及模块 require 的库的说明（第 5.1 节）。模块的代码本身就带着足够的上下文，不需要当初写它的 AI。修复者像通常的编程 Agent 一样只改出问题的地方：用 `edit_file` 按原文精确替换，只能改这个模块文件，改动大时一次替换一整段也可以；每改一次宿主就编译一次，编译不过时，诊断作为这次 `edit_file` 的结果返回，它接着改。它回复改好了，宿主把文件存为新版本，从头重跑这次调用（不重做已列出的写入），之后的调用都用新版本；它也可以回复 `{"$task_error":…}` 放弃，这时错误才抛给调用方。修复进行时，已经在跑的同一模块的调用照旧用旧版本；在同一版本上出错的调用等这一次修复，不重复修。
  - **主程序**：没有捕获的错误，连同这一轮已写入的文件，交回主 AI。它在同一轮里回复修正后的完整程序（从头运行，不重做已写入的部分），或用文字告诉用户为什么做不成。这时熟悉阶段的上下文已经去掉，需要时它可以再看、再跑（第 4 节）。每轮最多重写 3 次；仍然出错时，错误作为结局结束这一轮，下一条消息从新的一轮开始，不会重跑出错的程序。
  - 普通函数的错误照常直接抛出；提问不是错误，不自愈。
- **虚函数说做不到是正常的。** 它回复 `{"$task_error":…}` 时，错误抛给调用它的代码，和其他错误一样处理：代码可以捕获它、换一种做法；模块里没有捕获的，交给修复者。修复者通常该做的是把活拆细或换一种做法，而不是把“这一块做不到”当成整个任务做不到。
- **上下文超限：不压缩，直接抛错。** 虚函数的下一次请求放不进上下文时，它以名为 `ContextOverflow` 的错误结束，异常回到调用它的代码：代码可以把工作拆得更细后重新调用，或者继续上抛；模块里没有处理的，同样交给修复者。错误中带上虚函数已经完成的副作用（例如已写入的文件），避免上层重复写入或覆盖。
- **主窗口放不下时，交给 AI 自己处理，不暴露给用户。** 放不进剩余空间的结果不交付，原件存为资产，AI 收到 `MATERIAL_OVER_CAPACITY`（大小、剩余空间、资产编号），自行决定按页读取、释放已加载的材料或换一种做法。
- **模型服务连不上，不算谁做不到。** 模型请求在拿到完整回复之前没有任何副作用，连接失败、回复完整之前超时、5xx、429 时宿主退避重试几次（429 按 Retry-After）。仍然不行，就以名为 `ModelUnavailable` 的错误结束，只写原因、不带服务地址；它和提问一样升到主程序，不交给修复者，也不触发主程序自愈。
- 模型的上下文窗口按配置声明，但不超过 256k；配置写得更大也按 256k 计算。
- **思考不关。** 思考等级最低是 low，配置成 none 或 minimal 也按 low 发。
- **两种接口。** 提供方默认走 Chat Completions；配置成 `api: openai-responses` 时走 Responses，像 Codex 一样：角色提示词是 `instructions`，其余系统消息在原位置成为 developer 消息，消息的名字写在正文开头；`store: false`，要求返回加密推理，每一步把模型之前的推理项放回请求、排在它引出的调用前面，模型接着自己的思路走。Chat Completions 没有地方放加密推理，经 sub2api 这类把 Chat 转成 Responses 的中转时，前面几步的推理就传不回来。两种接口的回复都整理成同一种消息，宿主其余部分不区分。
- **结果未知的外部写操作不自动重放。** 进程中断时被切断的调用不会在重启后接着跑，因为它最后一步可能已经执行却没有记录；这些调用按失败处理。只有插嘴暂停在安全点停下的调用才会接着跑。

## 9. 副作用边界

作用域隔离的是上下文，不是外部世界。并发的虚函数和模块可能写同一个文件，所以宿主为 Agent 的写入保留按文件的基线；遇到外部修改或并发冲突时停止并保留双方内容（`managed_files`）。基线按任务记，看的是谁改的，不是用什么改的：任务自己运行的命令改了它管理的文件，和受管写入一样算它自己的改动，命令结束后基线跟上；命令开始前文件就已经和基线不同，基线不动，下一次写入照样停下；仍在后台运行的进程之后还会写，它的改动不算。命令运行时宿主里的其他写入都要等它，分不清的只有这段时间里宿主之外（用户的编辑器、其他进程）改了同一个文件，这种情况算作任务自己的改动。

同一个任务里的函数共用这份基线，所以函数之间另有一条规则。每次写入，不管是受管写入还是命令的改动，都记一个写入版本和写入者：并行的 async 函数记它自己，主程序和它的同步调用记 `@main`。async 函数开始时记下当时的版本号，被插嘴暂停的程序记暂停那一刻的版本号。async 函数用 `io.write` 整份写一个文件时，如果它开始之后有别的写入者写过这个文件，它手里的内容可能是旧的，宿主就停下，保留当前文件和待写内容。它开始之前的写入不算，所以按顺序调用的函数、后面几轮的函数都不受影响。宿主不记函数读到的是哪个版本，同时运行的函数即使重新读过文件，也照样会被拦；提示词里"一个文件一步只有一个写入者"，就是引导模型避开这种写法。局部修改（`io.edit`、`io.replace`）是在文件当前内容上替换，抹不掉别人的改动，不检查；主程序自己的整份写入也不检查。

这属于副作用边界，与上下文管理无关。

## 10. 已废弃，不得恢复

以下机制与本设计冲突，已经删除，不得再加回来：

- **上下文折叠**：按容量把旧对话折叠成摘要（原 `step_context`）。资产存储及 `read_asset`、`release_assets` 等工具不在此列：它们是 AI 自己处理大材料的手段，保留。
- **任务/步骤/saga 流程**：任务树的步骤节点和结束节点、结束节点持有迭代器、模型可调用的 `create_task`／`branch_task`，任务板（`read_task_board`）与任务定义、计划确认（`main_task_anchor`）。保留下来的是精简后的函数帧。
- **要 AI 额外记住的特殊 API**：`invoke_library`、`define_task_body`、`host.read_scope`／`scope_variables`，以及要求 AI 手动调用的 `execute_program`、`check_program`。（`read_program_guide` 保留，是按需查阅的编程指南，不是流程的一部分。）
- **完整工具列表**：每次请求都附上所有工具定义。
- **兜底的 `host` 库**：没归到其他库的宿主工具全部并进一个库，import 它就拿到全部能力。宿主自带的库按能力拆开（第 5.2 节）。
- **适配层**：把虚拟机执行伪装成旧式工具往来，以便沿用上述机制。
- **用状态驱动流程**：状态标记、完成确认、计划工具、证据/阻塞校验、催促提示。

21. 第 8 节的 Responses 通道和思考等级下限：提供方配置 `api: openai-responses` 时，`model_round` 把同一份请求转成 Responses 形式发到 `/responses`（`model_stream::responses_request`），流的解码器同时认得两种接口的事件，Responses 的推理项存在助手消息上（`model_stream::REASONING_ITEMS`），下一次请求放回去，走 Chat Completions 时不发；思考等级 none、minimal 按 low 发。请求记录和传输日志记的是实际发出的形式。测试：`model_stream` 里三个解码与转换的测试，`a_responses_provider_gets_the_same_work_and_its_reasoning_back` 用假的 `/v1/responses` 检查第二次请求带回了加密推理，并排在调用和结果前面。真实模型测试可以用 `REAL_WIRE=responses` 临时改走 Responses，不必改配置。2026-11-01 用户自己的 sub2api 上验证可用（[记录](luna-terra-feature-probe.md)）。起因是用户说明 `gpt-proxy` 是 sub2api，它把 Chat Completions 转成 Codex 的 Responses，推理在这层转换里丢掉。
22. 按第 3.1 节改提示词：虚函数（`virtual_leaf.md`）契约不返回内容时回复 `null`，一件事只用一种做法，改了文件就不再返回文件内容，要返回内容就不自己写；主 AI（`single_agent.md`）和写模块的 AI（`module_author.md`）的提示词写明文件是所有函数共享的状态、一个文件一步只有一个写入者、看实际的文件和测试而不看函数的转述；task-program Skill 加了一段说明和 modify/review 的例子，例子由 `published_flow_examples_compile_with_the_fixed_whitelist` 编译。宿主本来就接受 `null`，测试 `a_virtual_that_changes_files_can_return_nothing` 检查调用方拿到 `null` 并读到虚函数改过的文件。起因：2026-10-31 的 `luna-program2` 里虚函数改完文件又被要求返回内容，拿修改说明凑数，覆盖了源码；2026-11-01 Luna 走 Responses 的 mini-webpack 里，虚函数被要求返回整份文件时说做不到。还没用真实模型验收。
23. 第 9 节的基线认任务自己的命令：`business_tool` 在可能改文件的命令（`run_program`、`run_project_script`、`install_dependencies`）开始前，记下本任务基线里仍和基线一致的文件，命令结束后，其中变了的文件把基线改成现在的内容（`managed_files::untouched`、`Untouched::adopt`）；并行函数跑的命令同时记成这些文件的写入者，和它的受管写入一样。命令开始前就和基线不同的文件、还在后台运行的进程，基线都不动。主 AI 熟悉阶段、主程序、模块和虚函数跑的命令都走这个入口。测试：`a_commands_changes_become_the_tasks_baselines_but_not_another_tasks`、`a_change_made_outside_before_the_command_still_conflicts`、`a_parallel_functions_command_makes_it_the_files_writer`，以及经过 `business_tool` 的 `a_command_the_task_runs_changes_its_files_as_its_own_edit`（用 python 改文件）和 `what_a_background_process_changes_is_not_taken_as_the_tasks_own`（用 npm 启动后台进程，没有 Node 时跳过）。起因：2026-11-01 Luna 走 Responses 的 mini-webpack 第 3 轮，主 AI 用 `node -e` 改了测试文件，下一份程序再用 `io.write` 写它时被当成外部修改停下。命令的改动本来就由 `execute_tracked` 记进每一轮的改动记录（撤销用），只是没有同步到基线，同样的命令写进程序里跑也会停。
24. 第 9 节函数之间的写入检查：原来宿主只记每个文件最后一个并行写入者，这条记录从不清理，函数早就结束了，照样拦后来的函数。现在每次写入都记写入版本和写入者（`agent_file_writer_versions`；主程序记 `@main`，命令的改动也算）。async 函数开始时、程序被插嘴暂停时，记下当时的版本号（帧上的 `file_write_clock`）。整份写入只有在开始之后有别的写入者时才拦，冲突提示列出当前文件和待写内容。不记函数读到的版本：那样每次读都要存一份全文，读文件还得排队，等正在运行的命令跑完。旧表 `agent_parallel_file_owners` 不再使用。测试：`only_another_functions_write_after_this_one_started_conflicts`、`a_functions_own_later_write_does_not_hide_another_writer`；经过 `business_tool` 的 `parallel_functions_and_the_main_program_through_the_file_tools`、`a_parallel_functions_command_counts_as_its_write`；经过整轮插嘴暂停和恢复的 `a_resumed_program_can_rewrite_a_file_it_wrote_before_the_pause`。起因：2026-11-01 用 Luna high 续跑 mini-webpack，第 5 轮三个 async 函数（分别在事件 2375、2515、2741 开始）整份写 `mini-webpack.js` 都被拦下。记录里的写入者是第 3 轮的 `implementChanges`，它在事件 1706 就结束了，中间只有第 4 轮的主程序改过这个文件。
25. 虚函数提示词（`virtual_leaf.md`）：原来只说技能说明可能描述的不只是这个函数的部分、按契约给它的那部分做，现在通过 `@uses` 传进来的用户要求也一样。起因：2026-11-01 Luna high 第 9 轮，主 AI 的第一份程序让 `@virtual async function implement` 返回三个文件的完整内容、自己不写文件，又按提示词用 `@uses` 把用户原话交给它；原话里有"运行完整回归测试"，虚函数不写文件就跑不了测试，回复做不到（同时说一次回复放不下三个完整文件）。主 AI 第二份程序改成让它直接改文件，这次成功了。第 22 条起因里的情形这是第二次出现。这句话只针对前一个原因；主 AI 那边先不改，看后面的运行里第一份程序还会不会选择返回整份文件。
26. `edit_file` 的报错写明文件里实际有什么：旧文本找不到时，附上文件里最接近的几行（带行号）。找法是旧文本各行（忽略缩进，跳过太短的行）在文件里出现的位置推出起始行，取多数；单行旧文本差一点时，取和它共有单词最多的那一行；什么都不像就说"没有一行出现在文件里"。旧文本不唯一时，写明出现了几次、在哪几行。实现在 `file_edit::text_edits`（`closest_lines`、`occurrences`），Agent 和外部 MCP 的 `edit_file` 都走这里。测试：`a_missing_anchor_shows_the_closest_lines_of_the_file`、`an_ambiguous_anchor_says_where_it_occurs`，以及经过 `business_tool` 的 `a_failed_edit_tells_the_agent_what_the_file_has`。起因：2026-11-01 mini-webpack 第 1—18 轮，`edit_file` 147 次失败 50 次（34%）：38 次旧文本找不到（23 次刚读过文件但没抄准，14 次自己改过之后没重读），11 次不唯一；原来的报错只说"没找到"，模型往往要重读整个文件再试。失败从发生到同一文件下次写成功合计 10.6 分钟，约占总时长一成。没有去掉 `edit_file`：按行号的 `replace_range` 27 次里 21 次不带 `expected_old_text`，行号过时会悄悄替换错行；整份重写又贵。
27. 流程图按函数帧重新加入，和 agent 核心解耦（2026-11-01）：流程图自己读 agent 的状态。只读模块 `frame_view` 提供 `GET /agent/tasks/{id}/frames`（每个帧的种类、函数名、契约、调用行、状态、起止时间，运行中的帧附上它最近一步的推理摘要和工具）和 `/frames/{帧 id}`（实参、返回值、这个帧自己的事件，以及调用它的那份程序源码），只读函数帧表和事件，不写任何东西；前端的流程图注册成插槽 `agent.flow`，只拿会话 id，运行中每 1.5 秒读一次。核心里只为旧的请求级流程图服务的东西已删除：每次模型请求写的 `flow/node_add`、`flow/node_state`，窗口的 `previous_node`，以及 `/flow/nodes/{id}/interrupt`（它其实只是取消整个任务）；旧会话里留下的这些事件不再读取。对话里每一步先显示模型的推理摘要（`reasoning_content`，任务结束后流式增量被删，原来刷新就看不到了），程序里的虚函数和模块调用各占一行，写明调用行、状态和正在做什么，它们自己的步骤收在这一行下面；`assistant/delta` 带上帧 id，串行调用的虚函数流式输出时就显示在它的调用下面（并发的调用不流式输出）。

真实模型验收（gpt-6.1-terra，思考等级 low，测试在 `src/single_agent/documented_examples.rs`）：只给一句话的任务，分别做出 5、20、50 页互相链接的 HTML 幻灯片。50 页时第一层自己写出大纲，用 `Promise.all` 同时调用 10 个叶子，84 秒完成。

现状：宿主、提示词和 task-program Skill 都已按第 3 节。保存于这次改动之前的程序，主脚本里的 `@virtual` 仍按旧方式写成代码。宿主、提示词、语言手册和 task-program Skill 都已按第 5 节的动态库和第 5.1 节的技能说明范围。

## 12. 尚未决定

- 新的记忆（第 4.2 节）和现有的工作记忆、架构记忆（MCP 时期的记录工具）是合并还是并存。
- 是否改用 Node/V8 运行真实 JS。
- 验收的虚函数要不要比声明它的代码更窄的工具范围，比如只读。现在同一段代码里声明的虚函数共用一组工具，验收的虚函数也拿得到写工具，弱模型可能边验收边修改。按“只禁大问题”的原则，先在契约里写明“只读，不修改”，用 Luna 的测试看模型实际会不会越界，再决定要不要收窄。
- 熟悉阶段运行的命令要不要收紧。运行方法也可能改动文件，比如构建产物，或者模型直接用命令改代码。先在提示词里写明“这里运行是为了了解，不在这里改项目”，在 Luna 的测试里用每一轮的工作区改动记录（`workspace/changes`）数一数熟悉阶段有没有改过文件，再决定。2026-11-01 的 12 次真实运行里发生过一次：Luna 走 Responses 时，在一次程序出错后重新查看，直接用 `node -e` 改写了测试文件，下一份程序再写这个文件时，宿主按外部修改的保护规则（`ASSET_CONFLICT`）停下了这一轮。其余运行都没有。那次停下是宿主没有把命令的改动记进基线，已改（第 11 节第 23 条）；之后这种改动不会再停下这一轮，只能从 `workspace/changes` 数出来。
