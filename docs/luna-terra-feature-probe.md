# Luna 与 Terra：小功能对照实验

## 方法

2026-10-31，分别从 `terra-run` 复制相同的项目文件和依赖到 `feature-luna` 与 `feature-terra`，两组使用相同用户消息、宿主配置、medium 思考档位及全新会话；只更换 `REAL_MODEL`。任务是实现 `node mini-webpack.js --version`，只输出 package.json 版本及换行，保持原有打包功能，增加并运行测试。真实测试入口为 `real_model_small_feature_probe`。先跑 Luna，发现连续 10 次同一 `list_skills({})` 查询后由实验监控取消，再跑 Terra；监控仅属于测试，不是生产宿主策略。

## 观察

- Luna：68.4 秒，工具调用 `list_skills` 12 次、`read_tool_contracts` 3 次、`read_program_guide` 1 次，零个 `program/start`。最后连续 10 次 `list_skills({})` 触发人工设计的监控取消；状态为 cancelled。之前大任务的首次运行也出现同类行为，17 次 list_skills，零程序。
- Terra：63.6 秒，`list_skills` 1 次，生成并运行 1 个程序，状态 completed。它先生成了一份未通过编译的程序，再根据诊断改正后执行。独立检查版本命令：退出 0、stdout `1.0.0\n`、stderr 空。`node --test` 15/15 通过。
- Luna 实际请求的连续消息中，可见反复出现的 assistant 工具调用及对应 tool 结果 `[]`，调用 ID 相互对应；因此至少在检查过的请求中不是空列表结果没有被送回模型。返回空列表与工作区未安装项目技能一致。
- 宿主允许反复进行无状态查询；此次自动取消器是实验中额外加的，表明原运行没有阻止这种循环，但单凭这些事实不能判断它是模型缺陷、提示词和工具交互设计导致，还是提供方兼容问题。需要进一步控制单个因素复测才能定位。

完整会话数据库分别位于两个实验文件夹各自的 `.codex-workspace-mcp/codex_state.db`。Luna 的 run_task 返回成功不代表任务成功：监控调用了取消，实际任务状态是 cancelled。Rust 测试本身只负责采集，不以产品功能完成作为 pass 条件。

## 下一步

固定同一模型分别测试非空技能目录与空目录；再独立测试在工具结果或提示中明确说明“空列表表示无可用技能、继续编程”。每组多跑几次，并核对完整模型请求。另可设计宿主通用的无进展检测，但应先确认重复只读查询是否真的没有新状态，再采用可恢复的提示或终止，不能静默伪造工具结果或把一次循环直接归因于架构。

## 补充控制实验：启动程序与产物验证

同样的小功能和代码基线，继续使用 Luna medium，每组一个新会话。以下是探索性小样本，用户提示的改变会同时影响多个因素，不能视为严格归因：

| 条件 | 观察 |
| --- | --- |
| 原始提示，第二次 | 15 次 list_skills、11 次契约查询、0 次 program/start；重复查询交错出现，不满足连续 10 次 list_skills 的实验监控条件，随后由实验者手动中断。 |
| 只增加“空列表后继续，不要重复查” | 8 次 list_skills、0 次 program/start；Luna 说不要重复，却又查询，最终普通文本称将继续检查项目；会话 completed，但并未修改项目。 |
| 提供 spec-driven-testing 技能 | 查询并读取真实非空技能后转向多次 read_session_history（手动中断前至少 10 次），0 次 program/start。并非只有空列表会导致准备阶段打转。 |
| 增加明确指令“先输出完整宿主 JS 程序，在 @virtual 中读代码实现”第 1 次 | 生成并执行程序，先产生语法和测试错误，后自行修复；独立检查版本输出正确，15/15 测试通过。 |
| 同一明确指令第 2 次 | 生成并执行程序；虚函数直接修改文件并曾跑通测试，但返回的 edits.content 是修改说明。主程序随后把该说明当成完整文件内容写入 mini-webpack.js，造成源码损坏，并因另一个路径不匹配终止。最终主回复称无法完成重新验证；独立复查版本命令 SyntaxError、测试 0/9。 |

这些记录支持一个工作假设：Luna 在当前主 Agent 的“双阶段”工作方式下，经常停在准备调用，没有转入编写程序；明确说明这个转换可帮助它启动，但不是充分条件。结果也暴露了另一条边界：虚函数同时具有文件写入能力、又被要求返回供上层写入的 `edits`，模型可能把修改摘要作为完整源码，上层只验证了类型便覆写了文件。没有证据证明此问题只发生于 Luna，也不能把 session completed 当作业务成功；该轮主回复实际上说明了未完成验证，但对最终源码损坏的判断不准确。可查看 `luna-program2` 的 program/start（事件 281）、虚函数返回（423）、主程序 write_file（425），以及最终文件。

实验中 `run_task` 结束和 Rust ignored 测试通过仅表示采集函数返回；不代表功能或最终产物验收通过。`luna-program2` 的中间测试通过不能替代最后一次写入后的独立验收。所有实验副本位于 `D:\enterpriseProject\mini-webpack-experiment\luna-*`，各自数据库保留事件。

建议后续针对真实架构分别做两类实验：一是优化主 Agent 对“原生准备工具/程序工具/虚函数工具”的清晰引导，分别对不同模型重复测试；二是把虚函数职责设计成明确的“直接修改并返回验证事实”或“只生成完整文件内容不写入”，并测试调用方对结果的验证。建议先建立可复现验收与回归，再决定宿主是否需要通用重复查询/无进展检测；这些建议不是本次已经实现的修复。

## Luna max 对照（2026-10-31）

在相同项目基线和原始功能请求下，把 `FEATURE_PROBE_EFFORT` 从 medium 改为 max；请求记录确认 `reasoning_effort` 为 `max`。约 103 秒，会话状态 completed，但没有 `program/start`，也没有实现功能；独立运行 `node mini-webpack.js --version` 退出码为 1。调用 list_skills 3 次、read_tool_contracts 3 次、read_program_guide 1 次、read_session_history 2 次。

具体线索：事件 102 中，Luna 的回复把 `<thinking>`、JS 代码块与工具调用混在一条消息，并在随后查询会话历史；事件 140 的最终文本重复了两个看似 JS 的代码围栏，其中首个开头紧贴 `</thinking>`。`program_flow::reply_source` 只将行首（允许前导空白）的围栏视为起始；按其逐行扫描方式，这个回复没有识别出有效程序，最终被当成普通文本结束。就算修正围栏识别，还需处理其两个代码块和不含完整任务的代码，因此不能推断只修解析器就能完成任务。

请求中指定 max 不等于已验证服务端实际以 max 推理。官方 GPT-6 Luna 文档指出，OpenAI Chat Completions 的 function calling 只支持 reasoning_effort=none；本项目使用 Chat Completions，此实验运行的提供商或兼容网关是否遵循同样限制尚未确认，因此这次及之前 medium 的调用结果需要带着接口兼容性疑点解释，不能直接得出官方原生模型的能力结论。应在确认提供商及接口行为后，比较支持的调用方式。

## 熟悉阶段的真实验收（2026-11-01）

宿主已按[设计文档](agent-design-guide.md)第 4 节加上熟悉阶段：主 AI 先能直接读、跑、看图，程序开始执行时去掉这一轮此前的工具往来；回复里有程序却没运行时回 `PROGRAM_NOT_RUN`。每个任务都从全新副本开始：`--version` 用 `terra-run` 的副本（改动前 `--version` 退出码 1，原有测试 14/14），五页幻灯片和 mini-webpack 从空目录开始。Luna（`gpt-6-luna`）全部用 OpenAI 文档里 Chat Completions 支持函数调用的思考等级 none；Terra（`gpt-6.1-terra`）用各测试原来的等级（`--version` 和 mini-webpack 为 medium，幻灯片为 low）。两者都经同一个中转 `gpt-proxy`。运行脚本、日志和每次的数据库在 `D:\enterpriseProject\mini-webpack-experiment\accept-*`。

| 任务 | Terra | Luna（none） |
| --- | --- | --- |
| `--version` | 43 秒完成；独立检查 stdout 为 `"1.0.0\n"`、退出码 0、stderr 空，`node --test` 16/16 | 600 秒超时被取消，没有程序，功能未实现 |
| 五页幻灯片 | 53 秒完成，5 页，页页互链 | 107 秒结束，0 页；最后回答说“当前可用能力里没有可调用的主程序运行通道” |
| mini-webpack 四轮 | 隐藏验收 3/3 → 6/6 → 7/8 → 9/9，约 5 分钟 | 第 1 轮没有程序就回答“尚未写入或验证任何实现”，验收 0；第 2 轮上下文达到 231k 上限，`INPUT_OVER_CAPACITY`，测试在第 2 轮停止 |

**Terra：按设计走通。** 每轮先看再写：列目录、读文件，`--version` 和 mini-webpack 第 4 轮还先跑了现有测试。程序里是真正的代码，不再是转交：`--version` 的主程序 52 行，用 `io.edit` 精确改参数判断、写测试文件、跑测试、失败就 `throw`，没有虚函数；mini-webpack 第 2–4 轮同样直接改代码；只有第 1 轮从空目录写整个打包器时用了一个虚函数，契约里写着熟悉时得到的事实（“当前目录没有项目文件，Node 环境没有预装 acorn 或 Babel”），安装依赖和跑测试写成代码并检查结果。熟悉阶段没有改动任何文件，没有出现 `PROGRAM_NOT_RUN` 或被拒的调用，主 AI 上下文峰值 13k–25k token。mini-webpack 第 3 轮漏掉“无扩展名路径”一项，是因为测试只在有函数调用开始时才发出这条插话，这一轮直接改代码、没有函数调用，插话没有发出；第 4 轮按验收反馈补上。这个触发条件是按旧的“交给虚函数”写法设计的，应改为在程序开始时发出。

**Luna（none）：有事可做了，但一直没有转到写程序。** 不再反复查技能（三个任务里 `list_skills` 共 2 次），而是真的在看、在跑，熟悉阶段也没有改动任何文件；但三个任务里一次程序都没有写，连一个 ```` ```js ```` 标记都没有出现。none 档位下它不输出推理，也不输出文字，只有工具调用，直到最后的回答。`--version` 的 10 分钟里有 127 次请求：`read_file` 21 次（`mini-webpack.js`、`package.json` 反复重读）、`run_program` 17 次（多是 `node -e` 查看文件）、`run_project_script` 5 次、`read_session_history` 27 次、`read_asset` 40 次、`release_assets` 6 次，还对不是附件的资产调了 2 次 `read_attachment`；上下文涨到 141k token。看的东西在增加，却没有收敛到“可以写程序了”。

**两个可能的原因，可以分开验证：**

1. none 档位没有推理，模型没有办法计划“看够了，现在写程序”。之前 medium、max 的运行里，Luna 是写过 js 代码块的（当时被宿主丢掉或没认出来，这两处现在都会如实反馈）。
2. 运行程序的方式是“不带工具调用地回复一段 js”，Luna 不把回复当成可以执行的动作。幻灯片任务里它自己说“没有可调用的主程序运行通道”，并在那之前读了 7 次编程指南、8 次会话历史。

用新宿主让 Luna 改用 medium 重跑同样三个任务，可以把两者分开：写出程序并跑通，说明主要是档位问题；仍然在找运行通道，说明需要把运行程序做成一个工具调用。

### Luna 用 medium 重跑（2026-11-01）

同一个宿主程序、同一套测试、全新副本，只把 Luna 的思考等级从 none 换成 medium：

| 任务 | Luna（none） | Luna（medium） |
| --- | --- | --- |
| `--version` | 600 秒超时，没有程序 | 104 秒完成；独立检查 stdout 为 `"1.0.0\n"`、退出码 0、stderr 空，测试 14 → 15 全部通过 |
| 五页幻灯片 | 0 页 | 45 秒，5 页，页页互链 |
| mini-webpack 四轮 | 第 1 轮 0 分，第 2 轮上下文撑满 | 3/3 → 6/6 → 7/8 → 8/9 |

**结论：主要是档位问题，不是运行方式问题。** 有了推理，Luna 用同样的“回复一段 js”写出并运行了程序，不再说缺运行通道。和改动之前同样用 medium 的运行相比（2026-10-31，`--version` 反复查技能、一次程序都没写），这次的差别来自宿主：熟悉阶段让它有事可做，没运行的程序会被说出来。

- **熟悉阶段收敛了。** `--version` 在写程序前只有 18 次主请求（none 时 127 次）：读了 5 次文件、跑了 1 次现有测试和 3 次 `node`，然后写程序；没有反复读会话历史。三个任务的主 AI 上下文峰值 16k–42k token。熟悉阶段没有改动任何文件，没有被拒的调用。
- **程序里是真正的代码。** `--version` 的主程序 40 行，直接改代码、写测试、跑测试，没有虚函数；mini-webpack 第 1 轮的主程序 215 行，把整个打包器直接写进去；第 2、4 轮各用了一个虚函数做修改。
- **`PROGRAM_NOT_RUN` 在真实运行里起了作用。** 第 3 轮 Luna 又把代码块紧贴在 `</thinking>` 后面（正是 max 那次丢掉程序的写法），第 4 轮在一段说明文字中间带了 js 标记；宿主两次都如实说明没有运行，Luna 两次都改正后运行了程序。
- **CSS 用例没过，是代码质量问题。** Luna 的打包器用模式匹配识别 import，没有用解析器（Terra 用了 acorn），遇到隐藏用例里的 CSS 引入就报“无法识别的 import 语法”。第 4 轮 Luna 自己指出了原因（只认带 `from` 的 import），但修改没有覆盖这个用例。

**对运行方式的影响：** 现在的“回复一段 js 就是主脚本”对 Luna（medium）和 Terra 都能用，不必改成工具调用。none 档位下 Luna 不写程序，是缺推理还是缺工具通道，没有单独验证；按 OpenAI 文档，none 是 Chat Completions 上唯一支持函数调用的档位，但这个中转上 medium 可用。经这个中转用 Luna 时，用 medium。

**更正：** `gpt-proxy` 是用户自己部署的 sub2api，背后是 ChatGPT 订阅。sub2api 把 `/v1/chat/completions` 转成 Codex 后端的 Responses 请求（[sub2api #1696](https://github.com/Wei-Shaw/sub2api/issues/1696)），所以上文引用的 OpenAI 开放平台对 Chat Completions 的限制并不直接适用。代价在这层转换：Chat Completions 没有地方放加密的推理项，前面几步的推理传不回下一步。另外按用户的说明，思考等级不会是 none，最低是 low；宿主现在把配置成 none 的也按 low 发，上面 none 的结果只作为记录。

### 改走 Responses（2026-11-01）

宿主加了 Responses 通道（[设计文档](agent-design-guide.md)第 8 节）：请求像 Codex 一样发到 sub2api 的 `/v1/responses`，`store: false`，要求返回加密推理，每一步把模型之前的推理项放回请求、排在它引出的调用前面。同一个宿主、同一套测试、全新副本，Luna 用 medium，只换通道：

| | Chat Completions | Responses |
| --- | --- | --- |
| `--version` | 通过；写程序前 17 次调用，上下文峰值 23k | 通过（`"1.0.0\n"`、退出码 0、15/15）；9 次调用，峰值 18k |
| 五页幻灯片 | 通过 | 通过 |
| mini-webpack | 3/3 → 6/6 → 7/8 → 8/9 | 3/3 → 5/6 → 5/8，第 3 轮被 `ASSET_CONFLICT` 停下 |
| 正文里的 `<thinking>` | 有，第 3 轮还因此出现过一次 `PROGRAM_NOT_RUN` | 0 |

- **通道本身是通的。** 所有请求都去了 `/responses`；推理项确实传了回去，mini-webpack 64 次请求里有 41 次带着之前的推理项，共 95 个。正文里不再混进 `<thinking>`，说明那是 Chat 转换层带进来的。
- **熟悉阶段收得更快。** `--version` 写程序前的调用从 17 次降到 9 次。
- **mini-webpack 这一次反而更差，原因在程序的写法，不在通道。** 运行错误里多是按原文精确替换没找到对应文本（例如 “Could not find the doubled newline escapes”），以及让虚函数返回整份文件、它说做不到（“I can’t return the required complete updated bundler and test sources within this response”）——这正是设计文档 3.1 节“一个文件一步只有一个写入者、改代码就让虚函数直接改”针对的写法，对应的提示词还没改。第 3 轮的停止，是 Luna 在一次出错之后重新查看时，直接用 `node -e` 改写了 `test-mini-webpack.js`，接着下一份程序再写这个文件，宿主发现文件在它管理的写入之外变了，按保护规则停下这一轮。这是第 12 节记下的“熟悉阶段的命令可能改动文件”第一次真的发生；按修正后的统计（把每次文件变化归到它之前的那次调用），12 次运行里只有这一次。
- **只有一次运行，分不清通道的影响和每次运行本身的波动。** 要下结论，需要每种通道各跑几次。
