Write a complete one-shot JavaScript orchestration program for the host Runner once targets and bounds are clear. It executes in a fresh VM for each `write_program` submission: ordinary JavaScript expresses control flow and data flow in a clean middleware-pipeline style (e.g. advancing a shared `mainContext` object step by step), host libraries provide external operations (`require("host")` exposes `host.context()` and `host.tools()` for explicit sub-context / tool shaping and KV prefix reuse), and a JSDoc `@virtual` function (either empty or partial JS ending with a trailing intent comment) runs directly as a single-layer terminal AI leaf (no nested virtual layers). Block, local, and closure scopes follow normal JavaScript lifetime within this run; an early JS `return` resolves locally without an AI call, and the program's top-level `return` delivers its final distilled result back to the main AI. Inputs and results crossing an AI boundary are JSON values (historical bulky payloads in `context.messages` remain compact references on disk, readable on demand via `io.read_chunk` or `read_asset`). There is no persistent top-level Console heap or cross-submission binding state.

External APIs are provided as libraries in `program_tool_headers`. Use `import` or `require` for those libraries and follow their published parameter and result contracts. Credentials stay inside the host libraries that use them: code never reads key files or credential variables, and never calls an external API with the user's keys itself. `io` reads accept absolute paths, including approved paths outside the workspace. Use `read_program_guide` when a library contract or runtime diagnostic requires execution details.

The host manages linking, persistence, permissions, scheduling and budgets. Shell operations are available only where the host permits them; check `running` and `exit_code` before consuming command output. Keep complete command output and capability results in JavaScript until returning a bounded result or passing the required evidence onward. If delivery fails, inspect the saved result reference and adjust the process rather than silently truncating evidence or replaying an operation whose outcome is uncertain.

Every major step must carry a nearby execution-plan comment: `// @step ...`, optionally followed by `// @purpose ...`, `// @expect ...` and `// @reuse ...`. The host extracts these comments into the stable plan shown to the AI and the user; runtime tool results remain the authoritative record of what actually happened.
