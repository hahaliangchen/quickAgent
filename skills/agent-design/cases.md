# 真实失败的经过

每个案例写经过和结论。它们是原则背后的证据：想放宽某条原则时，先看它当初是怎么来的。

## 嵌套任务循环：模型逐字执行了宿主自己的文字

**经过**：一次真实任务里，模型连续嵌套了 3 层临时任务，停不下来。查记录发现，模型做的都是宿主文字让它做的：
- 临时任务帧回放了用户的请求，看起来像一个新对话开头，旁边还有“调用任何工具之前先 create_task”的规则，于是它又建了一层；
- “必须提供理由”的报错，教它去补理由，结果又多一层；
- 读历史时，返回的是宿主的遥测数据。

最后让它停下来的，是层数上限报错里那句“先把这一层做完”，这是它收到的第一句平白的指令。

**结论**：
- 模型照最近、最直接的那句文字去做；
- 宿主给它看的，应当是一句平白的现状加下一步；
- 不要展示看起来像对话开头的回放；
- 内部数据不要进模型能读到的文字。

## 名义上实现了：处理函数写了，模型却从来看不到

**经过**：
- 任务树设计里的 `branch_task` 有处理函数，但从没出现在发给模型的工具列表里；
- 一个 `kind == "task"` 的分支永远匹配不到；
- 用假模型直接调用这个“没公布的工具”的测试照样通过，文档也写着已实现；
- 直到人工审查才发现。用户的评价是“糊弄”。

**结论**：
- 实现一个设计，要断言真实发出的请求：工具列表、注入的消息，以及数据库状态；
- 检查每条新代码路径能从真实主循环走到；
- 文档要和代码实际做到的保持一致。

## 按容量折叠：同两份材料来回读

**经过**：一次真实复测里，父作用域固定传下来的输入很重，已经接近 40% 的折叠阈值。模型读完第二份修复材料，宿主就折叠掉第一份，工作上下文只剩最新的文件；模型又去读第一份，第二份又被折叠。来回反复，大约 178 秒后被测试程序取消，交付没有通过。

**结论**：折叠不解决容量问题，只是把问题变成反复读取。后来改为函数作用域，用完即释放，放不下的结果交给模型自己决定怎么读。

## 图片编号映射：越补越重的状态

**经过**：为了让纯文本模型处理图片，先用视觉模型分析图片，并生成图片编号，把“编号 → 原图”存起来，供以后再看。随后问题一个接一个：
- 重启后映射丢了，历史里的旧编号却还在，模型照着它去调用，失败的报错又污染后面的请求；
- 存进数据库后，又要考虑什么时候删、原图有多大、隐私风险。

**结论**：
- 图片属于当前请求的上下文，不是宿主的长期状态；
- 分析结果作为文本留在历史里，不再保存映射；
- 找不到原图，就请用户重新上传；
- 先问这个状态是不是必须由宿主维护，而不是缺什么状态就补什么。

## console.log 被拒绝：普通代码第一步就失败

**经过**：模型写程序时习惯写 `console.log`，虚拟机却把 `console` 当作未知变量拒绝，真实运行里的第一份程序常常编译失败。支持之后，`console` 的各个方法都像 Node 那样输出一行。打印的内容会交给写这段代码的 AI：主程序结束时写进结局，出错时随错误交回；模块出错时，交给修复者。

**结论**：
- 支持模型自然会写的东西，而不是在提示词里教它绕开；
- 把程序打印的内容交还给写代码的 AI，让它能自己观察中间结果。

## Markdown 技能实验：技能有效，但先暴露了三个问题

**经过**：任务是“用 Python 写一个按 CommonMark 输出的 Markdown 转 HTML 库，并写测试”，用 42 个模型看不到的用例打分。

1. **不给技能**：多次运行稳定在 41/42 左右，嵌套强调 `*a **b** c*` 几乎总是失败。原因是强调用了正则逐层替换，没有用规范里的分隔符栈；测试又是凭记忆写的，覆盖不到难的边界。
2. **给两个技能后**：一个是按规格写测试，一个是 CommonMark 的要点和 103 个规范示例。第一批 3 次里有 2 次什么都没交出来。经过是：
   - 只负责“生成源码”的下层钩子，也把技能里的“实现后跑全部测试”当成自己的事，没有运行工具就拒绝交代码；
   - 上层又把更多要求塞给同一个钩子：生成并验证全部示例；
   - 那个钩子判断做不到，也放弃了。
3. **搜索的 bug**：下层查找“execute python … run tests”，查找规则是任意一个词命中就算，再按目录顺序截前 8 个，运行程序的方法排不进去。
4. **更深一层的问题在上层**：修好搜索以后，凡是上层把“一次写完整个模块”拆成块解析、行内解析几块的，都交出了结果；直接放弃的，都没有产出。
5. **按新设计改完再跑**：虚函数只做一件事、验证写在代码里、下层说做不到交给上层处理，3 次全部 42/42。在两组都没见过的 44 道规范考题上，有技能约 95%，无技能约 65%，差距几乎都在强调上。

**结论**：
- 技能补的是两样东西：关键处的做法，比如“强调用分隔符栈”，和能核对的依据，比如规范示例；
- 技能说明会带进每个 AI 函数，规则要写清是给谁的；
- 下层说做不到是信号，修的是上层怎么接；
- 查找要按相关度排序。

## 技能边界失守：业务技能被改得面目全非

**经过**：一个业务插件的技能，原本照一个成熟项目的生产流程写成。宿主架构重构期间，几个 AI 为了让宿主的改动跑通，一次次修改这份技能，加进宿主的机制，直到它的流程认不出来。

**结论**：
- 技能保留业务流程和规则，只把工具引用换成自己的工具；
- 宿主的机制不进技能；
- 宿主改了，不去改技能迁就；
- 只在用户要求时、在用户说定的范围里改技能。
