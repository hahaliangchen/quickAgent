# 怎样确认设计真的做到了

## 接通：用真实请求体证明

- **假模型抓请求**：用一个假的模型服务接住宿主发出的每个请求，断言里面的东西：
  - 工具列表；
  - 系统提示词就是这个角色该用的那份；
  - 注入的消息，比如技能说明、已有模块列表、任务输入；
  - 不该出现的内容确实没有，比如调用方的对话、内部编号、旧代码。
- **查数据库和事件**：每个关键动作都有事件或记录，测试里查这些记录，而不只看返回值。
- **新路径要能走到**：每条新代码路径都要能从真实主循环走到。只给处理函数写测试、而模型永远看不到这个工具，等于没做。
- **先复现问题再修**：先写一个用真实失败输入复现问题的测试，确认它失败，再修，再确认它通过。比如用真实运行里模型发出的那条查询，测查找结果里有没有该有的方法。
- **核对文字的原话**：改了提示词，在测试里断言请求里的系统提示词就是新文件的内容。

## 迁移：每一步都能跑

- **按顺序推进**：先改设计文档，标“待实现”；再改宿主代码；再改提示词；再改技能和示例；最后做真实验收。
- **每一步做完都跑全量测试**：和改动前对比失败名单，确认没有新增。
- **先新后旧**：先让新路径跑通真实示例，再删旧机制，避免项目长期跑不起来。
- **兼容旧状态**：已保存的旧状态，比如序列化的程序，要能按原来的方式继续，或者明确拒绝；不能悄悄改变含义。

## 验收：真实模型、看不到的用例

- **隐藏用例**：用真实模型跑真实任务，用模型看不到的验收用例打分；用例在运行结束后才放进去。
- **公平考题**：要看隐藏用例以外的质量，再准备一批双方都没见过的考题。期望结果用可信的参考实现生成，比如 CommonMark 用 micromark。
- **稳定性**：再测随机输入会不会崩溃，以及极端输入下的耗时。
- **记录**：记下分数、用时、模型请求次数，以及模型实际读了什么、调用了什么；后两样从事件记录里查，不靠猜。

## 对照：改提示词或技能时

- **同条件**：同一个任务、同一个模型、同样的推理强度，有和无两组同时跑，每组至少 3 次。
- **先定标准**：先定好判断标准，比如“关键用例 3 次中至少 2 次通过，且平均分不低于对照组”，再看结果。
- **先找原因**：结果不好时，先查事件记录找原因，再决定改哪一层。常见的原因有：模型没读技能，规则被下层用错，上层没接住失败，宿主有 bug。
- **记进文档**：结果和分析写进实验文档，包括没达到的部分和后来更正的结论。

## 失败分析：先看上一层

- **看真实请求**：读模型实际收到的请求体。它照字面执行，问题常常就在宿主自己写的那句话里。
- **顺着错误往上看**：对每个“做不到”，顺着调用链看上一层：它拆细了吗？换做法了吗？重写了吗？还是把下层的“做不到”当成了整个任务做不到？
- **分清来源**：是环境问题（网络超时、缺工具），还是设计问题，各自记清楚。

## 评审时要问的问题

1. 宿主有没有替模型做语义判断？
2. 这个新状态能不能不要？如果要，它什么时候产生、什么时候失效、谁来清理？
3. 模型会读到哪些原文？最后一句是不是平白的现状加下一步？有没有内部编号、哈希、遥测？
4. 有没有像对话开头的回放，会被模型当成新任务？
5. 这个机制在真实请求里出现了吗？能从主循环走到吗？
6. 下层失败时，上层能接住吗？
7. 提示词里有没有写成禁令？能不能改成建议？
8. 这条规则是给谁的？会不会被下层当成自己的事？
9. 能不能用语言已有的形式表达，而不是新造一个特殊调用？
10. 业务规则有没有混进通用宿主？宿主机制有没有写进业务技能？
11. 用户点名过最简形式吗？现在的方案有没有超出它？

## 和用户协作

- **区分提问和动手**：用户提问或边想边说时，只回答，不动手；收到明确的“改”“做”“实现”，或者用户点了按钮，才开始改。
- **只改点名的范围**：动手前说清要改哪一层、哪些文件，只改这些；不去改另一层来补这一层的问题。
- **没说的就是同意**：用户没反对的建议和细节，算是同意了，不要反复确认；但沉默或提问，不等于同意开始新的工作。
- **如实汇报**：说清哪些做了、哪些没做、哪些没验证；自己说错的地方，发现了就改正，并写进记录。
